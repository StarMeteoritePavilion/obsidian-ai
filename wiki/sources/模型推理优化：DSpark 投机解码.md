# 模型推理优化：DSpark 投机解码

原始资料：[[raw/sources/模型工程/推理优化/硬核解读 DeepSeek DSpark： 大模型推理快 60%-85%，投机解码的新天花板|硬核解读 DeepSeek DSpark：大模型推理快 60%-85%]]

## 核心结论

DSpark 同时优化投机解码的草稿生成与验证调度。半自回归生成让深层并行模型负责第一个 Token 所需的容量，再用轻量串行模块恢复后续位置的连贯性；置信度调度则按任务接受率和实时系统负载决定验证长度，而不使用固定值。

## 为什么并行草稿反而接受得更长

并行草稿缺少块内依赖，容易发生 Modal Collision 和 Suffix Decay，后续位置的质量弱于自回归草稿。投机解码却从第一个 Token 开始验证，只要首位被拒，后续全部失效。并行模型能够使用更深网络，首位准确率更高，这项优势足以使总接受长度超过自回归草稿。半自回归模块不是用完整自回归过程重做草稿，而是在并行底稿上用极轻量串行计算补充位置依赖。

资料给出的结果是：轻量串行模块增加约 1.5% 延迟，接受长度最多提高约 30%；两层半自回归草稿的接受长度约为 4.0，超过五层纯并行模型的约 3.1。综合四个目标模型，DSpark 接受长度约为 3.90，强并行与强自回归基线分别约为 3.25 和 3.00。

## 负载感知的验证调度

固定验证长度无法同时适配任务与负载。资料画面给出的接受率对比为：代码与数学任务约 92%，开放式闲聊约 46%，后者还会明显波动。置信度头估计每个草稿 Token 通过验证的概率。调度器以“预计接受的草稿数 × 每秒轮数”为有效吞吐目标，从高置信度位置开始扩展验证范围，在目标不再上升时停止。系统空闲时可以多验证，繁忙时则提前舍弃低置信度尾部。

调度依赖两个约束：概率必须经过校准，而不只是能够排序；早停只能依据已经确定的草稿部分，不能读取尚未确定的内容，否则会引入偏差并破坏无损性质。资料称，在闲聊任务中筛除低置信度尾部后，草稿接受率由 42% 提高到 95% 以上。

## 线上结果与边界

资料称 DSpark 已在 DeepSeek-V4 线上系统承载真实用户流量。旧线上基线每轮只猜一个 Token，因为静态增加草稿长度会在高并发下因过度验证拖垮吞吐。在吞吐对齐的前提下，DSpark 使单用户生成速度提高约 60%～85%，并在旧基线无法维持吞吐的高响应速度档位保持服务能力。

所有数字都属于资料转述的对应模型、硬件、任务和负载设置。实际收益依赖草稿模型、校准质量、任务接受率、批量大小与实时负载，不能直接外推到其他推理系统。
