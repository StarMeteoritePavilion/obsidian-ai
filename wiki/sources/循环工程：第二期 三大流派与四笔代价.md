# 循环工程：第二期 三大流派与四笔代价

原始资料：[[raw/sources/应用工程/循环工程/第二期：三大流派与四笔代价|第二期：三大流派与四笔代价]]

## 核心结论

同一套循环能力可以承载三种不同的自治哲学。它们的分歧不是工具能否工作，而是人能从执行循环中退出多远。人工介入越少，验证债、理解腐烂、认知投降和 Token 失控越需要由外部机制约束。

## 三种流派

- **结构化流派**：以 Addy Osmani 的观点为代表，用独立评判器、Git worktree 隔离和人工卡点保留工程责任。防护更强，代价是速度较慢。
- **极端流派**：以 Geoffrey Huntley 的 Ralph Wiggum 技术为代表，用单任务循环、外部规格、持久计划和程序化反馈追求最终一致。适合绿地项目，不适合直接用于已有代码库。
- **精准修正流派**：以 Rico Kahler 的观点为代表，把重复引导工作移入规则、Skill、CI、PR 模板或自动化任务，并用经济公式决定是否值得建设。

## 执行视界与盈亏平衡

执行视界是系统执行速度超过人产生、排序和审查好想法速度的转折点。越过这条线后，瓶颈由执行转为判断。

循环的基本盈亏平衡条件是：

`P × N × (S + R) > F`

建设成本必须低于预期复用次数带来的注意力节省与风险规避。工具、仓库、模型和人的要求变化还会使循环衰减，因此长期收益必须扣除维护成本。

## 四笔代价

1. **验证债**：系统产出速度超过审查速度，弱评判器无法证明结果可靠。
2. **理解腐烂**：代码持续变化，但人的系统地图停止更新。
3. **认知投降**：人因循环运行顺畅而停止形成自己的判断。
4. **Token 失控**：循环缺少预算、轮次和重试边界，消耗增长却没有对应进展。

四者形成因果链：弱评判器导致验证债，未验证变化导致理解腐烂，理解缺口诱发认知投降，持续加速又可能烧穿 Token 预算。

## 案例边界

资料引用 Geoffrey Huntley 分享的案例：一位工程师以 297 美元 API 成本交付价值 5 万美元的合同。该数字是来源中的个案，不代表一般回报率。

Ralph 还用于构建编程语言 CURSED 的编译器和标准库。Huntley 同时明确限制其适用范围：适合从零启动的绿地项目，不用于已有代码库。
