# 上下文工程：RAG 个人知识库基础架构

原始资料：[[raw/sources/应用工程/上下文与知识工程/这就是RAG 一看就懂的个人知识库架构|这就是RAG 一看就懂的个人知识库架构]]

## 核心结论

基础向量 RAG 不把整份长文档直接交给大语言模型，而是预先完成分块、Embedding 和向量存储；收到问题后，再用同一个 Embedding 模型编码查询、检索距离最近的文本片段，并把片段与问题共同组成上下文。这种方法能够减少无关信息并降低幻觉风险，但不能保证回答正确。

## 最小链路

1. 按字数、段落、句子或更复杂策略把文档切成片段。
2. 使用同一个 Embedding 模型把各片段转换为固定长度向量，并保留向量与原文的对应关系。
3. 将原文、向量及其关联写入向量数据库。
4. 用户提问后，把问题转换为同一向量空间中的向量。
5. 检索距离最近的若干片段，与问题一起交给大语言模型生成回答。

资料用 `text-embedding-3-small` 的 1536 维输出和 `text-embedding-3-large` 的 3072 维输出解释固定长度向量，并列举 Pinecone、ChromaDB，以及 PostgreSQL 配合 pgvector 插件的存储方案。这些名称与维度对应资料发布时举出的具体模型和产品，不构成其他系统的固定选型。

## 两项结构性限制

- **分块破坏语义关系**：如果“我是程序员老王，我爱吃瓜”被拆开，后半句中的“我”可能失去与“老王”的指代关系，使相关查询无法召回该片段。更复杂的分块策略只能减少误伤，不能彻底避免。
- **缺少全局视角**：统计全文中“我”字出现次数，需要遍历所有片段；没有哪个局部片段与问题特别相关，单纯按向量相似度选取少量内容难以完成这类任务。

资料提出两种改进方向：在预处理阶段把代词替换为明确对象，或让大语言模型根据语义决定分块位置。两者都只能改善特定问题，不是覆盖所有文档和查询的完整方案。

## 与现有知识的关系

本资料解释基础向量 RAG 的最小链路与局部检索边界。现有 RAG 系列资料进一步加入元数据、混合检索、RRF、重排序、查询增强、多跳和自适应路由；GraphRAG 则通过实体关系、来源映射、社区分层和全局搜索补充纯向量检索缺少全局视角的问题。
