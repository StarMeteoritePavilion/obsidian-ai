# AI 计算硬件：内存带宽、互联与软件生态

## 核心结论

- CPU 能执行模型运算；在大模型单请求推理中，参数从内存送往计算核心的带宽可能先于浮点算力成为瓶颈。
- HBM 缩短内存与计算单元之间的物理路径；批量处理多个请求又让同一批参数服务多个 Token，把瓶颈从数据搬运转向并行计算。
- 计算卡以大量专用核心换取吞吐。模型超过单卡显存时，推理主要传递中间激活，训练还必须跨并行组同步与参数同量级的梯度，因此对互联带宽要求更高。
- CUDA、HBM 与 NVLink 并非不可复制的单点。英伟达更深的优势来自 PyTorch、cuBLAS、cuDNN、CUDA 内核、算法优先适配和研究者习惯共同形成的软件—硬件生态。
- AMD ROCm 选择兼容既有生态，Google TPU／OpenXLA 选择重建完整技术栈；两者分别承担兼容性差距或迁移成本。

## 一条完整的瓶颈迁移链

| 场景 | 主要约束 | 资料中的解决方向 |
| --- | --- | --- |
| CPU 单请求推理 | DDR5 读取全部参数的带宽 | 用 HBM 提高内存带宽 |
| HBM 多请求服务 | 通用 CPU 核心数量 | 用大量专用计算核心并行处理批量请求 |
| 模型大于单卡显存 | 参数无法装入一张卡 | 沿模型顺序拆分参数，卡间传递中间激活 |
| 大规模训练 | 跨并行组同步同量级梯度 | 用 NVLink／Infinity Fabric 等高速互联 |
| 异构硬件落地 | 框架、算子与算法兼容 | 维护成熟软件栈，或建立新的端到端技术栈 |

这条链表明“峰值算力最高”不是完整的系统判断。单请求、批量推理、模型并行与数据并行训练的数据流不同，瓶颈也随之移动。

## 资料中的教学估算

Llama 3.1 405B 在 FP16 下约占 810GB。资料把每 Token 的参数计算简化为一次乘法和一次加法，得到约 $8.1\times10^{11}$ 次浮点运算；根据 EPYC 9965 估算的每秒 $2.8\times10^{13}$ 次运算，理论值超过每秒 30 Token，但 12 通道 DDR5 约 600GB/s，完整读取参数需约 1.35 秒，资料给出的实际速度约为每秒 0.7 Token。

这组数字用于解释算力屋顶与带宽屋顶的差异，不是通用基准。量化、批量、缓存、算子实现、内存访问模式和软件版本都会改变实际结果。

## 软件生态为何能放大硬件优势

PyTorch 负责上层模型表达，cuBLAS、cuDNN 等中间层把矩阵与深度学习算子映射到 CUDA 内核。二十多年积累使新算法和优化通常优先进入这套路径，硬件选择因而同时受到算子覆盖、框架集成、工具链和现有代码影响。AMD 的 ROCm 尝试兼容这一路径；华为昇腾还面临资料所述兼容性与 7nm 制程限制。

Google TPU 则以 MXU、ICI 和 OpenXLA 形成独立的计算、互联和软件栈，已经覆盖推理与训练。TPU 只通过 Google Cloud 出租，Gemini 完全使用 TPU 训练；资料还称 Anthropic 已开始租用 TPU 训练。独立技术栈减少对 CUDA 标准的依赖，同时限制可用软硬件范围，并提高开发者迁移要求。

## 适用边界

- 本资料是面向系统瓶颈的教学讲解，没有提供统一精度、批量、功耗、延迟与软件版本下的厂商实测。
- “中间激活几十到几百 MB”“批量复用 1,000 个请求”等是来源中的数量级或示例，不构成所有模型并行方案的固定数据。
- 厂商兼容性、制程、价格和供货会随时间变化；“时间是护城河”是作者基于生态积累得出的观点，而不是单项性能测试结论。
