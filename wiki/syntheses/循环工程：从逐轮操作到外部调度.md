# 循环工程：从逐轮操作到外部调度

循环工程管理跨轮次决策流：系统在一次执行结束后，自行触发下一轮、组织分工、检查结果、保存状态并决定继续或停止。它改变的不是某一句 Prompt，而是人和 Agent 在整个执行周期中的位置。（[[wiki/sources/循环工程：先导篇 从 Prompt 到 Loop|从 Prompt 到 Loop]]、[[wiki/sources/循环工程：第一期 什么是 Loop Engineering？|什么是 Loop Engineering]]）

## 人的位置从循环内部移到外部

在逐轮交互中，人负责给出下一条指令、观察结果并推动 Agent 继续，相当于循环中的“人肉时钟”。循环工程把触发与接力交给系统，人转而负责目标、边界、验证、停止和恢复。（[[wiki/sources/循环工程：先导篇 从 Prompt 到 Loop|从 Prompt 到 Loop]]）

这不是取消人的工程责任，而是把责任从内层执行移到外层判断。循环能够执行工作，但是否值得执行、证据是否足够、结果能否进入生产以及失败后由谁负责，仍需由人决定。（[[wiki/sources/循环工程：第一期 什么是 Loop Engineering？|什么是 Loop Engineering]]）

## 稳定结构：三层递进，一个外壳

两份资料对结构的表述存在演进：

- 先导篇把 Prompt、Context、Harness 和 Loop 描述为四层结构，用于概括系列路线。
- 第一期明确修正为 Prompt、Context、Loop 三层递进，Harness 是包住三层的整体工程外壳。

综合两份资料后采用第一期的精化模型：

1. **Prompt**：管理当前任务怎样表达。
2. **Context**：管理当前轮次能够看到什么。
3. **Loop**：管理跨轮次怎样触发、执行、反馈和停止。
4. **Harness 外壳**：为三层共同提供工具、权限、安全、隔离和恢复。

这一修正不改变前三项能力逐层扩展的关系，只改变 Harness 的位置：它不是单独的业务阶段，而是横切整个执行系统的工程环境。（[[wiki/sources/循环工程：第一期 什么是 Loop Engineering？|什么是 Loop Engineering]]）

## 三种自治哲学

第二期资料把循环设计归纳为三种流派。它们使用相近的工具，区别在于怎样分配人与系统的责任：

- **结构化流派**用独立评判器、隔离工作区和人工卡点限制自治范围。它优先保证可验证性与最终责任，代价是循环速度较慢。
- **极端流派**用单任务循环、外部规格、持久计划和程序化反馈反复修正结果。它接受更高的失败率和 Token 成本，但只适用于能够从零启动、具有明确反馈的绿地项目。
- **精准修正流派**先识别重复的引导工作，再用盈亏平衡公式决定是否值得把它固化为规则、Skill、CI、模板或自动任务。

三种流派没有统一的最优解。选择取决于任务能否外部验证、错误影响范围、人的审查能力、复用次数和维护成本。（[[wiki/sources/循环工程：第二期 三大流派与四笔代价|第二期]]）

## 循环成立的最低条件

多次执行不等于循环。一个循环至少需要三个连接动作：

1. **自行触发**：通过时间、事件或状态条件开始下一轮。
2. **组织执行**：自行拆分任务，并在需要时调度多个 Agent 协作和监督。
3. **持久反馈**：把结果与未完成状态写入对话之外的载体，供下一轮读取。

缺少自行触发，系统仍依赖人的下一条指令；缺少持久反馈，各轮执行彼此断开；缺少检查和停止条件，循环只能持续运行，无法证明任务已经完成。（[[wiki/sources/循环工程：第一期 什么是 Loop Engineering？|什么是 Loop Engineering]]）

## 从最低条件到可运行闭环

第三期资料把最低条件展开为五个可执行动作：

1. **发现**：读取 CI、Issue、Commit 和稳定项目规则，识别值得处理的问题。
2. **交付**：在隔离工作区中完成修改，避免并行 Agent 相互覆盖。
3. **验证**：由独立评判器根据测试和行为证据决定是否通过。
4. **持久化**：把结果送往 PR、Ticket 等外部系统，并保存下一轮所需状态。
5. **调度**：由时间或事件触发下一轮，不再依赖人手动启动。

Automations、Worktrees、Skills、Connectors、Sub-agents 和 Memory 六个组件分别为这些动作提供触发、隔离、规则、外部连接、独立判断和跨轮状态。Harness 提供承载它们的工程外壳，但只有加上调度和结果回流，一次 Harness 执行才会形成持续循环。（[[wiki/sources/循环工程：第三期 Loop 该怎么搭？|第三期]]）

## 评判器必须与生成者分离

生成者的上下文包含完整的实现理由，让它评价自己的结果时容易把意图当成证据。循环持续多轮后，这种自我确认会被反复放大，使验证债继续累积。

独立评判器需要同时具备三种隔离：

- **上下文隔离**：不继承生成者的自我说服过程。
- **职责隔离**：使用审查指令，必要时使用不同模型。
- **证据隔离**：通过测试、页面操作、DOM 和截图检查结果，不接受生成者的主观描述。

Ralph 使用单元测试、编译与类型系统、静态分析形成三层 Backpressure，也是同一原则的程序化版本：继续运行的权力由外部证据授予，而不是由刚完成工作的 Agent 自己决定。（[[wiki/sources/循环工程：第三期 Loop 该怎么搭？|第三期]]）

## 四笔代价会沿反馈链累积

Prompt 错误通常在当次输出中暴露，Context 错误通常表现为当前回答偏离。Loop 错误则可能在无人值守时被写入持久状态，再进入下一轮并持续放大。

第二期资料把这种放大归纳为四笔代价：

1. **验证债**：产出速度超过审查速度，弱评判器无法证明结果可靠。
2. **理解腐烂**：代码继续变化，但人的系统地图停止更新。
3. **认知投降**：人因系统运行顺畅而停止形成自己的判断。
4. **Token 失控**：循环缺少预算、轮次和重试限制，消耗增长却没有对应进展。

四者形成因果链：弱评判器产生验证债，未验证变化累积为理解腐烂，理解缺口诱发认知投降，持续运行又可能烧穿 Token 预算。（[[wiki/sources/循环工程：第二期 三大流派与四笔代价|第二期]]）

因此，自动化程度上升时，工程重点会从“怎样继续”转向“凭什么继续”：

- 每轮结果必须经过可检查的验证。
- 循环必须具有明确的完成和中止条件。
- 工具权限与影响范围应被 Harness 限制。
- 状态写回前需要防止错误成为下一轮的事实。
- 失败后必须能够恢复到可信状态。

这些边界共同决定循环能否从演示进入生产。（[[wiki/sources/循环工程：先导篇 从 Prompt 到 Loop|从 Prompt 到 Loop]]、[[wiki/sources/循环工程：第一期 什么是 Loop Engineering？|什么是 Loop Engineering]]、[[wiki/sources/循环工程：第二期 三大流派与四笔代价|三大流派与四笔代价]]）

## 执行视界与自动化经济性

当系统执行速度超过人产生、排序和审查好想法的速度，瓶颈会从执行转为判断。第二期资料把这个转折称为执行视界。

是否建设循环可以用 `P × N × (S + R) > F` 判断：预期复用次数带来的注意力节省和风险规避，必须超过建设成本。循环还会随工具、仓库、模型和人的要求变化而衰减，因此长期收益必须同时计算维护成本。（[[wiki/sources/循环工程：第二期 三大流派与四笔代价|第二期]]）

## 循环放大已有能力，也放大理解缺口

循环可以加速已经被人理解和验证的工作，也可以让未经理解的结果更快累积。两种用法采用相同的自动化结构，差别在于设计者是否仍对目标、约束、验证证据和最终后果负责。

所以，人的位置虽然从内层执行移到外层调度，但不能从工程判断中退出。循环设计的目标不是“无人负责”，而是让人的注意力集中在系统无法替代的边界判断上。（[[wiki/sources/循环工程：第一期 什么是 Loop Engineering？|什么是 Loop Engineering]]）

## 与上下文工程的边界

上下文工程负责为每一轮选择、压缩、隔离和清理信息；循环工程负责把多轮执行连接成能够继续、检查和停止的决策流。上下文是循环每一轮的输入治理，循环则决定这些轮次怎样连接。（[[wiki/syntheses/上下文工程：有限窗口中的信息治理]]）

当循环把结果写回下一轮时，两者在状态边界相交：上下文工程决定哪些历史状态值得重新进入窗口，循环工程决定何时读取、怎样使用以及何时停止继续传播。

第四期资料进一步说明，两层不只相邻，还复用同一套基础设施：

- Agent Skills 在 Context 层负责渐进式披露，在 Loop 层负责知识固化和跨轮复用。
- Sub-agents 在 Context 层隔离探索窗口，在 Loop 层分离 Maker 与 Checker。
- 工具平台在 Context 侧承载检索、压缩和结构化，在 Loop 侧承载调度、完成条件、并行与外部连接。

复用不等于职责混同。同一个组件进入更高层后，会从“怎样准备本轮输入”转为“怎样组织下一轮运行”。Prompt、Context 和 Loop 仍是三层递进，Harness 仍是包住三层的共同外壳。（[[wiki/sources/循环工程：第四期 搭好 Loop ≠ 能上线？|第四期]]）

## 从能运行到能上线

搭建循环可以压缩为五步：建立触发、接入发现源、保存状态、安装独立评判器、隔离并行工作区。前两步让系统开始自动运行，后三步让它具备跨轮记忆、拒绝错误和并行执行能力。（[[wiki/sources/循环工程：第四期 搭好 Loop ≠ 能上线？|第四期]]）

上线门槛则由六项检查共同定义：

1. 明确发现源。
2. 保存仓库内状态文件。
3. 设置独立 Evaluator。
4. 隔离并行工作区。
5. 设置 Token 或预算上限。
6. 保留人工复核点。

前两项回答循环能否运行，后四项回答循环失控时能否被发现、限制和停止。只完成自动发现和状态保存，会得到一个能够持续自我确认、却没有外部否决机制的循环。循环范围可以先小，但评判、预算和人的最终责任不能省略。（[[wiki/sources/循环工程：第四期 搭好 Loop ≠ 能上线？|第四期]]）

## 评估工程接管“凭什么继续”

循环工程规定 Maker 与 Checker 分离，却还需要回答 Checker 用什么数据、标准和方法作出判断。评估工程把这部分展开为真实输入、专家黄金答案、模型输出和评分，并按确定性选择代码、LLM 或人工裁判。

当评估进入 CI/CD，循环的停止条件和上线条件就能落到同一套业务质量门禁上：执行完成不再等于任务合格，只有通过独立评估的结果才能继续传播或进入生产。（[[wiki/sources/评估工程：第一期 排行榜遥遥领先，用起来怎么各种拉胯？|评估工程第一期]]、[[wiki/syntheses/评估工程：从通用基准到业务质量门]]）
