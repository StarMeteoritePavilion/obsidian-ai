# 提示词工程：从单轮指令到生产规范

提示词工程是在不修改模型权重的前提下，通过输入设计发挥模型已有能力。最有效的路线不是一次加入所有技巧，而是先识别失败类型，再增加能够直接解决该问题的最小机制。（[[wiki/sources/提示词工程：第一期 提示词工程入门|第一期]]、[[wiki/sources/提示词工程：第四期 多步编排|第四期]]）

## 六级问题分层

| 任务状态 | 优先方法 | 解决的问题 | 主要边界 | 来源 |
| --- | --- | --- | --- | --- |
| 模型已经理解简单任务 | 零样本指令 | 明确任务、输入和输出格式 | 复杂推理容易失败 | [[wiki/sources/提示词工程：第一期 提示词工程入门|第一期]] |
| 输出格式或标签不稳定 | 少样本演示 | 展示任务结构、标签空间和输出模式 | 普通示例不能传递多步推理 | [[wiki/sources/提示词工程：第二期 少样本提示|第二期]] |
| 任务需要多步推导 | CoT、零样本 CoT、Auto-CoT 或 ToT | 显式提供或搜索推理路径 | 依赖模型基础能力，并增加准备或推理成本 | [[wiki/sources/提示词工程：第三期 让 AI 先想再说|第三期]] |
| 单条路径不稳定或任务过大 | 自我一致性、链式提示 | 用投票降低偶发错误，或把任务拆成可检查步骤 | 增加 Token、调用次数和延迟 | [[wiki/sources/提示词工程：第四期 多步编排|第四期]] |
| 缺少知识、计算或行动能力 | 生成知识、解释器、工具调用 | 补充内部知识、精确计算和外部能力 | 生成知识仍会出错；代码需要沙箱；工具需要权限边界 | [[wiki/sources/提示词工程：第五期 知识增强与工具调用|第五期]] |
| 提示需要进入生产环境 | XML、system prompt、证据约束、长文排序和正向输出控制 | 提高复用、迁移、解析与核实能力 | 模型和 API 的版本行为必须重新核对 | [[wiki/sources/提示词工程：第六期 Anthropic 工程规范|第六期]] |

## 统一工作流

1. 定义任务、输入和可验证的输出契约。
2. 先用零样本建立基线。
3. 根据失败类型增加示例、推理、采样、拆分或工具，不同时增加无关机制。
4. 把中间结果结构化，使后续步骤和评估程序能够稳定解析。
5. 使用真实任务评估准确率、成本、延迟和失败类型。
6. 进入生产前，把稳定规则、动态输入、证据和输出格式分区，并锁定模型与 Prompt 版本。

该流程把提示词从一次性话术转成可迭代的工程对象。新增技巧只有在解决已观察到的失败时才有价值；否则只会增加上下文负担和维护成本。（[[wiki/sources/提示词工程：第一期 提示词工程入门|第一期]]、[[wiki/sources/提示词工程：第六期 Anthropic 工程规范|第六期]]）

## 三条选择原则

### 先匹配失败类型

- 格式失败优先修改输出契约或加入少样本示例。
- 推理失败优先增加推理过程、独立采样或任务拆分。
- 知识不足优先检索或工具调用，不能用更长的推理替代缺失事实。
- 计算不准优先交给解释器，不能把概率文本生成当成确定性计算。

### 让成本随必要性增长

零样本与少样本最轻，CoT 与链式提示增加生成长度和调用次数，自我一致性与思维树进一步增加采样和搜索，工具工作流还需要执行环境、权限与错误处理。方法越重，越需要评估证明收益超过成本。（[[wiki/sources/提示词工程：第三期 让 AI 先想再说|第三期]]、[[wiki/sources/提示词工程：第四期 多步编排|第四期]]、[[wiki/sources/提示词工程：第五期 知识增强与工具调用|第五期]]）

### 把输出当成接口

团队复用、链式处理和自动评估都要求输出具有稳定结构。XML、JSON 或明确字段不是排版装饰，而是模型与下一步骤之间的接口契约；结构必须与任务复杂度匹配，简单任务无需增加多余层级。（[[wiki/sources/提示词工程：第四期 多步编排|第四期]]、[[wiki/sources/提示词工程：第六期 Anthropic 工程规范|第六期]]）

## CoT 可见性不等于推理忠实性

CoT 能把中间步骤变成可读文本，却不能保证这些步骤忠实反映模型内部计算，也不能保证步骤与最终答案一致。1776 年平闰年案例中，模型正确复述判断规则，却输出相反结论；DataAlchemy 的受控实验还显示，当任务类型、推理步数或查询格式偏离训练分布时，可见思维链会明显退化。（[[wiki/sources/大语言模型：思维链的模式匹配与泛化边界|思维链泛化边界]]）

因此，增加 CoT 只是一种提示与输出组织手段。高风险任务仍需独立核验最终答案、检查关键步骤，并用任务、长度与格式扰动测试稳定性。论文实验支持训练分布依赖的解释，但不构成对所有大模型内部机制的完整证明。

## Prompt 与工具调用接口的边界

User Prompt 承载用户直接提出的问题，System Prompt 承载角色、背景和稳定规则。当工具说明与调用格式完全写入 System Prompt 时，Agent 需要自行解析模型按自然语言约定生成的结果；Function Calling 则把工具定义与调用请求变成专门的结构化接口。两种方式都向模型说明可用能力，但后者把格式契约从普通提示文本中分离出来。（[[wiki/sources/AI Agent 基础：Prompt、Function Calling 与 MCP|AI Agent 基础]]）

Function Calling 只规范模型怎样提出工具调用，实际函数仍由 Agent 或应用执行。MCP 位于另一侧，规范 Agent 怎样连接提供 Tool、Resource 与 Prompt 的外部服务。三者分别处理输入表达、模型调用接口和外部能力连接，不能互相替代。（[[wiki/sources/AI Agent 基础：Prompt、Function Calling 与 MCP|AI Agent 基础]]）

## 来源边界与冲突

- 第二期和第三期把少样本与推理能力描述为依赖模型规模的涌现能力；具体参数门槛应回到原论文或官方资料核实。
- 第六期复盘把“自我一致性”归入第三期，但第三期原始文章讨论 CoT、零样本 CoT、Auto-CoT 和 ToT，第四期才正式引入自我一致性。知识库按各期实际内容归类，同时保留这一来源内部差异。
- Claude 的 adaptive thinking、prefill、长上下文排序和 API 迁移要求具有版本时效性，接入具体模型前必须核对对应版本的官方文档。

## 与上下文工程的边界

提示词工程管理当前任务怎样表达；当问题扩展到对话历史、检索文档、工具定义、记忆、压缩和隔离时，进入[[wiki/syntheses/上下文工程：有限窗口中的信息治理|上下文工程]]。提示词是上下文的一部分，但不能独自承担全部信息治理。

简单问答允许用户逐轮用新 Prompt 纠正方向；Agent 的自主工具循环则会持续加入 Tool Call 与 Tool Response，用户最初的要求容易被中间信息淹没。System Prompt 可以规定记笔记和状态更新策略，但笔记插入、历史修剪、摘要替换、长返回外移和工具输出精简仍需要 Agent 以程序化方式执行，属于上下文治理。（[[wiki/sources/上下文工程：从 Prompt 到 Agent 上下文治理|Prompt 到 Context 导论]]）

## 与后训练的边界

提示词工程不修改模型权重，只在推理时组织输入；SFT、DPO、RLHF、RLAIF、RLVR 和 GRPO 等方法通过训练改变模型的行为倾向，属于[[wiki/syntheses/大模型后训练：从模仿到行为选择|大模型后训练]]。当模型已有能力但当前任务表达不清时先改 Prompt；当稳定失败跨任务反复出现，并且具备合格示范、偏好数据或可靠反馈时，再判断是否需要后训练。
