# 上下文工程：有限窗口中的信息治理

上下文工程管理模型在当前轮次能够看到什么。目标不是填满窗口，而是在容量、注意力、成本和延迟约束下，构建完成任务所需的最小、高信号、可追溯且已处理冲突的 Token 集。（[[wiki/sources/上下文工程：第一期 从 Prompt 到 Context|第一期]]、[[wiki/sources/上下文工程：第三期 原则、策略、评估|第三期]]）

## 信息治理闭环

```mermaid
flowchart LR
    A["窗口外信息"] --> B["写入与存储"]
    B --> C["路由、检索与选择"]
    C --> D["压缩与分层"]
    D --> E["结构化与隔离"]
    E --> F["组装当前上下文"]
    F --> G["模型生成与工具执行"]
    G --> H["检索、生成与端到端评估"]
    H --> B
```

闭环中的每一步都可能产生新信息、噪声或错误。工具结果、中间状态和失败证据不能自动升级为事实，必须经过验证、压缩、标记或隔离后，才能重新进入下一轮上下文。

## 六类上下文信息

| 信息类型 | 作用 | 主要风险 |
| --- | --- | --- |
| 系统指令 | 定义角色、规则和底线 | 与动态任务混合后被覆盖 |
| 对话历史 | 保存当前任务的累积状态 | 过长后引发分心和 Lost in the Middle |
| 外部知识 | 提供可更新、可追溯的事实 | 检索错误、来源缺失或提示注入 |
| 工具定义 | 声明可调用能力 | 工具过多会淹没任务信号 |
| 用户输入 | 指定当前目标 | 可能与既有规则或旧结论冲突 |
| 示例样本 | 展示期望行为与输出模式 | 示例失配会引导错误模式 |

这六类信息分别变化，不能依靠一段静态 Prompt 长期承载。系统需要按稳定性分层、按任务路由，并为每类信息保留身份和来源。（[[wiki/sources/上下文工程：第一期 从 Prompt 到 Context|第一期]]、[[wiki/sources/上下文工程：第六期 结构化与隔离|第六期]]）

## 四项核心策略

| 策略 | 核心问题 | 实施要点 | 失败信号 |
| --- | --- | --- | --- |
| 写入 | 哪些信息应离开窗口长期保存 | 保存知识、偏好、决策、状态和来源元数据 | 关键事实只存在于短期对话 |
| 选择 | 哪些信息应进入当前窗口 | 混合检索、重排序、查询增强、多跳与免检索判断 | 文档存在却答不到，或工具选择错误 |
| 压缩 | 怎样提高信息密度 | 抽取、摘要、结构化、层次化与冷热分层 | 约束丢失、否定反转、调试证据消失 |
| 隔离 | 怎样防止任务相互污染 | XML/JSON、物理隔离、逻辑分区、代码沙箱和独立子上下文 | 规则串扰、状态冲突和标签注入 |

四项策略不是顺序固定的一次性管道。检索不足会触发新写入，压缩丢失锚点需要调整摘要策略，隔离后的任务只应把必要结论返回主流程。（[[wiki/sources/上下文工程：第三期 原则、策略、评估|第三期]]、[[wiki/sources/上下文工程：第五期 上下文工程压缩|第五期]]、[[wiki/sources/上下文工程：第六期 结构化与隔离|第六期]]）

RLM 把隔离进一步用于后训练泛化：原始材料保存在代码变量中，子模型和工具返回也不自动进入主 Context；主模型只读取当前决策所需的局部探针结果。完整任务即使远离训练分布，每次调用仍可保持局部分布内。Context 的组织方式因此不只影响当前轮次质量，也可能影响强化学习能否学到跨长度、跨领域的组合策略。（[[wiki/sources/大模型后训练：RLM Harness 组合泛化|RLM Harness 专题]]）

## 长上下文的物理边界

输入与输出共享窗口容量。窗口扩大后，位置编码、KV 缓存、$O(n^2)$ 注意力计算和中间遗忘仍会限制有效质量；标称长度不等于稳定可用长度。因此，关键内容的位置、Token 精确计数和输出预留比单纯扩大窗口更重要。（[[wiki/sources/上下文工程：第二期 窗口与 Token|第二期]]）

Token 数量之外，Tokenizer 还决定信息以哪些离散片段进入模型。中文语义部件、答案前导空格和数字分组可能改变 Token 边界，进而影响初始向量、内部表示和输出分布。因此，上下文治理能够选择与组织文本，却不能消除模型分词与表示机制带来的架构层差异。（[[wiki/sources/模型原理：Token Space 与 Latent Space|Token Space 与 Latent Space]]）

应用层文本压缩与推理系统层 KV 缓存优化解决不同问题：前者减少模型接收的信息，后者降低长上下文的显存或复用成本。两者不能互相替代。（[[wiki/sources/上下文工程：第五期 上下文工程压缩|第五期]]）

模型架构层还有另一类问题：线性 RNN 使用固定大小的隐状态，成本随序列线性增长，却可能覆盖早期信息。Memory Caching 通过分段保存隐状态检查点并按需聚合，把效率与长程召回的取舍变成可调段长。它改变模型内部如何保存和查询序列状态，不替代应用层的信息选择、RAG、压缩或隔离。（[[wiki/sources/长序列建模：Memory Caching|Memory Caching]]）

多模态文档把这一边界放大。MMLongBench-Doc 案例中，完整视觉内容约需 206M 个视觉 Token，而所比较模型的上下文上限为 128K，相差 1,609 倍；资料据此估算只有约 0.06% 的 PDF 信息能直接进入窗口。该比例只属于对应基准与视觉表示，但它说明文档视觉内容不能依靠完整塞入 Context，必须在视觉压缩、检索粒度和外部索引之间分配信息预算。（[[wiki/sources/多模态模型：架构、数据、推理与检索|多模态技术地图]]）

MoBA 则保留 Transformer 架构，把上下文划分为 KV 块，再为每个 Query 动态选择少量相关历史块。它减少窗口内部实际参与注意力计算的连接；Memory Caching 增加线性 RNN 可检索的历史检查点；上下文工程筛选进入窗口的信息。三者分别处理稀疏计算、架构记忆和应用层信息治理，不能互相替代。（[[wiki/sources/模型架构：MoBA 混合块注意力|MoBA]]）

## RAG 的生产链路

RAG 把模型权重中的参数化记忆与外部可更新知识结合。生产质量不只取决于向量检索，还取决于分块、元数据、关键词与语义混合检索、RRF、重排序、查询扩展、查询分解、HyDE、多跳和自适应路由。（[[wiki/sources/上下文工程：第四期 RAG 检索增强生成|第四期]]）

外部技能库是另一类运行时上下文：它不检索事实文档，而是检索从成功与失败轨迹中蒸馏出的操作规则。SKILLRL 先用 SFT 教模型怎样使用技能，再在强化学习中约束并优化这种行为；验证失败还会反向更新技能库。这说明技能检索同时跨越上下文注入与后训练，但它仍受技能冗余、冲突、检索延迟和窗口预算约束。（[[wiki/sources/大模型后训练：SKILLRL 技能增强强化学习|SKILLRL 专题]]）

MemRL 则让运行时反馈直接改变情景记忆的检索顺序。系统先按语义相似度粗筛，再按历史任务成败形成的 Q-value 精排；模型权重保持冻结，环境奖励更新的是记忆效用和新记忆。它把“选择哪些外部经验进入当前 Prompt”变成可持续学习的决策，但仍依赖可靠奖励，并需要处理记忆增长、淘汰和多 Agent 污染。（[[wiki/sources/Agent 记忆：MemRL 运行时强化学习|MemRL 专题]]）

原始 RAG 论文中的 DPR、FAISS、BART 和端到端联合训练，与应用层“替换外部索引即可更新知识”的工程叙述处于不同层级。知识库保留两种表述，不把现代 RAG 管道等同于原始联合训练框架。

多模态 RAG 还需要保留页面布局、表格、图形和空间关系。ColPali 使用 PaliGemma 为页面 Patch 建立多向量视觉索引，在资料转述的 SlideVQA 设置中达到 `nDCG@5 = 54.4`；SimpleDoc 先做页面级粗排，再做元素级精排，在 MMLongBench-Doc 设置中达到 `G-Acc = 60.58`。页面级检索快但粗，元素级检索细但慢，分层检索是在二者之间建立工程折中，不会自动消除视觉编码、重排和生成的累计延迟。

资料称当前较优多模态 RAG 的端到端延迟约为 2～5 秒，距离 500ms 工业目标仍有约 4～10 倍差距。CMR 与 RAG 的融合则提出新的查询形式：用参考图像、修改文本和文档上下文共同检索证据。其价值取决于组合查询表示、证据定位和延迟是否能同时满足任务要求，不能只用离线召回率判断生产可用性。（[[wiki/sources/多模态模型：架构、数据、推理与检索|多模态技术地图]]）

## 2026 年五层生产架构

第八期资料把前七期方法组合为五层：（[[wiki/sources/上下文工程：第八期 2026 生产实践|第八期]]）

1. **Agent Skills**：启动时只暴露名称和描述，命中后再加载完整指令与资源。
2. **混合压缩**：保留近期对话、工具返回和尚未解决的失败证据，用摘要替换旧历史。
3. **上下文路由**：在信息进入窗口前，只加载当前领域的指令、知识和工具。
4. **自主检索**：Agentic RAG 管理搜索策略，GraphRAG 处理跨文档关系，Self-RAG 判断是否需要检索及结果是否足够。
5. **工具管理**：MCP 偏向结构化交互，Skill/CLI 偏向执行任务；两者都必须控制模型可见的工具数量。

五层的共同作用是把选择点前移：未命中的技能、无关领域知识、过时历史和不可用工具不进入当前注意力窗口。

## 失败诊断表

| 表现 | 主要原因 | 优先检查 |
| --- | --- | --- |
| 错误被后续持续引用 | 毒化 | 写回验证、来源元数据、RAG 替换 |
| 模型重复旧结论 | 分心 | 历史长度、摘要触发、窗口重建 |
| 工具多但选择错误 | 混淆 | 工具路由、按需加载、任务隔离 |
| 新事实无法纠正旧判断 | 冲突 | 早期结论、独立上下文、状态升级规则 |
| 文档存在却无法回答 | 检索或位置问题 | 分块、召回、重排序、Lost in the Middle |
| 相同失败反复发生 | 失败证据被过早删除 | 保留近期参数、原始返回和错误栈 |

四类退化及其案例来自第七期资料。资料中的模型排名、提升比例和 Token 节省属于对应实验或案例，不能脱离条件外推。（[[wiki/sources/上下文工程：第七期 上下文是怎么坏掉的|第七期]]）

## 与 Prompt 和 Loop 的边界

[[wiki/syntheses/提示词工程：从单轮指令到生产规范|Prompt Engineering]] 管理当前任务怎样表达；Context Engineering 管理当前轮次让模型看到什么；[[wiki/syntheses/循环工程：从逐轮操作到外部调度|Loop Engineering]] 管理系统跨轮次怎样触发、反馈、验证和停止。Prompt 是上下文的一部分，上下文是循环每一轮的输入治理，Loop 则连接多轮决策。

Harness 包住三层，为工具、权限、安全、隔离和恢复提供共同工程环境。Agent Skills 与 Sub-agents 会在 Context 和 Loop 两层复用，但职责分别是按需加载/隔离信息，以及固化规则/分离生成者与评判器。

## 来源边界

- 第三期资料同时出现“Bird Score”“ROGAS”和“RAGAS”，知识库不推断这些名称相同，落地前需核对原论文或官方项目。
- Claude API、Compaction、缓存、计费和工具命令具有版本时效性，必须按实际模型版本重新核对。
- 第八期资料中的行业时间判断和效果数字均保留来源属性，不作为跨系统通用结论。
