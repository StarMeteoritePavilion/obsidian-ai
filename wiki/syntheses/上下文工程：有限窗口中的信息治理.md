# 上下文工程：有限窗口中的信息治理

上下文工程管理当前调用能够看到什么，以及这些信息凭什么进入窗口。目标是在容量、注意力、成本和延迟约束下，保留完成任务所需的高信号证据、用户约束和执行状态；减少 Token 是手段，保持可验证的任务连续性才是判断标准。（[[wiki/sources/上下文工程：提示词、上下文与 Harness 的职责边界|职责边界]]、[[wiki/sources/上下文工程：第三期 原则、策略、评估|原则与评估]]）

## 信息治理闭环

```mermaid
flowchart LR
    A["窗口外资料与任务状态"] --> B["按问题选择"]
    B --> C["压缩、标记与隔离"]
    C --> D["组装当前上下文"]
    D --> E["生成与工具执行"]
    E --> F["核验结果与失败证据"]
    F --> G["带来源和状态写回"]
    G --> A
```

工具返回、模型总结和失败解释都是待判断的信息，不能因进入历史就自动成为事实。写回时区分已验证成果、尚未解决的问题和来源观点；后续选择还要检查适用条件与时效。否则一次错误会被重复检索、摘要和引用，形成上下文毒化。（[[wiki/sources/上下文工程：第七期 上下文是怎么坏掉的|上下文退化]]、[[wiki/sources/Agent 世界模型：服务于行动的选择性压缩|判断与知识的时效]]）

## 六类上下文信息

系统指令、对话历史、外部知识、工具定义、用户输入和示例样本承担不同职责。规则需要稳定，任务与证据持续变化，示例用于展示模式，工具定义只说明可调用能力。组装时应保留这些信息的身份、来源和优先关系，不能把不可信资料中的指令混成系统规则。（[[wiki/sources/上下文工程：提示词、上下文与 Harness 的职责边界|信息组成]]、[[wiki/sources/上下文工程：第六期 结构化与隔离|结构化与隔离]]）

预算也必须覆盖完整请求。Codex 与 Claude Code 的抓包都显示，用户短输入之外还有项目规则、运行环境、工具 Schema 与历史；只计算用户消息会漏掉主要开销。不同抓包的工具数、消息块数和 Token 数不一致，反映各自版本与配置，不能拼成固定启动成本。（[[wiki/sources/Codex：请求结构、服务端通信与 Token 计量|Codex 请求]]、[[wiki/sources/Claude Code：请求结构、SSE 与缓存 Token 计量|Claude Code 请求]]）

## 四项核心策略

| 策略 | 应作的判断 | 必须保住的内容 |
| --- | --- | --- |
| 选择 | 当前问题需要哪些证据、规则和工具；何时不再检索 | 任务相关性、来源与适用范围 |
| 压缩 | 哪些历史可摘要，哪些仍需原样读取 | 用户锚点、否定条件、近期工具配对与未解决的失败证据 |
| 隔离 | 哪些任务、外部内容和能力不应共享上下文 | 子任务边界与主流程必要结论 |
| 写回 | 哪些经验值得持久化，是否已验证、何时失效 | 来源、验证状态、决策依据、待办和失效条件 |

四项策略反复协作，不是固定顺序的一次性流水线。完整回传历史能维持短对话连续性，却不能替代长期选择与压缩；把大工具返回外移后按需读取，也必须保留定位与验证所需的信息。（[[wiki/sources/上下文工程：第三期 原则、策略、评估|四项策略]]、[[wiki/sources/AI Agent：工具调用、MCP 与最小实现|短对话历史回传]]）

### 选择：先缩小任务范围，再找证据

按查询路由领域规则、资料和工具，把选择前移到信息进入窗口之前；检索后再用重排序与证据筛选减少噪声。工具或 Skill 可先暴露名称与描述，命中后加载定义和参考材料，但描述重叠也会导致误触发。MCP 标准化连接，不自动解决工具定义过多的问题。（[[wiki/sources/上下文工程：第八期 2026 生产实践|生产组合]]）

### 压缩：摘要历史，恢复工作现场

抽取、生成摘要、结构化和冷热分层适合不同信息。稳定约束不能与普通历史一起有损压缩；长任务应先保存关键决策、待办与进度，近期参数、原始返回和错误信号仍需保真。清除不再需要的工具块与用摘要替换旧历史是不同操作，选择取决于任务是否还有未解决依赖。（[[wiki/sources/上下文工程：第五期 上下文工程压缩|压缩策略]]）

Claude Code 的 `/compact` 案例用 Summary、近期消息和附件共同恢复现场，并保护工具调用与结果的配对。它证明压缩后的可继续执行性需要单独设计，不能只凭摘要变短验收；具体模板、附件数量和阈值留在版本案例中。（[[wiki/sources/Claude Code：compact 上下文压缩与工作现场恢复|压缩与恢复]]）

### 隔离：分开信息，不等于验证事实

分隔符、XML 与 JSON 用于标识共享窗口内的信息身份；独立子上下文用于阻止任务状态和约束互相污染；沙箱限制执行能力。三者作用不同，结构标签需要转义动态输入，也不能代替权限边界。主流程接收必要结论和证据，不应默认收回子任务完整日志。（[[wiki/sources/上下文工程：第六期 结构化与隔离|隔离层次]]）

WebSearch 子 Agent 案例把网页结果留在工具较少的子上下文，主流程只接收链接与摘要，同时减少上下文负担和直接攻击面。但摘要仍可携带误导内容，隔离不证明事实可信；Skill 的渐进式披露同样不证明第三方提示词或脚本安全。（[[wiki/sources/Claude Code：WebSearch 子 Agent、服务端搜索与攻击面隔离|搜索隔离]]、[[wiki/sources/Claude Code：Skill 渐进式披露与第三方执行边界|Skill 信任边界]]）

### 写回：长期经验必须能够被纠正

Agent Memory 保存会话和执行经验，LLM Wiki 沉淀可长期维护的结论。两者都需要防止旧判断覆盖新事实：记录来源、验证状态、适用条件和失效条件；替代旧结论时保留其证据与时间。识别过期记忆不保证行动时会停止使用，历史成功率也不能代替当前环境校验。（[[wiki/sources/上下文工程：LLM Wiki 的摄取时编译与知识治理|知识治理]]、[[wiki/sources/Agent 世界模型：服务于行动的选择性压缩|记忆时效]]）

## RAG 的生产链路

向量 RAG 通过分块、Embedding、检索和上下文组装提供局部证据；生产中再组合关键词与语义检索、RRF、重排序、查询扩展或分解。相似不等于事实一致，分块会切断指代，HyDE 生成的假设文档不能当答案证据。原始 RAG-Sequence／RAG-Token 属于特定训练生成框架，普通“检索服务加通用模型”不等于复现它。（[[wiki/sources/上下文工程：RAG 从个人知识库到生产检索|RAG 链路与边界]]）

| 要回答的问题 | 主要机制 | 增加的责任 |
| --- | --- | --- |
| 某条事实或局部事件是什么 | RAG 从原始片段召回证据 | 分块、召回、重排和来源核验 |
| 实体如何关联，全文有哪些共同主题 | GraphRAG 抽取关系并生成社区报告 | 构图成本、实体消歧、生成关系与原文校验 |
| 多份资料共同支持什么长期结论 | LLM Wiki 在摄取时编译并持续维护知识页 | 冲突处理、版本替代、语义检查和人工审阅 |

三者可叠加，应按问题需要路由，不能仅凭资料量选替代方案。GraphRAG 的 Local Search 从实体扩展上下文；本库资料所述 Global Search 在选定层级的社区报告上执行 Map-Reduce，不逐层下钻原始文本。图谱和摘要仍由模型生成，来源映射只是可核验基础，不保证抽取正确。（[[wiki/sources/上下文工程：GraphRAG 从知识图谱到分层检索|GraphRAG]]、[[wiki/sources/上下文工程：LLM Wiki 的摄取时编译与知识治理|LLM Wiki]]）

LLM Wiki 把查询时的重复综合前移到摄取阶段，也使错误可能长期传播。不可变来源、段落级溯源、替代关系、结构与语义检查、人工审阅和高价值回答回写需共同工作；不能把派生页上的相互引用当作新增独立证据。（[[wiki/sources/上下文工程：LLM Wiki 的摄取时编译与知识治理|摄取时编译的治理代价]]）

DRAG 与 IterDRAG 则分配同一次任务中的文档数、演示数和迭代次数：前者展示完整证据问答，后者交替子查询、检索和中间答案。更多材料并非单调增益；方法选择要同时看有效窗口、问题跳数、调用成本与停止条件，论文配置不构成默认参数。（[[wiki/sources/上下文工程：DRAG 与 IterDRAG 推理扩展|检索与推理预算]]）

多模态检索还要保留布局、表格与空间关系。ColPali 的页面 Patch 多向量索引和 SimpleDoc 的页面粗排—元素精排展示不同粒度取舍；图像、修改文本与文档上下文组成的查询还需验证组合表示。容量与延迟数字属于各自实验，不能用离线召回率证明整条生产链可用。（[[wiki/sources/多模态模型：架构、数据、推理与检索|多模态检索]]）

### 从查询需求选择知识处理方式

可以沿下列顺序作选择；这是基于现有资料的采用指引，不是三套方法的性能排名：

1. **先确认是否需要检索。** 创意或不依赖外部事实的任务可不检索；全文统计应遍历完整材料，不能拿局部相似片段代替全集。局部事实查询先评估带来源的基础 RAG。（[[wiki/sources/上下文工程：RAG 从个人知识库到生产检索|RAG 的适用范围]]）
2. **再定位基础检索的不足。** 如果正确片段没有被召回，先检查分块、关键词与语义融合、重排；如果问题依赖跨实体关系或全局主题，再评估 GraphRAG，并承担实体消歧、社区报告核验及构图成本。多跳查询也可采用逐步检索，不因“多跳”就强制构图。（[[wiki/sources/上下文工程：GraphRAG 从知识图谱到分层检索|GraphRAG 成本与边界]]、[[wiki/sources/上下文工程：DRAG 与 IterDRAG 推理扩展|迭代检索]]）
3. **最后判断结论是否需要长期维护。** 多份资料持续进入、同一主题反复综合时，可用 LLM Wiki 保存结论与冲突，查询仍可调用 RAG 或图检索；一次性问答无需承担完整摄取和审核流程。（[[wiki/sources/上下文工程：LLM Wiki 的摄取时编译与知识治理|长期知识资产与维护代价]]）

采用后用同一组真实问题分别测量召回、答案证据、全局覆盖、延迟和维护成本。资料规模增长本身不构成升级理由；已有片段正确但生成忽略证据时，也不能只靠换索引解决。（[[wiki/sources/上下文工程：RAG 从个人知识库到生产检索|分层评估]]、[[wiki/sources/上下文工程：LLM Wiki 的摄取时编译与知识治理|按查询路由]]）

## 长上下文的物理边界

窗口需要预留输出空间，标称长度不等于稳定有效长度；位置效应、KV 显存与注意力计算仍会限制质量和成本。Tokenizer 决定文本的离散结构与占用长度，应用选择文本不能消除模型表示差异，也不能仅凭答案猜出错误发生在哪个内部环节。（[[wiki/sources/上下文工程：第二期 窗口与 Token|窗口限制]]、[[wiki/sources/大语言模型：Token、Embedding 与 Latent Space|表示边界]]）

| 机制 | 改变什么 | 不解决什么 |
| --- | --- | --- |
| 检索、修剪、摘要 | 模型收到哪些信息及其表达 | 模型内部缓存与计算方式 |
| KV Cache | 请求内复用已处理 Token 的 K／V | 证据筛选与跨任务事实更新 |
| Prompt Cache | 跨请求复用稳定前缀的 Prefill K／V | 不返回历史答案，也不消除新后缀和输出成本 |
| GQA、稀疏注意力、Memory Caching | 模型内部的共享、筛选或历史状态保存 | 应用层来源、冲突和任务治理 |

因此，缓存命中时上下文仍可增长；首轮成本不能直接乘以轮数，但缓存便宜也不是无限加入历史的理由。模型内部算法的召回和计算取舍由 [[wiki/syntheses/长上下文模型架构：共享、筛选、压缩与可增长记忆|长上下文模型架构]] 承接，请求内外复用由 [[wiki/sources/模型推理优化：KV Cache 与 Prompt Cache 的复用层级|缓存层级]] 承接。

缓存失效要区分模型边界、请求前缀变化和生命周期，不能统称为内容太长。Claude Code 的既有 Deferred Tool 按需加载与安装 MCP 后重建会话不是同一种变化；第三方代理对动态 `cch` 的处理也不能外推到官方服务。断点回溯、TTL、计费和接入配置必须回到具体版本检查，抓包计量不证明服务端物理 Hash 或 Block 实现。（[[wiki/sources/Claude Code：ToolSearch 延迟加载与缓存保持|按需加载]]、[[wiki/sources/Claude Code：模型、工具、注入与 TTL 的缓存命中边界|失效位置]]、[[wiki/sources/Claude Code：第三方 API 的 cch 缓存失效与 Attribution Header|代理边界]]、[[wiki/sources/模型推理优化：Codex 自动前缀缓存|观测与实现边界]]）

## 外部记忆与后训练的交界

MemRL 冻结模型权重，按语义粗筛、历史反馈形成的效用精排来选择情景记忆；SKILLRL 则把轨迹蒸馏成技能并与 SFT、RL 和验证驱动更新协同。两者都改变进入上下文的经验，但学习对象不同，不能把运行时记忆更新等同于参数训练；奖励可靠性、冗余、冲突和延迟仍需治理。（[[wiki/sources/Agent 记忆：MemRL 运行时强化学习|MemRL]]、[[wiki/sources/大模型后训练：SKILLRL 技能增强强化学习|SKILLRL]]）

RLM 将大材料和完整工具返回留在代码变量中，主模型只读取局部探针与分解逻辑，使长任务可由相近的局部调用组合。这显示上下文组织可能影响训练后的组合泛化，但证据主要覆盖可切分任务和一个底座，且训练仍可能学到短任务捷径；不能外推到高度耦合任务。（[[wiki/sources/大模型后训练：RLM Harness 组合泛化|RLM]]）

## 失败诊断表

| 表现 | 要区分的原因 | 优先核验 |
| --- | --- | --- |
| 错误被持续引用 | 未验证写回与过期知识 | 原始来源、验证状态、失效条件 |
| 重复旧结论、新事实不起作用 | 历史分心与判断冲突 | 旧结论位置、摘要保真、独立上下文 |
| 文档存在却答不到 | 召回失败、分块断裂与位置效应 | 先查检索片段，再查生成是否正确使用 |
| 工具多但选不准 | 定义噪声、描述重叠或路由错误 | 当前工具集合、按需加载与任务范围 |
| 同一失败反复发生 | 压缩丢证据或经验已过期 | 近期参数、原始返回、错误栈与环境变化 |
| 费用升高但任务无进展 | 历史增长、缓存失效或无界检索 | 完整请求、变化位置、实际命中和停止条件 |

这些是诊断入口，不是凭现象直接认定根因。验证应分三层：检索是否找到必要证据，生成是否忠实使用证据，端到端任务是否完成并满足成本与风险要求。BERTScore 只衡量表示相似度，RAGAS 是评估工具且指标随版本变化，两者都不能取代事实核验与人工标签校准。（[[wiki/sources/上下文工程：第七期 上下文是怎么坏掉的|退化机制]]、[[wiki/sources/上下文工程：第三期 原则、策略、评估|分层评估]]）

## 与 Prompt 和 Loop 的边界

[[wiki/syntheses/提示词工程：从单轮指令到生产规范|Prompt]] 负责表达任务，Context 负责当前信息治理，[[wiki/syntheses/循环工程：从逐轮操作到外部调度|Loop]] 负责跨轮触发、反馈与停止。[[wiki/syntheses/驾驭工程：模型之外的 Agent Harness|Harness]] 提供工具、权限、状态、恢复和审计环境；信息隔离与执行权限应协作，不能互相替代。

这套职责划分用于解释问题，不是统一行业层级。来源对 Harness 的范围采用不同口径，同一 Skill、子 Agent 或压缩机制可以承担多种职责。第八期的技能、混合压缩、路由、自主检索与工具管理，是这些策略的一种生产组合，不是每个系统必须安装的五个组件。（[[wiki/sources/上下文工程：提示词、上下文与 Harness 的职责边界|定义差异]]、[[wiki/sources/上下文工程：第八期 2026 生产实践|组合条件]]）
