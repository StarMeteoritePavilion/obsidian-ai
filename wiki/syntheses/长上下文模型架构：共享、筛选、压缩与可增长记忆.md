# 长上下文模型架构：共享、筛选、压缩与可增长记忆

长上下文不是单一容量数字。模型需要同时处理 KV Cache 容量、每步读取带宽、注意力打分成本、长程召回和训练稳定性。现有资料给出五条不同路线：共享 KV、稀疏筛选、序列压缩、线性与全注意力交替，以及为线性记忆增加可增长检查点。它们作用在不同位置，不能只按“支持多少 Token”横向排名。

## 五类机制

| 机制 | 改变对象 | 主要收益 | 主要代价 |
| --- | --- | --- | --- |
| GQA | 多个 Query Head 共享 KV | 压缩 KV Cache | 共享粒度影响表示容量 |
| DSA／MSA／MoBA | 只精算少量 Token 或块 | 降低主注意力计算 | 筛选本身仍需打分，Top-N 与块大小影响召回 |
| CSA／HCA | 先压缩序列，再稀疏选择或全量查看 | 同时减少索引与 KV 成本 | 压缩会改变细节保留方式 |
| 混合注意力 | 线性注意力与全注意力交替堆叠 | 用线性成本处理大部分上下文，用全注意力保留长程依赖 | 周期比例、实现细节和任务收益缺少消融 |
| Memory Caching | 保存分段 RNN 隐状态检查点 | 让线性模型重新查询早期状态 | 检查点存储随段数增长 |

## 共享 KV 不等于压缩序列

GQA 让多组 Query Head 共享较少的 Key／Value。在资料的教学配置中，64 个 Query Head 分为 4 个 KV 组，缓存降至原来的 1/16。它减少每个序列位置保存的 KV 数量，但没有减少序列位置本身。（[[wiki/sources/模型架构：GQA、DSA 与 MSA 长上下文优化|GQA、DSA 与 MSA]]）

因此，GQA 与稀疏注意力可以叠加：前者压 Head 维度，后者减少主注意力实际处理的位置。二者的节省口径不能相乘后直接当作端到端速度，因为筛选、访存和硬件利用率仍会产生独立成本。

## 稀疏筛选仍有索引成本

DSA 在 Token 级筛选，MSA 与 MoBA 在块级筛选。MoBA 把 Query 与历史块表示计算门控分数，再让被选块进入可变长度注意力；当前块必须始终参与，以满足因果生成。块级选择降低细粒度索引数量，却会把块大小、Top-k 和跨块依赖变成新的召回旋钮。（[[wiki/sources/模型架构：MoBA 混合块注意力|MoBA]]、[[wiki/sources/模型架构：GQA、DSA 与 MSA 长上下文优化|GQA、DSA 与 MSA]]）

筛选器并非免费。资料明确指出，打分注意力仍需接触完整上下文；即使它远小于主注意力，在百万 Token 下也可能成为线性瓶颈。

## 先压缩再筛选

DeepSeek V4 资料中的 CSA 先把时间维度约压缩四倍，再从压缩块中选择 1,024 个；重叠窗口使这些块约覆盖 8,000 个原始 Token。HCA 则进行更强的约 128 倍压缩，在约 8,000 个块上执行稠密注意力。两者在层间交错，一个保留局部细节，一个提供全局概览。（[[wiki/sources/模型架构：DeepSeek V4 的长上下文与训练稳定性|DeepSeek V4]]）

“先压再选”同时降低索引对象数量与主注意力范围，但压缩质量成为新的前提。资料中的 KV Cache、成本和能力数字只适用于对应模型、精度与服务口径。

Qwen 3.5 的混合注意力不压缩序列，也不先做 Token 或块级筛选，而是把线性注意力与全注意力按周期交替：资料所述 15 个周期中，线性注意力占 75%，全注意力占 25%。它改变的是注意力计算形态，而不是 KV Head 共享、稀疏索引或压缩后再选择。视频没有给出精确实现或消融，因此该比例只描述设计意图，不能据此比较各路线的实际召回或延迟。（[[wiki/sources/大语言模型：Qwen 3.5 的 MoE、混合注意力与应用演示|Qwen 3.5]]）

## 为线性记忆增加可增长容量

Memory Caching 不从 Transformer 注意力中删连接，而是为线性 RNN 保存分段隐状态检查点。GRM 按当前 Token 与历史段的相关性加权，Memory Soup 先融合记忆参数，SSC 只激活少量检查点。段长越短，召回能力与成本越接近 Attention；段长越长，系统越接近固定容量线性 RNN。（[[wiki/sources/长序列建模：Memory Caching|Memory Caching]]）

Fenwick Tree 的 Log-Linear 组织虽达到 $O(L\log L)$，但早期层级可能把最长约一半历史压入单个记忆，资料转述的召回结果反而较差。均匀分段的价值是把压缩压力分散到各段，而不只是降低复杂度。

## 模型内机制与应用层治理

模型能够处理更长序列，不表示应用应该把全部历史直接塞入窗口。RAG、摘要、结构化和上下文路由决定哪些外部信息进入模型；GQA、稀疏注意力、压缩注意力、混合注意力和 Memory Caching 决定进入模型后的表示与计算方式。（[[wiki/syntheses/上下文工程：有限窗口中的信息治理|上下文工程]]）

选择路线时应分别记录：有效召回距离、细节损失、KV 容量、每 Token 读取量、索引成本、主注意力 FLOPs、端到端延迟和任务准确率。任何单一指标都不能代表完整长上下文能力。
