# 为什么你的Agent总翻车？Harness Engineering全拆解：Anthropic、OpenAI、DeepMind都在押注的Agent Runtime

当模型已经足够强，Agent 仍然会在真实任务中翻车。问题往往不只在 Prompt 或模型本身，还在模型外部的运行系统：任务怎样拆解、上下文怎样管理、工具怎样编排、权限怎样设定、状态怎样交接、结果怎样验证、失败怎样恢复，以及什么时候把控制权交还给人类。这套运行系统就是 Agent Harness。

## 一、什么是 Harness Engineering（定义）

Harness 原指控制马匹的一整套马具。对应到 Agent，模型像一匹能力强、速度快却不知道方向的马，人类工程师负责确定方向，Harness 则把模型的原始能力导向有用工作。Harness Engineering 因而不是教模型怎样回答，而是设计模型怎样工作。

资料将 Prompt、Context 与 Harness 放在一条逐层包含的链路中（Harness 包含 Context，Context 包含 Prompt）：
- **Prompt Engineering**：关注怎样措辞、少样本示例与思维链，本质是优化单轮文本输入。
- **Context Engineering**：在操作系统层面管理工作内存（如 RAG、记忆注入、对话历史管理），解决“让模型看到什么”。
- **Harness Engineering**：管理模型能使用什么工具、拥有什么权限、怎样保持状态、必须通过什么验证、失败后怎样重试及何时由人接管。

> **概念追踪**：近年来，“Engineer the Harness”逐渐成为业内共识。包括 HashiCorp 联合创始人 Mitchell Hashimoto 的技术博客，以及 OpenAI 和 Anthropic 等头部厂商的技术探讨中，都曾提及通用 Agent Harness 及相关概念，强调系统运行环境的重要性。

## 二、兴起原因

为何 Harness Engineering 会在当前阶段集中升温？作者综合资料归纳了以下原因：

1. **系统设计成为主要差异**：模型能力提高后，只有在合适的工作环境约束下，才能稳定发挥能力。
2. **长时程任务的系统性缺陷**：跨上下文窗口的长任务容易导致裸模型耗尽上下文或提前宣布完成，更换模型不能自动消除此类问题。
3. **局部失败的累积效应**：假设每一步成功率为 95%，在**各步骤完全独立**的假设下，串联 20 步后的端到端成功率会降至约 35.8%（$0.95^{20}$）。单步可靠不代表整条流水线可靠，必须有系统级验证和恢复。
4. **模型能力趋同（作者观点）**：随着各大基础模型核心能力差距缩小，围绕模型构建的运行系统成为新的差异化竞争力。

## 三、跨组织案例对比与共性

不同厂商在构建 Harness 时采用了不同的架构，但“生成与评估分离”以及“外部化状态”成为高度共性的设计模式。

| 组织/项目 | 核心 Harness 架构与机制 | 效果与数据自述 | 备注与第三方评论 |
| :--- | :--- | :--- | :--- |
| **Anthropic** | 早期采用简单的双角色共享上下文；后向 Planner、Generator、Evaluator 等多 Agent 架构演进，并通过进度文件和 Git 历史等外部制品承接长任务。 | 官方及行业实践表明，由于模型自我评价易过度自信，工程化独立的评估 Agent 成为提升稳定性的常见选择。 | 架构的复杂化演进反映了长任务对评估独立性的要求。 |
| **OpenAI (Codex相关实践)** | 强调动态访问可观测数据；依赖自定义 Linter 与结构测试执行架构约束；通过后台 Agent 定期清理以对抗系统熵增。 | 据相关分享称，使用此类架构的小型团队能在数月内生成百万行级代码，实现极高的 PR 产出率与构建速度。 | 专家总结了类似架构的支柱，但也提醒应客观看待工具厂商对 AI 能力的宣传动机。 |
| **Google DeepMind (相关验证模型)** | 采用 Generator（生成解法）、Verifier（检查缺陷）、Reviser（修正错误）三者循环，直至通过验证。 | 官方声称该架构在特定数学或证明基准（如解决特定开放问题）上取得极高准确率。 | 业内也有评论指出，此类方案在脱离设计边界的更广泛问题集上错误率可能显著上升，泛化能力受限。 |
| **Gemini生态 (如Google ADK)** | 内置 Evaluation Harness，提供 CI/CD 脚手架；部分前沿研究引入加密推理状态（如 Thought Signatures），传回历史用于跨步恢复。 | 相关 SDK 的更新持续引入图式工作流等复杂机制。 | Anthropic 偏向外部制品，Google 偏向模型侧状态，两条路线效果待观察。 |
| **Vercel** | 实践中发现，从提供完整工具库转为移除大部分冗余工具。 | 官方称步骤、Token消耗和响应时间因此下降，成功率反而提高。 | 约束 Agent 的解决空间，反而能提高自主执行可靠性。 |
| **Stripe (如Minions)** | 在隔离且预热的 Devbox 中运行，通过 MCP 等标准访问大量内部工具。 | 强调从一开始就提供与工程师一致的上下文。 | - |
| **Manus** | 官方透露，产品达到生产就绪前经历了长周期的多次完整架构重写。 | - | 成熟 Harness 通常来自高成本、密集的迭代，并非一蹴而就。 |

**共性总结**：
- **生成与评估分离**：几乎所有成熟方案都不再信任模型的单次生成，而是引入独立 Evaluator 或确定性 Linter 拦截错误。
- **状态外部化**：进度不再仅存在于模型上下文中，而是沉淀为文件、Git 提交或独立的 Thought Signatures。

## 四、成熟 Harness 的六个模块

结合行业实践，成熟的 Harness 包含以下六个模块：

1. **上下文工程与知识管理**：利用 `AGENTS.md` 等预置指令和动态日志注入，使用子 Agent 隔离任务，并对溢出窗口进行压缩。
2. **工具编排与权限设计**：精心筛选工具集（避免冗余），管理 MCP 集成、文件系统访问与沙箱隔离。
3. **验证机制与硬约束**：使用 Linter、结构测试等不依赖模型判断的**确定性规则**拦截幻觉。
4. **状态管理与记忆持续性**：通过进度追踪、功能清单、增量检查点，解决会话重置问题。
5. **可观测性与反馈闭环**：记录轨迹，将生产失败归因至具体 Harness 缺陷，驱动系统迭代。
6. **人类接管与生命周期管理**：在关键风险节点（删除、扣费等）主动挂起并请求确认，提供重试与 Hook。

### 三类控制的责任边界（加深建议）

为了防止 Agent 失控，Harness 必须明确三类控制机制的责任边界：
- **确定性约束（代码/系统级）**：由 Linter、类型系统、沙箱权限负责。它们拥有**一票否决权**，绝不允许模型绕过规则（如语法错误、越权访问）。
- **模型评判（Evaluator Agent）**：负责语义层面的质量检查（如“逻辑是否自洽”、“是否满足需求”）。提供重试反馈，但不能替代确定性约束的安全底线。
- **人类接管（Human-in-the-loop）**：负责高价值决策（发布、扣费、销毁）。当系统遇到无法确定的风险或超脱预定义重试逻辑时，必须无条件将控制权交还人类。

## 五、风险与局限

1. **过度工程化与模型升级包袱**：Harness 必须随模型能力变化而删减。原本用于补偿旧模型缺陷的复杂机制，在新模型上可能变为累赘。
   - *Harness 回归验证清单（随模型升级时执行）*：
     1. 该模块最初是为了规避旧模型的什么缺陷而建？
     2. 移除该模块后，新模型在基准测试中的表现是否依然达标？
     3. 引入的中间层 Agent（如 Planner/Evaluator）是否拖慢了新模型本可一步完成的推理？
2. **风险放大效应**：多 Agent 配置和复杂的搜索逻辑可能增加意外污染。例如在类似 BrowseComp 等基准的评测复盘中，有时会观察到多 Agent 配置下非预期解法的发生率反而高于单 Agent 配置。这表明不当的 Harness 可能成为风险放大器。
3. **证据基础局限**：支持 Harness Engineering 的多数证据来自 AI 工具厂商（存在利益关系）。如 OpenAI 百万行代码案例使用的是熟悉 AI 系统的专家团队，缺乏在普通工程团队中的可复现性证明。

## 六、三步落地路径

针对准备引入 Agent 的团队，作者建议按以下三步逐步落地：

1. **短期起步**：立即在项目根目录创建 `AGENTS.md`，每当 Agent 重复犯错，就工程化一条经过验证的规则。
2. **中期巩固**：建立由 Linter、结构测试、Pre-commit Hook 和基本可观测性组成的**确定性验证层**。
3. **长期架构**：设计模块化、可替换的 Harness 系统，确保在底层大模型升级时能够平滑迁移，并及时剥离不再需要的冗余机制。
