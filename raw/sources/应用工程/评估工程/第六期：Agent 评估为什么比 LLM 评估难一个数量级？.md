# 第六期：Agent 评估为什么比 LLM 评估难一个数量级？

> 评估工程系列 第六期

评估 Agent 的核心难点在于：传统 LLM 评估检查的是“模型输出了什么文字”，而 Agent 评估检查的是“Agent 改变了什么状态”。“复杂度高一个数量级”是描述两者差异的定性判断，体现在跨越多轮的错误传播、极高的环境依赖以及多步非确定性上。

## 评估流程与五层架构

Agent 评估不再是单次文本校验，而是从任务定义到最终状态验证的完整流程。结合 Anthropic 相关的评估实践，这一流程建立在五层基础设施架构之上：

1. **指标层 (Metrics)**：定义成功标准，使用 `pass@k` 和 `pass^k` 等指标量化非确定性。
2. **评估套件 (Suite)**：按能力维度组织任务。
   - **Capability Suite（爬山）**：用于测试新能力，可以从零通过率开始，衡量模型的上限与进步。
   - **Regression Suite（护栏）**：用于测试已掌握的能力，在修改 Prompt 或升级模型后运行，任何分数下降都应触发警报。
3. **评估驭具 (Harness)**：评估基础设施，负责并发执行、环境重置隔离、步骤记录、评分聚合。注意区分 Harness 与 Agent Scaffold：Harness 用于**评估**模型，而 Agent Scaffold（如 Claude Code 或 CrewAI）是用于**运行** Agent 任务的外部系统框架。
4. **Agent 类型适配**：针对代码、对话、研究和计算机使用等场景，配置不同任务逻辑。
5. **评分器 (Graders)**：组合不同逻辑，最终检查状态产出。

## Agent 评估的八个核心术语

为了统一评估标准，业界（参考 Anthropic 等机构的 Agent 评估框架与术语定义）定义了以下核心概念：

- **Task**：最小评估单元，包含输入和成功标准。
- **Trial**：一个 Task 的一次尝试运行；由于 Agent 具有非确定性，同一 Task 需要运行多次。
- **Transcript**：一次 Trial 的完整运行日志，包括模型输出、工具调用、种子/时间/API 依赖记录以及环境反馈的中间结果。
- **Outcome**：Trial 结束时环境的最终客观状态（如文件内容、数据库记录），而不是 Agent 对其自身行为的自述。
- **Grader**：评分逻辑。一个 Task 可以配置多个 Grader。
- **Harness**：并发执行与评分的底层基建。
- **Suite**：组织在一起的 Task 集合。
- **Agent Scaffold**：让模型具备 Agent 能力的软件编排系统。

## 为什么 Agent 评估更加困难？

### 错误传播与累积（失败归因）

Agent 的执行是多步的。如果前一步工具选择错误，后续步骤就会基于错误状态继续，导致失败级联。通过阅读 Transcript 进行失败归因变得至关重要，仅看最终得分无法定位故障发生在哪一步。

### 非确定性与 `pass@k` / `pass^k` 的统计

工具调用的细微差异、时间因素和 API 响应都可能改变行为。同一任务必须执行多次 Trial。
- **`pass@k`（至少成功一次）**：衡量 k 次独立尝试中至少成功一次的概率，公式为 $1 - (1 - p)^k$。假设单次成功率 $p = 75\%$，则 `pass@10` 接近 100%。此估算假设各次 Trial 是**独立同分布 (IID)** 的。如果环境未重置或采用固定种子连续失败，该独立假设将失效。
- **`pass^k`（每次都成功）**：衡量 k 次尝试全部成功的概率，公式为 $p^k$。在同样 75% 成功率下，`pass^10` 约为 5.6%（$0.75^{10} \approx 0.0563$）。

两项指标反映了不同的产品要求：是只需要“总能找到一个可用答案”（如代码生成），还是要求“每次都不出错”（如金融交易）。

### 环境状态隔离与重置

Agent 评估必须依赖真实的沙箱环境。每次 Trial 必须从干净状态启动，进行**环境重置**。如果状态隔离不彻底，就会出现信息泄漏——例如测试中曾观察到 Agent 从上一次 Trial 的 Git 提交历史中提取信息作弊，导致评估结果虚假偏高。

## 检查状态，而非检查自述

Agent 评分的核心原则是：**检查 Outcome（最终状态），而不是限制路径。** 要求 Agent 必须按特定顺序调用工具，会把“实现路径”误认为“任务目标”。客服 Agent 即使态度礼貌，若未在系统中写入退款记录也应判失败；反之，只要代码通过了所有单元测试，即使中间推理步骤冗长也算成功。

为了检查状态，通常组合三种评分器：
- **Code-based**：单元测试和静态分析，提供客观、快速的反馈。
- **Model-based**：用 LLM 检查多轮对话的语气或研究结果的信息覆盖度。
- **Human Grader**：人工审核，用于验证与校准自动评分器。

## 四类 Agent 的评估配方

尽管术语和架构相同，不同 Agent 的基准与评分器组合各有侧重：

1. **Coding Agent**：依赖 Code-based 评分器进行确定性测试（fail-to-pass 和 pass-to-pass）。以 SWE-bench Verified 为例，其解决率在一年内（至2024年下半年）从约 40% 快速上升至 80% 以上，随着基准趋于饱和，需要更难的任务来持续区分模型能力。
2. **Conversational Agent**：通常使用第二个 LLM 模拟用户进行对抗对话，并检查业务状态是否正确变更。涉及的基准如 τ-bench (tau-bench)（原视频音译或笔误为 T-Bench/T²-Bench），专门用于测试真实的工具调用与对话。
3. **Research Agent**：结合信息支撑度 (Groundedness)、覆盖率 (Coverage) 和来源质量。
4. **Computer Use Agent**：在真实 GUI 沙箱中操作并检查界面与后端状态。典型任务定义参考 [WebArena](https://webarena.dev/)（现实网站环境任务）与 [OSWorld](https://os-world.github.io/)（操作系统级别的多模态任务环境）。

## 持续运行的评估体系

建立 Agent 评估不应等待完美架构，而应遵循从易到难的迭代路径：
1. 从 20～50 个简单任务起步，跑通手动闭环。
2. 确保成功标准可由任何人客观判定，无歧义。
3. 平衡问题集，覆盖高频问题和边缘错误情况。
4. 保证每次 Trial 的严密环境隔离。
5. 优先设计确定性评分器。
6. 定期阅读 Transcript 分析关键技能与失败起点。
7. 长期维护：当 Capability 达标后，将其纳入 Regression 体系长期自动运行（如 CI/CD）。
