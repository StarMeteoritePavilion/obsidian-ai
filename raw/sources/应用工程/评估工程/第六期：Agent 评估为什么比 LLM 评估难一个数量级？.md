> 评估工程系列 第六期

前五期讨论的代码评分、LLM 裁判、SLM 裁判和产品评估，基本围绕单次调用展开。Agent 则会跨越多轮，调用工具、修改文件、查询数据库，并在环境中留下状态。一个错误不再只是一句不合规的回复，而可能沿着“选错工具—改错状态—后续全错”的链条传播。

Agent 评估与 LLM 评估的根本区别是：LLM 评估检查模型输出了什么文字，Agent 评估检查 Agent 改变了什么状态。客服 Agent 即使表达礼貌，没有真正创建退款记录也应判为失败；编程 Agent 即使推理过程混乱，只要最终代码通过全部单元测试，仍可能完成任务。

## Agent 评估更加困难的原因

### 错误会传播和累积

Agent 不是一次调用后直接给出结果，而是一条多步执行链。前一步推理、工具选择或状态修改出现偏差，后一步就会基于错误状态继续运行。只检查最终回复无法解释错误从哪里开始，也无法判断环境是否已经受损。

### 结果具有非确定性

同一任务运行三次，可能得到三个不同结果。模型随机性、工具返回的细微差异和时间敏感的 API 调用都会改变行为，因此单次运行没有足够的统计意义，同一任务需要执行多次试验。

### 评估依赖真实环境

Agent 声称已经完成退款，不等于数据库中真的出现了退款记录。Agent 评估必须检查文件、数据库、页面和后端等环境状态。错误传播、非确定性和环境依赖叠加后，资料将其复杂度概括为比传统 LLM 评估高一个数量级。

## 五层评估架构

Agent 评估由五层共同组成：

1. **评估套件 Suite**：按能力维度组织任务，分为 Capability Suite 和 Regression Suite。
2. **评估驭具 Harness**：负责并发执行、环境隔离、步骤记录、评分和结果聚合；共享状态是评估的主要风险。
3. **评分器 Graders**：组合 Code-based、Model-based 和 Human 三类评分逻辑，检查产出而不是路径。
4. **指标层 Metrics**：使用 `pass@k` 和 `pass^k` 描述多次试验中的不同成功要求。
5. **Agent 类型适配层**：为 Coding、Conversational、Research 和 Computer Use Agent 分别配置评分器。

## 八个核心术语

- **Task**：最小评估单元，包含输入和成功标准。
- **Trial**：一个 Task 的一次尝试；同一 Task 因非确定性需要运行多次。
- **Grader**：评分逻辑。一个 Task 可以配置多个 Grader，每个 Grader 也可以包含多个检查。
- **Transcript**：一次 Trial 的完整记录，包括输出、工具调用、推理步骤和中间结果。
- **Outcome**：Trial 结束时环境的最终状态，不是 Agent 对自己行为的描述。
- **Harness**：并发执行、记录、评分和聚合的评估基础设施。
- **Suite**：按能力维度组织的一组 Task。
- **Agent Scaffold**：让模型成为 Agent 的软件系统，负责处理输入、编排工具和管理状态，例如 Claude Code 与 CrewAI。

## Capability 爬山与 Regression 护栏

Capability Eval 回答“Agent 能做什么”。它可以从零通过率开始，把退款处理等新能力拆成可运行的评估任务，再用 30%、60%、90% 等通过率量化进步。

当 Capability Eval 达到高通过率后，可以转入 Regression Suite。Regression Eval 回答“Agent 还能做以前的事吗”，每次修改 Prompt、更换模型或升级依赖后自动执行；任何分数下降都应触发检查。Capability 用于爬山，Regression 用于护栏。

## `pass@k` 与 `pass^k`

`pass@k` 衡量 k 次尝试中至少一次成功的概率。k 越大，这个值越接近 100%，适合代码生成或研究等“一次成功就够”的场景。

`pass^k` 衡量 k 次尝试全部成功的概率。k 越大，这个值越低，适合客服和金融交易等用户期望每次成功的场景。

两项指标在 k 等于 1 时相同，随着 k 增大却走向相反。资料以 75% 的单次成功率为例：`pass@10` 几乎达到 100%，`pass^10` 只有 5.6%。选择哪项指标，本质上是在决定产品需要“总能找到一个可用答案”，还是“每次都不出错”。

## 检查产出，不检查路径

Agent 评分的核心原则是检查产出，而非检查路径。如果规定 Agent 必须先调用 `search_code`，再调用 `read_file` 才能得分，就会把一种实现路径误当成任务目标。正确的检查对象是代码是否通过单元测试、退款记录是否创建、配置文件是否正确修改。

三类评分器各有侧重：

- **Code-based**：编程 Agent 的首选，使用单元测试和静态分析产生快速、客观、可复现的信号。
- **Model-based**：对话和研究 Agent 的主力，使用 LLM rubric 与断言检查语气、同理心和信息完整性。
- **Human Grader**：金标准和校准基准，通过 SME review 与 spot-check 验证自动评分器。

## 四类 Agent 的评估方案

### Coding Agent

确定性单元测试是核心评分器，同时检查 fail-to-pass 和 pass-to-pass。资料以 SWE-bench Verified 为例，称其一年内从约 40% 上升到 80% 以上，开始趋于饱和，需要更难的任务继续区分能力。

### Conversational Agent

使用第二个 LLM 模拟用户，向被评估 Agent 发起对抗性多轮对话。评分同时检查工单是否关闭、退款是否处理等状态，以及语气、同理心和解释清晰度等 LLM rubric。资料列出的相关基准包括 T-Bench 与 T²-Bench。

### Research Agent

研究任务通常没有唯一标准答案，需要组合 Groundedness、Coverage 和 Source Quality 三类评分器，分别检查证据支撑、事实覆盖和来源权威性。资料列出的相关基准是 BrowseComp。

### Computer Use Agent

在真实 GUI 沙箱中运行，检查 URL、页面状态和后端数据，确认界面操作是否真正改变了系统。资料列出的相关基准包括 WebArena 与 OSWorld。

四类 Agent 使用同一套术语和流程，但评分器组合不同。Agent 评估不是 LLM 评估的放大版，而是针对环境行为和最终状态重新设计的系统。

## 从零开始的八个步骤

1. **起步**：先建立 20～50 个简单任务，选择典型场景，尽快跑通闭环。
2. **手动检查**：手动运行全部任务，确认任务定义没有歧义。
3. **写清楚**：让任何人都能根据成功标准判断通过或失败。
4. **平衡问题集**：覆盖高频、边缘和已知失败，不只测试确定能通过的情况。
5. **隔离环境**：每次 Trial 都从干净状态启动，防止共享状态泄漏信息。资料提到，内部曾发现 Agent 从上一次 Trial 的 Git 历史中取得信息。
6. **设计评分器**：确定性检查优先，Model-based 补位，Human 负责校准，并始终检查产出而非路径。
7. **阅读 Transcript**：不能只看总分，还要检查 Agent 的实际行为，并从完整记录中识别关键技能和失败起点。
8. **长期维护**：让成熟的 Capability 进入 Regression，持续添加新任务，并在评估饱和时设计更难的任务。

资料给出的演进示例是：第一周手动运行 20 个任务，到第六个月在 CI/CD 中自动运行 500 多个任务。延迟建设评估，只会使补齐环境、任务和回归证据越来越困难。

## 总结

本期内容可以归纳为五点：

1. Agent 评估检查的是状态变化，不只是最终文本；错误传播、非确定性和环境依赖使它成为独立的评估问题。
2. Task、Trial、Grader、Transcript、Outcome、Harness、Suite 和 Agent Scaffold 构成共同词汇表，Capability 与 Regression 分别负责爬山和护栏。
3. `pass@k` 衡量至少一次成功，`pass^k` 衡量全部成功，两者代表不同产品责任。
4. 评分器应检查产出而非路径，并按 Coding、Conversational、Research 和 Computer Use Agent 组合不同配方。
5. 从 20～50 个任务起步，经手动检查、环境隔离、评分器设计和 Transcript 阅读，逐步形成持续运行的评估基础设施。
