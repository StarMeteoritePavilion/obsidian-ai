# 第一期：排行榜遥遥领先，用起来怎么各种拉胯？

## 通用榜单回答什么，业务评估回答什么

大模型在 ARC（小学科学）、MMLU（多任务语言理解）、TruthfulQA（真实性）、HellaSwag（常识推理）与 GSM8K（小学数学）等知名测试集上表现靠前，回答了模型在“通用能力标准化考试”中的水平。这些指标是典型的通用排行榜（Benchmark），主要用于横向比较各家模型的基础能力。

但在实际业务中，系统面对的是用户在特定情境下的非结构化输入，而非标准选择题。通用 Benchmark 无法替代业务评估：前者衡量基础常识与推理边界，后者则回答模型在“当前业务数据和场景中是否真正可用”。评估的本质，是将模型的基础能力映射为可衡量的业务可用性判断。

## 最小评估闭环

一次可靠的业务评估不再是单纯跑分，而是一个包含以下四个核心组件的质量闭环，缺失任何一环都会带来虚假的安全感：

1. **输入样例（Task/Trial）**：优先来自真实业务分布，并补入高风险边界案例；合成样例必须单独标记和验证。
2. **参考答案或成功条件（Golden Answer）**：由熟悉业务的领域专家定义，并通过复核与争议处理控制标注误差，不把单人答案视为天然绝对正确。
3. **模型输出（Transcript）**：在真实运行环境（如 Agent Harness）中，记录系统实际生成的完整运行轨迹。*（注：根据 Anthropic 的工程规范，Agent 的结果判定 Outcome 不能只依赖模型的语言自述，还必须检查它对真实环境状态引发的实质性改变。）*
4. **评分（Grader）**：将模型实际输出与黄金答案进行严格对比判定。

### 三种互补的评分方式

在这个闭环中，对输出进行判定（Grader）通常有三种方式，实际业务中应根据任务的主观性与确定性组合使用：

- **人工裁判**：领域专家逐条查看结果（如使用 Likert 量表打分或 A/B 比较）。它是处理主观、模糊和强上下文任务的理论“金标准”，但实际应用的前提是必须解决**“标注者一致性”**问题，并且受限于专家的真实业务资格。此外，它成本高昂、难以规模化。
- **代码扫描仪**：通过 Python 编写精确规则（如正则、关键字提取），成本最低且速度最快，适用于有确切标准答案的任务。但在面对语义多样化或上下文极度依赖时，极易出现误判。
- **LLM 裁判**：用能力更强的模型依据严格的评分标准（Rubric）检查输出。它在速度与语义理解之间取得了平衡，但需要高度校准，否则模型的原生偏见会直接污染评估结果。

## 评估成熟度路线表：从 Workbench 到 CI/CD

建立评估体系并非搭建巨石阵，而是按业务成熟度逐步展开的三步路线：

### 第一阶段：Workbench 实验原型

- **做法**：在实验环境中抽取少量真实用例，人工逐条打分并快速迭代 Prompt。具体平台不影响这一阶段的目的。
- **目标**：不追求平台化，重点是形成对模型“在当前场景哪里可用、哪里不可用”的直观体感与基本判断。

### 第二阶段：半自动混合评估

- **做法**：引入自动化判断，将有标准答案的部分交由代码评分，复杂主观的部分保留人工裁判，人机混合执行。
- **样本管理**：在这一阶段，测试集需要扩大。原视频作者给出的经验起点是 **100 对以上**（30～50 对仅提供类似抛硬币的信号，100 对才具备基础的决策指导意义）。但“100条”并非科学硬规则，实际样本量必须结合业务能容忍的失败率、决策风险，通过**置信区间**等统计学方法精确倒推。
- **数据要求**：数据集不能随意抓取，须通过**分层抽样**确保不仅涵盖高频问题，更要覆盖极易失败的边缘情况和长尾输入。同时要严格进行数据集切分并引入**污染防范**机制，避免“刷题式”评估。

### 第三阶段：CI/CD 自动化门禁

- **做法**：将评估无缝嵌入研发的持续集成与部署（CI/CD）管道。
- **样本管理**：作者以 **1000 对以上**作为自动回归阶段的经验量级；实际数量仍由失败率、分层覆盖和门禁风险决定。
- **流程**：每次 Prompt、代码或配置变更都会自动触发管道评估。过程以自动化评分为主、人工定期抽检兜底；任何不及格的变更都将由代码门禁直接拦截。评估体系的判断标准、数据用例也在这条管道中基于真实世界的报错进行持续迭代。
