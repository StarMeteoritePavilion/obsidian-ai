> 评估工程系列 第四期

上一期介绍了 LLM 裁判：它能处理代码规则无法覆盖的语义判断，但一次评估要消耗一两千 Token，百万次评估可能花费 1 万至 5 万美元，延迟达到 1～3 秒。成本迫使团队只抽样检查约 1% 的流量，而最严重的失败往往正是最少见的部分。

SLM 裁判选择另一条路线：把小模型微调到只做一种判断。它不会写诗、翻译或解数学题，而是把模型容量集中到安全、合规或质量分类等单一任务。资料将这种专用模型概括为手术刀，将通用大模型比作瑞士军刀。

## LLM 裁判在生产规模上的三个问题

### 成本随流量线性增长

在百万条对话规模下，单个评估指标每月可能花费 1 万至 5 万美元。若同时检查毒性、PII、合规和质量四个指标，调用成本也会相应叠加到 4 万至 20 万美元。用户量增长 10%，账单也增长 10%，固定开销无法通过规模摊薄。

### 延迟难以进入实时链路

LLM 裁判一次判断需要 1～3 秒，实时场景中的用户无法等待每项评估串行完成。资料给出的 SLM 裁判延迟范围是 15～150 毫秒，更适合放进在线请求链路。

### 抽样会漏掉罕见失败

当成本只允许检查 1% 的流量时，随机抽样默认失败均匀分布，但生产事故通常集中在罕见的边缘输入中。资料以一个金融科技合规团队为例：LLM 裁判每天花费 3 万美元，以 94% 的准确率覆盖 1% 流量；替换为 SLM 裁判后，每天花费 600 美元，在同等准确率下覆盖全部流量。

## 四类 SLM 裁判

### Llama Guard 3

Llama Guard 3 由 Meta 推出，面向安全分类。资料介绍的 8B 版本在安全分类上超过 GPT-4；经过蒸馏后，1B 模型压缩到 440MB，能够在手机上运行，F1 只下降 1.3%。

### Luna

Luna 是 Galileo 开发的评估专用模型。它不生成完整文本，而是直接从 log probabilities 输出判断结果，延迟低于 50 毫秒。资料称其在幻觉检测上超过 GPT-5，成本约为后者的五十分之一。

### PHUDGE

PHUDGE 基于 Microsoft Phi-3 的 3.8B 模型微调，在四个基准上取得 SOTA。这个结果被用来说明：对单一评估任务而言，微调数据和方法的质量可能比模型体积更重要。

### Prometheus 2

Prometheus 2 是开放权重的 7B 模型，可以在消费级显卡上运行。资料给出它与 GPT-4 评估结果的 Pearson 相关性为 0.6～0.7，并将其作为自行搭建 SLM 裁判的开放基线。

这些模型分别侧重安全、速度、性价比和开放部署，不存在一把适用于全部评估场景的通用工具。

## 专一化为什么可能更快、更准

通用大模型执行毒性检测时，百科知识、多语言能力、编程和数学推理等大量能力并未参与当前判断，却仍然占用模型容量和计算成本。SLM 把容量集中到一个边界清晰的任务上，减少与当前判断无关的能力。

执行架构也不同。资料中的 SLM 使用单 Token 分类头直接输出概率，LLM 裁判则需要完成自回归文本生成。前者省去长文本生成过程，因此能够同时降低成本和延迟；在训练数据与任务边界足够明确时，专一化还可能提高准确率。

## 从数据到部署的五步流程

### 第一步：准备数据

先建立 300～500 条由领域专家标注的测试集，再准备 1000～10000 条训练样本。数据质量直接决定专用裁判的质量，训练前还要验证不同标注者之间的一致性。

### 第二步：选择模型规模

3B 模型的延迟约为 15～60 毫秒，适合延迟敏感的场景；8B 模型约为 50～150 毫秒，通常可以换取更高准确率。资料强调，基础模型之间的差别不是首要因素，微调质量才是决定性因素。

### 第三步：使用 LoRA 微调

LoRA 只训练约 1%～5% 的权重，资料给出的训练开销是 1～2 个 GPU 小时、50～500 美元。它让团队不必为每个评估指标重新训练并保存一份完整模型。

### 第四步：验证

使用生产样本测量 F1，并把 SLM 与原有裁判的差异控制在 3～5 个百分点以内。正式切换前先运行影子模式，在不影响线上决策的情况下观察判断差异。

### 第五步：部署

使用 INT8 量化提高推理速度，再通过 vLLM 或 TGI 进行批量推理，避免 GPU 长时间空闲。

## 一个基础模型承载多个指标

传统方案为四个评估指标部署四个独立模型，需要四张 GPU 和 64GB 显存。LoRA 方案只保留一个基础模型，并为不同指标加载小型适配器：PII 检测 12MB、毒性检查 15MB、合规检查 18MB、质量评分 10MB，总计 55MB。

请求到来后，系统用约 5 毫秒切换到对应适配器，评估完成后再切换。资料给出的资源变化是从四张 GPU、64GB 显存降到一张 GPU、16GB 显存和 55MB 适配器，显存节省 75%。适配器共享 KV 缓存，请求还可以跨指标批处理。

这套结构让新增评估指标的主要增量从一张 GPU 变成一个约 10～20MB 的适配器文件。

## 蒸馏与量化压缩

资料以 Llama Guard 3 的压缩管线为例：先通过知识蒸馏让 8B 教师模型训练 1B 学生模型，F1 下降 1.3%；再使用 INT4 量化，把权重从 16 位浮点压缩为 4 位整数，继续缩小体积。

最终模型为 440MB，可以在手机上以每秒约 30 个 Token 的速度运行，并在安全分类上保持超过 GPT-4 的结果。资料由此提出，蒸馏和量化可以组合使用：压缩比能够叠加，精度损失不必等比例叠加。

## 什么时候应该切换到 SLM

使用 SLM 裁判需要同时满足三个条件：

1. **日评估量超过 1 万条**：不足这个规模时，自建训练和部署管线的运维成本可能高于节省的 API 费用。
2. **评估标准已经稳定两个月以上**：标准频繁变化时，修改 LLM 裁判 Prompt 只需几秒，重新微调 SLM 却需要数小时。
3. **任务边界明确**：安全、PII 和合规等二元或分类判断适合专用模型。

主观质量评估、从未见过的新型失败模式，以及需要综合多因素上下文的任务，应继续交给 LLM 裁判。

两者可以分层协作：SLM 高效处理已知分布和绝大多数日常流量，LLM 接收 SLM 低置信度结果，负责捕获分布外问题。

## 总结

七句话说完：

1. LLM 裁判在生产规模上受到成本线性增长、延迟壁垒和抽样盲区的限制。
2. Llama Guard 3、Luna、PHUDGE 和 Prometheus 2 分别侧重安全、速度、性价比和开放部署。
3. 专一化把模型容量集中到单一判断，在边界稳定的任务上可能比通用模型更快、更便宜和更准。
4. SLM 裁判按数据准备、模型选择、LoRA 微调、验证和部署五步构建。
5. 一个基础模型配合多个 LoRA 适配器，可以用一张 GPU 承载多个评估指标。
6. 蒸馏与量化可以把 8B 模型压缩到 440MB，资料给出的 F1 损失为 1.3%。
7. 日量过万、标准稳定、任务明确时切换 SLM；否则继续使用 LLM 裁判。
