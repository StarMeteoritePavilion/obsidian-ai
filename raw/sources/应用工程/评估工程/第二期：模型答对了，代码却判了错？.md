> 评估工程系列 第二期

上一期建立了评估工程的整体框架，这一期直接进入代码评分实操。模型明明答对了，评分脚本却可能因为它多说了几个字，或者分类标签顺序相反而判零分。

代码评分是三种评分方式中最快、最便宜、最容易复现的一种，但尺子选错了比没有尺子更糟糕。它的核心是用 Python 编写确定性逻辑，自动比较模型输出与正确答案，不需要人工逐条检查，也不需要额外调用一个 LLM 当裁判。

## 两种武器与六步闭环

代码评分有两种主要方式：

- **精确字符串匹配**：像机器阅卷，输出必须与黄金答案完全一致，多一个空格、句号或解释都可能判错。
- **集合匹配**：像按要点批改，只要标签集合一致，排列顺序、大小写和多余空格都不影响结果。

选择哪种方式，取决于答案的结构，而不是哪种实现更严格。

一次代码评估可以组成六步闭环：

1. 建立带黄金答案的数据集。
2. 编写 Prompt。
3. 运行模型。
4. 用评分函数比较输出与答案。
5. 汇总分数并查看失败案例。
6. 根据失败原因修改 Prompt，再回到前面的步骤。

本期用两个案例演示这套闭环：动物腿数从 66.6% 提升到 100%，客户投诉分类从 85% 提升到 100%。前者使用精确匹配，后者使用集合匹配。

## 精确匹配：快，但非常脆弱

精确匹配只问一个问题：模型输出是否等于黄金答案？相等就得分，不相等就判零分。

它速度极快，不需要额外模型调用，并且相同输入和逻辑会产生一致结果；前提是任务存在明确的标准答案。它的缺点也来自同一性质：模型输出 `The answer is 6`，黄金答案是 `6`，语义虽然正确，字符串却不相等。

因此，精确匹配能够成立的前提是 Prompt 必须严格约束输出格式。

## 案例一：三版 Prompt 数动物腿

第一个案例让 Claude 计算动物有几条腿。数据集共 12 条，从普通动物到包含断腿、长回和额外腿等条件的组合题。

### 第一版：只要求用数字回答

第一版 Prompt 只要求模型回答动物腿数并使用数字。最终 12 题错了 4 题，正确率为 66.6%。错误分成两类：

- **格式错误**：模型给出了包含解释的完整句子，答案本身正确，但精确匹配不接受额外文字。
- **逻辑错误**：狐狸题正确答案是 5，模型回答 6；蜘蛛题正确答案是 10，模型回答 8；章鱼题正确答案是 9，模型回答 5。

这一步说明，评分失败和任务失败不是一回事。前者来自输出契约不一致，后者才是模型推理错误。

### 第二版：只输出一个数字

第二版增加明确约束：`Respond only with a numeric digit`，只允许输出一个数字，不得添加其他内容。

格式问题随之消失，但蜘蛛和章鱼等逻辑错误仍然存在。格式对了，不代表模型已经算对。

### 第三版：先推理，再提取答案

第三版引入思维链，让模型先在 `<thinking>` 标签中分步推理，再把最终数字放入 `<answer>` 标签。

狐狸题中，模型依次计算原有四条腿、断掉一条、重新长回，再增加一条，最终得到 5。章鱼题中，模型按 `8 - 2 + 3` 得到 9。分步过程暴露了之前凭直觉作答导致的错误，正确率最终达到 100%。

评分脚本再通过正则表达式从 `<answer>` 中提取数字，执行精确匹配。三版 Prompt 的变化分别解决了输出格式、推理过程和机器提取问题，每一步的效果都能由同一数据集验证。

## XML 标签让输出对机器友好

没有结构标签时，推理过程和最终答案混在一段自然语言里，评分脚本只能使用复杂且脆弱的解析逻辑。

加入 `<thinking>` 和 `<answer>` 后，推理与答案拥有明确边界：人可以检查推理，程序可以直接提取最终答案。工程化的目标不是只让输出对人友好，还要让它能够被机器稳定消费。

这一结构还会用于后续的 Agent 评估和生产护栏：生成过程可以保持丰富，进入评分和控制系统的结果则必须具有清晰接口。

## 集合匹配：忽略无意义的排列差异

精确匹配不适合多标签分类。模型输出“硬件故障、软件 Bug”，黄金答案是“软件 Bug、硬件故障”，两者包含相同标签，却会因为顺序不同而判错。

集合匹配先使用 `lower` 统一标签大小写、使用 `strip` 清理多余空格，再把模型输出和黄金答案分别转换为 Python `set`，最后比较两个集合是否相等。

这样处理后：

- 标签顺序不影响结果。
- 大小写不影响结果。
- 标签周围的多余空格不影响结果。

集合匹配把评分单位从逐字逐句提升为分类要点，适合答案由多个无序标签组成的任务。

## 案例二：客户投诉分类

第二个案例包含 20 条客户投诉和五类标签：软件 Bug、硬件故障、用户错误、功能请求和服务中断。

其中存在多标签输入。例如“程序崩溃，而且手机发热”同时属于软件 Bug 和硬件故障；“服务全断了，我还急需批量处理功能”同时属于服务中断和功能请求。

初版 Prompt 只有一句分类指令和类别列表，经常只输出一个标签、漏掉第二个，集合匹配后的正确率为 85%。

改进版做了两件事：

1. 为每个类别补充清晰定义，明确软件问题与物理设备问题等语义边界。
2. 加入九个输入输出 few-shot 示例，覆盖全部类别和常见的多标签组合。

修改后，20 条数据的正确率达到 100%。不过样本量太小，这个结果不能证明生产环境也能达到 100%；数据集仍需扩展到上一期提出的至少 100 条。

## 总结

七句话说完：

1. 代码评分使用确定性逻辑自动判卷，是三种评分方式中最快、最便宜和最容易复现的一种。
2. 精确匹配要求 Prompt 严格限定输出格式，否则语义正确也可能因为一个空格而判错。
3. 动物腿数案例通过格式约束、分步推理和结构化答案，把正确率从 66.6% 提升到 100%。
4. XML 标签把推理与最终答案分离，使评分脚本能够稳定提取结果。
5. 集合匹配通过 `set`、`lower` 和 `strip` 消除标签顺序、大小写和空格造成的误判。
6. 分类 Prompt 的两项核心改进是明确类别定义和加入 few-shot 示例。
7. 小数据集上的 100% 不代表生产级效果，仍需用更大、更真实的数据验证。
