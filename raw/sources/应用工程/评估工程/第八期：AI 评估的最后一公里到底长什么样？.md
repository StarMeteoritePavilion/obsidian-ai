> 评估工程系列 第八期（完结篇）

前七期建立了从代码评分到生产护栏的完整体系，但企业环境还会提出更严格的问题：当系统面对合规审计、法务审查和多模型切换时，关键行为还能依赖 Prompt 中的自然语言规则多久？

Joongho Ahn 与 Moonsoo Kim 的研究用消融实验展示了 Prompt 主导系统的边界。即使把完整规则写入 Prompt，模型仍在 30 次运行中出现 30 次违规。企业级 AI 因此需要把关键行为从 Prompt 迁移到代码拥有、可审计、可追溯的合同驱动架构。

## 从 Prompt 主导迁移到合同驱动

Prompt 主导依赖自然语言告诉模型“不要做某件事”，本质上仍然寄希望于模型遵守指令。规则难以审计、迁移和验证，模型升级后行为也可能改变。

合同驱动则由代码决定什么事实可以断言、什么信息可以暴露、什么表述可以到达用户。LLM 只负责把已经验证的事实转化为人类可读的语言。确定性控制归代码所有，因此能够审计、跨模型迁移并验证执行结果。

企业级评估工程由五层组成：

1. **源门 Source Gate**：把原始文档注册为结构化 Manifest，由代码决定哪些来源有资格进入系统。
2. **证据层 Evidence**：提取文本，记录文件哈希、文本哈希和页码或行号等证据位置。
3. **提升门 Promotion Gate**：只有经过代码提升的候选声明，才能成为运行时可断言的 Source-Backed Claim。
4. **组合边界 Composition Boundary**：把代码拥有的确定性控制与 LLM 的语言组合分开，并提供可替换接口。
5. **输出卫生 Output Hygiene**：在答案到达用户前检查泄漏、链接和语言合规。

## 从调试工具到治理系统

Eval Engineering 把评估从一次性调试工具升级为持续运行的治理系统。传统评估通常在部署前抽样运行，依赖静态测试集，容易被视为成本中心；评估工程在生产中持续运行，覆盖真实流量并随新边缘案例调整，因此成为战略资产。

资料给出的生命周期形成闭环：监控生产流量并发现边缘案例，创建 LLM 裁判，引入领域专家标注并精炼标准，在开发流量上评分和调参，再微调 SLM 替代 LLM。资料称最后一步可以节省 97% 的成本，完成后重新回到生产监控。任何阶段都不能跳过；缺少 SME 精炼就直接部署生产护栏，会把平庸判断固化并放大到生产规模。

ADLC，即 Agent Development Lifecycle，把评估置于 Agent 开发全生命周期的核心。AI 没有评估，只是昂贵的许愿。

## Prompt 不是护栏

消融实验比较了三种条件：

- **Prompt-only**：完整规则写入 Prompt，但 30 次运行全部违规，其中 15 次出现推荐式违规表述，15 次泄露内部 ID。
- **External Guard**：违规降为零，但错误拦截了 32 个正确回答，效用从 120/120 降至 88/120。
- **Harness**：代码拥有验证门并提供确定性回退，同时保持零违规和 120/120 的完整效用。

McNemar's test 得到 `p < 0.001`，资料据此将 Prompt-only 的失败解释为系统性问题，而不是偶然波动。外接通用护栏虽然能够阻止违规，却因过度拒绝损失业务效用；只有应用专属、代码拥有的执行层同时保留安全与效用。Prompt 不是护栏，代码层才是负载轴承。

## 从来源到可断言事实

Source-to-Claim Pipeline 解决的是一句模型输出究竟来自哪个文档、哪个位置的问题。管道分为三步：

1. **Manifest Registration**：原始文档先注册为结构化 Manifest，记录来源资格和适用范围，防止知识库退化成无边界的文件夹。
2. **Evidence Recording**：提取文本，保存文件哈希、文本哈希以及页码或行号等证据位置。
3. **Promotion Gate**：候选声明只有经代码提升，才能成为运行时可用的 Source-Backed Claim。

每条声明保持原子化，并绑定来源 Manifest、证据记录、实体作用域和使用策略。LLM 可以使用这些声明组织语言，但不得断言任何没有通过提升门的内容。该结构把“检索到文本”进一步收紧为“代码批准某条有来源的声明可以用于当前回答”。

## 可替换的组合边界

Composition Boundary 把系统分为两半。代码侧负责来源资格、实体路由、声明选择、答案规划、章节结构以及输出合同验证；LLM 侧只负责对结构化声明包进行语言组合，并生成跟进问题。

边界提供两种模式：

- **确定性组合器**：不使用生成模型，以纯模板填充提供可复现基线。
- **Live LLM**：把声明包交给托管模型，但输出必须通过同一套合同验证；不可用时回退到确定性模式。

在 Claude Sonnet 4、GPT-4.1 mini 和 Gemini 2.5 Flash 三个模型上的 270 次运行中，代码检查全部通过。模型差异只出现在语言组合侧，因此可以替换模型而不改变代码层保障。

## 企业数据上的实证结果

研究使用三星、SK、现代汽车、LG 和韩华五个韩国企业集团下 25 家上市公司的公开数据。来源包括韩国金融监督院 OpenDART 申报文件、IR 材料、市场数据和新闻，并形成 113 条有来源支持的运行时声明。

三个研究问题得到以下结果：

- **RQ1 合同保持**：合同保持率为 100%；30 个固定场景产生的 60 次输出全部通过输出卫生检查。
- **RQ2 模型替换**：三个模型共运行 270 次，代码检查 270/270 通过；首次输出有效 234/270，来源声明引用正确 252/270，答案结构正确 250/270。模型组合仍可能失败，但失败被同一合同边界捕获和记录。
- **RQ3 消融验证**：7/7 个故障破坏实验均被检出；Prompt-only 条件下 30/30 次违规，外部护栏效用为 88/120，Harness 保持零违规和 120/120 效用。

通过缓存和预热，完整链路延迟从 1648 毫秒降至 69 毫秒，答案质量保持不变。这些数字来自该研究的固定企业数据、场景、模型和实现，不能直接外推为所有系统的性能保证。

## 输出卫生的三族检查

输出卫生是答案到达用户前的最后一道验证门：

1. **泄漏检查**：拦截内部 ID、原始 Trace、API 诊断标签和状态标签。
2. **链接检查**：验证每个引用源可以解析，跟进问题能够面向用户呈现。
3. **语言检查**：强制答案包含规定的章节结构，禁止未经授权的推荐式措辞。

泄漏检查和语言检查在参考实现的 60 次输出中全部通过，链接则在调用时动态校验。在企业合规环境中，一条未经授权的买入建议或一次内部 ID 泄漏，可能比平均答案质量更重要。LLM 可以自由措辞，但措辞边界必须由代码强制执行。

## 从测试用例走向合同治理

八期内容形成三层结构：底层使用代码评分处理有标准答案的确定性任务；中间层使用 LLM 裁判处理主观任务，并在规模化后以 SLM 降低成本；顶层使用合同驱动架构，把关键行为写入代码拥有、可审计、可追溯的工程制品。

资料给出的五步行动路线是：

1. **今天**：从至少 20 个测试用例开始。
2. **本周**：创建 LLM 裁判。
3. **本月**：加入 SME 精炼。
4. **本季度**：部署生产护栏。
5. **今年**：用合同驱动架构治理 AI 产品。

## 总结

本期用七条核心认知收束整个系列：

1. Eval Engineering 把评估从一次性调试工具升级为持续治理系统。
2. Prompt 不是护栏；Prompt-only 的 30 次运行全部违规，代码拥有的执行层才是负载轴承。
3. Source-to-Claim Pipeline 通过来源注册、证据记录和提升门，决定什么可以断言为事实。
4. Composition Boundary 把代码侧确定性控制与 LLM 侧语言组合分开，支持模型替换。
5. Output Hygiene 以泄漏、链接和语言三族检查构成企业合规的最后防线。
6. 评估工程生命周期从生产监控走向 LLM 裁判、SME 精炼和 SLM 微调，各阶段不可跳过。
7. 落地从测试用例开始，经裁判、专家精炼和生产护栏，最终进入合同驱动治理。

评估工程系列至此完结。赢家不靠调用哪个模型来区分，靠的是怎样知道系统确实在工作。
