> 评估工程系列 第三期

代码评分速度快、成本低，却只能处理存在标准答案的任务。客服回复是否礼貌、摘要质量是否足够好等主观问题没有唯一答案，无法只依靠精确匹配或集合匹配解决。

LLM 裁判让能力更强的模型依据评估标准判断另一个模型的输出。它能够扩展语义评估的规模，但不能未经配置直接使用：通用裁判存在领域知识不足和系统性偏见，单个裁判还会受到高方差与调用成本的限制。

## 从输入到校准的四层结构

生产级 LLM 裁判由四层组成：

1. **输入**：打包待评输出、评估标准和 few-shot 示例。
2. **单裁判**：先通过定制 Prompt 把通用裁判的准确率从 64%～68% 提升到 75%～80% 以上。
3. **多裁判面板**：混合不同模型并进行多数投票，以降低方差。
4. **校准**：用人工黄金集交叉验证，资料以 Cohen's Kappa 大于 0.6 作为可进入生产使用的门槛。

资料用一句话概括其中的分工：从六成到八成主要依靠工程技巧，从八成继续向九成五推进则需要领域专家。工程可以把标准、上下文和示例组织清楚，但无法代替真正理解业务的人定义什么叫“好”。

## LLM 裁判能够工作的原因

资料给出三个原因。

第一，模型在训练过程中已经见过大量人类判断，对好文章、好摘要和好客服回复形成了通用直觉。资料援引 MT-Bench 的结果，称强 LLM 裁判与人类评估者的一致性达到 80% 以上，接近人类评估者之间的一致性。

第二，模型可以持续、批量执行相同的评分任务，不会因疲劳或情绪在评完数百条数据后随意改变标准。

第三，裁判会随基座模型升级而增强。当前使用 GPT-4 搭建的裁判，之后可以替换为更强的模型，无需像传统机器学习分类器那样重新训练整套评估器。

这些优势解释了 AI 评价 AI 的可行性，但不能证明任意裁判都可信。真正决定效果的是领域标准、偏见治理和人类校准。

## 通用裁判准确率停留在六成左右的原因

资料转述 UC Berkeley 的量化研究，将通用裁判的准确率天花板放在 64%～68%。问题并非模型完全没有判断能力，而是“好”在不同领域中的含义不同：

- 法律文档审查关注判例引用、风险标注和免责声明。
- 客服场景关注是否承认用户情绪、给出下一步操作，以及是否越权承诺。
- 代码助手关注代码能否运行、是否处理边界情况，以及是否符合风格指南。

如果只问“这个回答好不好”，裁判只能依靠通用语感判断。缺少领域上下文和可执行标准时，即使模型能力很强，也无法稳定对齐业务判断。

## 从 60% 到 80% 的四个改进

### 给裁判明确身份

不能只向通用模型提出评分请求，还要明确说明它当前承担的角色，例如“你是金融合规评审专家”。身份为后续标准提供领域视角。

### 把通过标准写清楚

不能使用“看看好不好”之类的模糊要求。应编号列出具体标准，并说明每一条在何种条件下通过、何种条件下不通过。

### 提供正反示例

至少给出三个 few-shot 示例，同时包含通过和失败案例。每个示例附上判断过程，使裁判了解领域专家如何应用标准，而非只看到最终标签。

### 先推理，再下结论

要求裁判先分析证据，再输出 `PASS` 或 `FAIL`，避免凭直觉立即作答。资料将角色、标准、示例和 CoT 推理组合后，把准确率区间从约 60% 提升到 75%～80%。继续提高则需要领域专家进一步修订标准和案例。

## 五种系统性偏见

LLM 裁判的错误并非完全随机。资料列出五种会系统性扭曲结果的偏见：

1. **位置偏见**：裁判偏好排在前面或后面的选项。成对比较时交换两次位置，只有结论一致才采信。
2. **冗长偏见**：裁判容易把更长的回答视为更好。标准应明确“分点论证优于大段叙述”，而不是字数越多越好。
3. **自偏好**：GPT 作为裁判时可能偏向 GPT 生成的答案。评估某个模型的输出时，使用其他模型进行跨模型裁判。
4. **近因偏见**：越晚出现的项目越容易占优。通过随机打乱评估顺序降低影响。
5. **格式偏见**：Markdown 标题、表格或 emoji 等形式可能获得额外偏好。评分标准必须明确格式不影响分数。

偏见治理不是一次性消除模型缺陷，而是把可预测的扭曲转成可检测、可缓解的评估条件。

## 多裁判共识

单裁判有三项根本限制：容易偏向同类模型，Prompt 措辞略有变化就可能导致结果大幅波动，并且规模化调用持续产生费用。

解决办法是组织三至五个不同模型组成裁判面板。以 GPT、Claude 和 Gemini 三个裁判为例，让它们独立评分，再根据任务类型聚合结果：

- 二元 `PASS`/`FAIL` 使用多数投票；三比零说明一致性较高，二比一表示样例仍有争议。
- 更重视召回、宁可误判也不愿漏判时使用最大池化，任一裁判给出 `PASS` 即算通过。
- 一至五分等序数评分使用均值。

混合模型可以降低单一模型自偏好的影响，多数投票可以降低方差。一个裁判的判断只是意见，多个独立裁判形成的稳定共识才能作为更强的证据。

## 裁判配置的三个维度

### 模型

大多数场景使用 GPT-4o、Claude Sonnet 等非推理模型，并加入 CoT 提示即可。只有当评估需要权衡多个因素和边界情况时，才使用 o1 或 Claude Extended Thinking 等推理模型。经验规则是：标准能用一句话说清，就不需要推理模型。

### 输出类型

Boolean 类型的 `PASS`/`FAIL` 几乎总是最佳起点。只有任务确实需要表达中间状态时，才使用分类或一至五分的离散评分。想要更细粒度，往往意味着标准仍不够清晰。

### 评估范围

评估范围可以从整个多轮对话的 Session，逐步缩小到单次请求—响应对的 Trace，再下沉到单个 LLM 调用的 Span。资料推荐先使用 Trace 级评估；需要诊断复杂工作流中的具体故障环节时，再检查 Span。

综合三个维度，资料推荐的高性价比配置是：Boolean 输出、非推理模型、CoT 提示和 Trace 级范围。

## 信任裁判的条件

资料提出三道门槛。

第一，评估标准必须能够清楚写成文字。主观但可定义的任务适合 LLM 裁判；需要精确计算或规则匹配的任务应退回代码评分。

第二，裁判必须与人类专家的黄金判断进行校准。资料给出的 Cohen's Kappa 解读是：低于 0.4 不可用，0.4～0.6 可以接受但仍需优化，大于 0.6 才达到生产级可信范围。

第三，涉及安全、合规或高风险决策时，即使 Kappa 达到 0.8，也必须保留人工终审。资料同时指出，人类评估者之间的一致性通常只有 0.2～0.3，因此 LLM 裁判达到 0.4～0.6 已经能够超过许多普通标注员；但这不取消高风险场景中的人类责任。

## 总结

本期内容可以归纳为七点：

1. LLM 裁判的本质是用 AI 评价 AI，利用模型已经内化的人类判断进行语义评分。
2. 通用裁判不能未经配置直接使用，资料给出的准确率上限为 64%～68%，根因是不同领域对“好”的定义不同。
3. 通过角色定义、明确标准、正反示例和先推理再判断，可以把准确率提升到约 75%～80%。
4. 位置、冗长、自偏好、近因和格式五种偏见必须治理，否则评估结果会被系统性扭曲。
5. 三至五个混合模型组成的多裁判面板与多数投票，是资料提出的生产级底线。
6. Boolean 输出、非推理模型、CoT 提示和 Trace 级范围，是资料推荐的高性价比配置。
7. Cohen's Kappa 大于 0.6 才进入生产级可信范围，高风险场景永远保留人工终审。
