> 循环工程系列 第一期

2026 年 6 月第一周，Peter Steinberger、Boris Cherny 和 Addy Osmani 几乎同时把注意力指向同一种变化：人不再逐轮 Prompt Agent，而是开始设计能够替人 Prompt Agent 的循环。

这就是 Loop Engineering，也就是循环工程。它的核心不是让 Agent 多运行几次，而是把原本由人承担的触发、分工、反馈和推进机制交给系统。人的位置由循环内部移到循环外部，从操作 Agent 的人转变为设计和调度 Agent 的人。

## Prompt、Context 与 Loop 的三层递进

三层工程分别管理不同尺度的问题：

1. **Prompt Engineering 管一句话**：斟酌措辞、提供示例、设定角色，把一次任务表达清楚。
2. **Context Engineering 管一个窗口**：决定检索什么、摘要到什么程度、保留什么以及清除什么。窗口有限时，放入错误信息往往比少放信息更危险。
3. **Loop Engineering 管持续运行**：让 Agent 在一次执行结束后自行触发下一轮、分配工作、验证结果、保存状态并决定下一步。

前两层完成后，得到的是一次能够良好运行、但结束后仍需等待人继续推动的 Agent。Loop Engineering 自动化的正是“等人敲下一拍”这件事。

## Harness 不是第四层，而是三层共同的外壳

一种常见画法把 Prompt、Context、Harness 和 Loop 排成四层，仿佛 Harness 只是介于单次运行和循环之间的一层。本期资料明确反对这种窄化。

Harness 是模型外部的整体工程框架。工具怎样接入、权限怎样控制、安全怎样保证、失败后怎样恢复，这些问题同时横切 Prompt、Context 和 Loop。更准确的结构是：

- 最内层 Prompt 管递给模型的一段话。
- 中间层 Context 管窗口里装什么。
- 最外层 Loop 管系统怎样反复运行。
- Harness 包住三层，为它们提供工具、权限、安全和恢复机制。

因此，把 Harness 降为四层结构中的第三层，相当于把整栋楼的框架说成其中一个房间。

## 循环比上下文多出的三个动作

### 在定时器上自行唤醒

上下文工程管理一次运行时模型看到什么，但这次运行仍需由人触发。循环具有自己的节奏：到点醒来、开始工作，而不是等待人按下按钮。

### 孵化小帮手并组织协作

循环可以把工作分给多个子 Agent，例如一个起草和修改，另一个专门审查。上下文工程关心单个 Agent 的窗口怎样配置；循环工程还要关心一组 Agent 怎样分工、协作和相互监督。

### 把结果送回下一轮

循环会把本轮发现的问题、完成的工作和后续状态写入持久载体。下一次运行先读取这些状态，再从上次停止的位置继续。跨越单次对话的外部记忆让各轮执行真正连接起来。

缺少自行唤醒和结果接力，系统只是由人手动运行了很多次，还不能构成自主循环。

## 层次越高，失败越晚暴露

区分三层并非只是术语需要，因为它们的失败方式不同：

- Prompt 出错通常能在当次输出中看到，修改指令即可重试。
- Context 出错会让模型基于错误或无关信息回答，但人仍可能在当前交互中发现偏离。
- Loop 出错时，系统可能在人不在场时持续运行、修改未经审阅的代码，并把错误状态送入下一轮。

工程层次越高，人离执行现场越远，错误被发现得越晚，累积时间和影响范围也越大。循环工程真正困难的部分不是让循环转起来，而是设置能够拦住错误的验证、停止与恢复机制。

## 循环是放大器

两个人可以搭建相同的循环，却得到相反的结果。一个人用循环加速自己已经理解透彻的工作，另一个人用循环逃避理解。

循环无法替人判断两者的差别。它只会放大被带入系统的东西：带入理解，就放大理解；带入偷懒，就放大偷懒。因此，循环设计不能以人退出工程判断为目标。人应当离开逐轮执行的位置，但仍需负责目标、约束、验证和后果。

## 总结

五句话说完：

1. Loop Engineering 把逐轮 Prompt Agent 的人替换为一套能够持续推进任务的系统。
2. Prompt 管一句话，Context 管一个窗口，Loop 管系统自行运行。
3. Harness 不是第四层，而是包住三层并横切工具、权限、安全和恢复的工程外壳。
4. 循环通过定时触发、子 Agent 协作和结果回写形成跨轮次接力。
5. 层次越高，失败越晚暴露；循环会放大人的理解，也会放大人的逃避。
