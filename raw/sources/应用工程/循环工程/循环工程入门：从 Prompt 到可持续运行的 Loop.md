# 循环工程入门：从 Prompt 到可持续运行的 Loop

## Loop 定义

2026年AI工程的一个显著变化是：人不再逐轮 Prompt Agent，而是开始设计能够自行生成 Prompt、自行执行并自行停止检查的循环。原视频作者（晴天AI实战）指出，“从 Prompt 转向 Loop”以及将此领域称为“Loop Engineering（循环工程）”是当前的一个重要工程趋势判断，它并非对已有概念的重新命名，而是标志着一种工作模式的根本转变[1]。

循环工程的核心不在于让 Agent 盲目地多运行几次，而是把原本由人承担的触发、分工、反馈和推进机制交给系统，实现跨轮状态接力和自主运作。

## 人的位置迁移

过去，人位于循环内部，逐句编写 Prompt，充当循环中的“人工时钟”：Agent 完成一轮后便停止，等待人的触发、判断和推进。

循环工程将人从循环内部移到了循环外部。系统的目标是自行决定下一步任务、自行完成分工执行、反馈结果并判断是否继续。人的职责从“操作 Agent 的人”转变为“设计和调度 Agent 的人”，重点在于设计整个循环的目标、边界、反馈方式和停止条件[2]。

## Prompt、Context、Loop 与 Harness 外壳

在原视频课程提供的概念框架中，工程体系被划分为三层递进的结构，外加一个共同的工程外壳（注：本篇采用第一期视频对先导篇的修正口径，不再将其列为平行的四层）：

- **最内层 Prompt（提示词工程）**：管“一句话”。负责斟酌措辞、提供示例、设定角色，把单次任务表达清楚。
- **中间层 Context（上下文工程）**：管“一个窗口”。决定检索什么信息、如何摘要、保留或清除什么历史。工程实践表明，当窗口空间有限时，放入错误的信息往往比少放信息更危险。
- **最外层 Loop（循环工程）**：管“持续运行”。负责在一次执行结束后自行触发下一轮、分配工作、验证结果并决定下一步。

**Harness** 并不是第四层，而是包住这三层的横切外壳。它为 Prompt、Context 和 Loop 提供工具库、执行环境、权限控制、安全边界以及失败后的恢复机制。这四者构成本系列教程的基础架构模型，而非行业的官方或统一分类[2]。

## 唤醒、子 Agent、状态回写

一个真正的“自主循环”不仅是简单地将代码重复运行，它必须具备以下三个新增动作（这也是实现跨轮次接力的必要条件）：

1. **在定时器上自行唤醒**：循环具有自己的节奏，能够在特定时间或事件下自动醒来开始工作，而不是等待人工按下按钮。
2. **创建子 Agent 并组织协作**：循环能够把工作分配给多个特定的子 Agent（例如起草者与审查者）。循环工程不仅要配置单个窗口，还要管理一组 Agent 如何分工和相互监督。
3. **把结果送回下一轮**：在单次运行结束时，系统将发现的问题和最新状态写入持久化的载体。下一次运行先读取这些状态再继续。

要实现以上动作，开发者必须回答三个关键的设计问题：**循环状态存在哪里？谁决定继续？谁有权停止？**
这就构成了一个最小循环示意路径：`触发 → 任务（分发） → 执行 → 验证 → 状态（回写） → 停止`[1][2]。

## 验证、停止、回退和成本

循环本质上是一台放大器：如果输入的是对任务的透彻理解，循环会放大这种理解；如果输入的是对理解的逃避，循环也会放大这种逃避。

更重要的工程判断是：工程层次越高，失败暴露得越晚。Prompt 错误会在当前输出中立刻显现，Context 错误可能在单次交互中被人类察觉；而 Loop 错误可能在人类不在场时持续运行，修改未经审阅的系统代码，并把错误状态送入下一轮。因此，循环能力越强、权限越大，以下四类边界的设计就越重要：

- **验证机制**：怎样确认每轮执行结果是可靠的，可以安全进入下一轮。
- **停止条件**：什么时候任务已经达成，或者在什么异常情况下必须中止。
- **回退机制**：当发现错误状态或发生破坏时，怎样恢复到可信的初始状态。
- **成本边界**：怎样防止 Token 消耗与计算资源在循环中失控。

循环工程并不意味着人可以放弃工程责任，而是要求人将精力集中在设定这些约束与后果管理上[1][2]。
