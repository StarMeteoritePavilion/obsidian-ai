# Loop 的组件、搭建方法与上线检查

一个持续运行的Agent流程要能发现工作、隔离修改、验证结果、保存状态并安排下一次执行。组件是否齐全只是起点；能否上线还取决于停止条件、预算、权限和人工复核。本篇把原课程两篇合为同一条设计路径，工具说明以2026-09-07实际读取的文档为准。

## Context与Loop怎样共用基础设施

Context关注一次调用可见的信息，Loop关注跨轮工作的触发、状态与停止。Skill既能按需提供项目知识，也能避免每轮重复交代稳定规则；子Agent既能隔离上下文，也能独立检查另一Agent的交付；持久文件既能补充当前信息，也能记录下一轮的待办。

原课程把Prompt、Context、Loop放在Harness的横切控制内，这是课程采用的概念模型。Addy Osmani在2026-06-08文章中把Loop说成“位于Harness上一层”，两种图示的划分口径不同，不能冒充统一的厂商架构。共同问题是：一次执行怎样变为有反馈、有状态的持续流程。[^组成]

## 五个动作与六个组件

Addy的原文列出五类组件再加持久记忆，并给出每日仓库分诊的设计形态。下面沿用课程的五动作映射，增加输入、产出和停点作为本文设计建议。[^组成]

| 动作 | 输入 | 组件与产出 | 停止或转人工条件 |
| --- | --- | --- | --- |
| 发现 | CI失败、Issue、Commit及已处理状态 | Skill整理规则；调度器触发；形成有来源的工作项 | 没有新工作就结束本轮；来源不可访问时记错，不臆造任务 |
| 交付 | 明确范围、规格、当前代码 | 子Agent在隔离Worktree中形成改动 | 越界修改、依赖冲突或任务未获授权时停止该项 |
| 验证 | 改动、规格、测试与行为标准 | 独立Checker给出通过／失败及证据 | 测试或行为不符就返修；没有有效验证不能发出完成信号 |
| 持久化 | 验证结果、最终产物、剩余问题 | Memory保存状态；Connector连接PR或工单 | 写入失败不能标交付成功；外发需要已有授权 |
| 调度 | 下次触发条件、运行预算 | Automation安排后续检查 | 目标完成、预算耗尽或明确停止后不再触发 |

六类组件是Automation、Worktree、Skill、Connector、Sub-agent和Memory。它们表达职责，不意味着必须安装六个独立产品：顺序、单任务流程未必需要并行Worktree，但仍要说明工作区所有权；没有跨系统交付时也不必为了凑数引入Connector。

## Maker与Checker分离

独立Checker使用不同上下文和明确验收条件，降低生成者只检查自己意图的风险。第二个模型也会出错，因此检查目标应落在证据上：

- 测试结果：执行了什么命令、哪些用例通过、退出状态是什么。
- 页面行为：实际点击后的状态、截图、控制台错误，而不只是代码看起来合理。
- 状态差异：文件、数据或外部系统是否达到预期，是否出现越界修改。

Addy的实践文强调，判断停止的模型不等于独立内容审查者。当前Claude Code官方/goal文档也说明，评估器只读取对话中已经出现的证据，**不会自行运行命令或读取文件**。因此“/goal显示达成”不能替代实际测试和独立审查。[^目标][^实践]

## 五步搭建一个有边界的循环

1. **先定义一次有终点的工作**：写明成功条件、允许目录、最大成本或轮数，以及失败后交给谁。先验证一次执行，再添加定时触发。
2. **接入发现源**：读取指定CI、Issue或Commit，把发现与来源绑定；保存已处理标识，防止下一轮重复提交同一改动。
3. **增加持久状态**：保存任务、尝试、验证结果和未完成项。不能只靠对话记忆，也不能把“已尝试”当“已完成”。
4. **安装验证与回退**：独立检查生成结果，明确失败停止条件；先确认可撤销动作和不可撤销动作分别如何授权。
5. **按需加入并行隔离**：只有独立任务才分发Worktree；合并前检查冲突和集成测试。隔离目录不能隔离共享数据库、账号和远端服务的副作用。

这些步骤是本文整合后的方法，不是运行过的完整自动化教程；本次未创建调度任务或向外部系统发布内容。

## 平台侧栏：/loop与/goal的生命周期

以下来自2026-09-07读取的Claude Code官方文档，代表当时文档行为，不保证原视频发布时已有全部能力。[^定时][^目标]

| 写法或能力 | 文档行为与限制 |
| --- | --- |
| `/loop 5m check the deploy` | 按固定间隔重复提示；秒数向上取整到分钟，不能认为任意秒级精准调度 |
| `/loop check the deploy` | 每轮动态选择间隔；文档列出特定第三方平台／关闭特性拉取场景需要v2.1.248及以上的差异 |
| `/loop` | 使用默认维护提示；存在`.claude/loop.md`时优先用项目文件，否则查看`~/.claude/loop.md`，都不存在才使用内置提示 |
| Session定时任务 | 需要本机及会话运行；周期任务创建7天后过期；新对话清除，会话恢复可恢复未过期任务 |
| Cloud Routines | 可独立于本机会话运行；新鲜克隆不等于拥有本机未提交文件和本地工具 |
| `/goal` | 每轮后由另一个模型检查条件；不自动改变权限模式，也不自行执行验收工具 |

课程提及Codex的Automations与Worktree，本文仅保留为原作者的产品对照，不提供未核对版本的Codex命令。实际配置应读取所用产品的当前官方文档。

## Ralph与Backpressure

Geoffrey Huntley在2026-01-17的原文把Ralph描述为：一个仓库中的单进程每轮处理一个任务，通过规格和反馈推动下一轮。他同时强调可以手动推动或设置暂停，模式并不限于完全无人值守。[^循环]

课程概括的单任务、主线程调度、每轮重载规格与计划，可以作为职责设计参考，但不把它们写成Huntley逐字制定的统一“三原则”。不用一段无限Bash循环作为可复制的生产方案：它缺少预算和停止策略，具体命令也必须来自当前安装版本。

Backpressure指把质量反馈送回生成过程，让失败阻止继续推进。Huntley的公开文章支持这种反馈思想；课程把它整理成三类检查：测试、类型系统、静态分析。这是课程的教学拆分，不是已经核实的固定三层产品接口。[^反馈]

| 检查 | 如何形成反馈 | 边界 |
| --- | --- | --- |
| 测试 | 行为不符合断言时拒绝交付，报告具体失败 | 测试集不完整仍会漏错 |
| 类型系统 | 编译或类型约束失败时阻止进入下一步 | 类型正确不等于业务正确 |
| 静态分析 | 检出规则、语义或安全问题并定位 | 规则未覆盖的路径仍需动态验证 |

原课程把Ralph限定为绿地项目，但Huntley的2026-01-17文章明确把模式扩展为各种任务；不能把“只适合绿地”当作恒定事实。实际选择要看历史复杂度、验证能力、回滚和人工监督。原稿的297美元／5万美元和CURSED具体案例本轮未取得原始运行记录，不作为工程收益证据；不把它换写成可推广回报率。

## 六项上线检查

下面是本文建议的验收问题，不是厂商强制政策。任一关键答案不明确时，该流程尚不具备对应的无人值守条件。

| 检查项 | 可验证的问题 |
| --- | --- |
| 发现源 | 给定一条已处理事件，下一轮会不会重复执行？来源失败怎样记录？ |
| 状态 | 杀掉并恢复运行后，能否从已验证状态继续，而非跳过未完成步骤？ |
| 评判 | Checker依据哪些实际证据拒绝错误交付？停止评估器会不会只读自述？ |
| 隔离 | 两个任务是否共享文件、数据库或外部账号？最终合并怎样验证？ |
| 预算 | 轮数、Token、运行时间和重试各由谁限制？达到上限后是否真的停止？ |
| 人工复核 | 哪些不可逆操作必须确认？何时通知人接管，通知失败怎么办？ |

循环运行得久不代表质量会自动提高。验收标准、可信证据、跨轮状态和停止权共同决定它是否能持续工作。
