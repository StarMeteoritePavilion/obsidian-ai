> 循环工程系列 第三期

上一期得到一个结论：循环越强，验证债、理解腐烂、认知投降和 Token 失控四笔代价越重。

本期不再讨论流派，而是拆解循环，分析五个动作、六个组件和一个能够说“不”的独立评判器，并说明 Ralph 如何把这些组件推到极端。

## 循环的五个动作

Addy Osmani 在 Google Chrome 为自己搭建了一个每天早上运行的垂直循环，把发现、交付、验证、持久化和调度五个动作串在一起。

### 发现：让 Skill 偿还意图债

每天早上，Automation 自动运行一个 triage Skill，读取昨天失败的 CI 测试、仍然打开的 Issue 和最近的 Commit，识别从昨天到今天出现的待处理事项。

项目规则、常见问题和构建方法被写入 `SKILL.md`，每次运行时自动取用，不必重新推导。Addy 把反复交代同一意图产生的成本称为意图债，Skill 的作用就是把这些稳定知识固化下来，逐步偿还这笔债。

### 交付：用 Worktree 隔离并行修改

每个发现都在独立的 Git worktree 中处理，由一个子 Agent 起草修复。隔离的原因很直接：让两个 Agent 同时修改同一个文件，与让两个工程师同时覆盖同一行代码一样容易造成冲突。

工作流程因此变成：发现问题后建立独立 worktree，子 Agent 在隔离环境中修改，完成后再交给下一步审查。

### 验证：让独立评判器审查结果

第二个子 Agent 按 Skill 和测试审查修改。它使用与生成者不同的指令，有时还会更换模型。

写代码的 Agent 给自己的结果打分时容易过于宽松，因为它的上下文中保留着“为什么这样写”的完整推导。独立评判器没有这条自我说服路径，更容易直接检查结果。

### 持久化：把结果和状态写出上下文

验证通过后，Connector 自动创建 PR、更新 Ticket，并把状态写入 Markdown 形式的持久 Memory，供第二天继续读取。系统无法处理的事项进入待处理收件箱，等待人在自动化边界处作出决定。

这种持久化同时保存了两类信息：已经完成并送往外部系统的结果，以及下一轮仍需继续处理的状态。

### 调度：让系统自行开始下一轮

Agent 会浏览仓库和执行任务，却不会自行形成每天早上持续运行的节奏。最后需要由 Automation 负责定时触发，让前四个动作自动开始。

缺少调度，系统只是由人手动运行了很多次 Harness。加上调度，它才从一次执行变成真正的循环：**make a loop an actual loop, not one run**。

## 支撑五个动作的六个组件

五个动作由六个组件共同完成：

1. **Automations**：定时触发循环，对应调度。
2. **Worktrees**：隔离不同 Agent 的文件修改，对应交付。
3. **Skills**：保存项目规则并指导问题发现。
4. **Connectors**：把结果送往 PR、Ticket 或通知系统。
5. **Sub-agents**：分离生成者与评判器，对应验证。
6. **Memory**：把状态写出当前上下文，供下一轮继续。

少一个组件，循环就会在对应动作上失去能力。六个组件并不是彼此独立的工具清单，而是一条从发现问题到下一轮重新启动的闭环。

## 一个能够说“不”的独立评判器

Anthropic 工程师 Prithvi Rajasekaran 观察到一个稳定现象：让 Agent 评价自己刚写的代码，它往往会给出偏高评价，即使结果在人看来质量一般。

问题不只在于模型能力，还在于生成者同时审查自己的结果。生成代码的上下文已经积累整条推导过程，它看到的不只是最终结果，还会沿着原有理由再次说服自己。

这个问题进入循环后会被放大。循环的价值来自无人值守地运行多轮；如果每一轮都由刚写完代码的 Agent 决定结果是否合格，系统便会持续自我确认。运行时间越长，自我肯定累积得越多，结果越可能偏离真实质量。

让生成者在同一上下文里“更挑剔”并不能可靠解决问题。更有效的结构是调用独立评判器，让它带着怀疑检查结果。其灵感类似生成对抗网络：一个负责生成，一个负责判别，通过结构把“写”和“审”分开。

评判器还可以接入 Playwright MCP，自行打开页面、点击按钮、截图并检查 DOM。判断依据由“这段代码看起来没有问题”转变为“点击登录按钮后页面确实跳转，并留下截图”。能够实际验证的评判器检查的是行为证据，而非生成者的意图。

## Ralph 如何把组件推到极端

Ralph Wiggum 技术在形式上只是一行 Bash `while` 循环：

```bash
while :; do
  cat PROMPT.md | claude-code
done
```

它遵循三条原则：

- 一个循环只做一件事。
- 主线程负责调度，子 Agent 承担重任务。
- 每轮重新加载规格和 `fix_plan.md`，不依赖上下文记忆。

Ralph 的特点是在非确定性世界中表现出一种可预测性：它可能失败，但失败模式可以观察，修正也可以进入下一轮。

## 三层 Backpressure

Ralph 使用三层 Backpressure 阻止错误继续向前传播：

1. **测试**：修改完成后立即运行单元测试，失败就继续修复。
2. **类型系统**：使用 Rust 编写编译器，利用编译器的严格检查拒绝不合法结果。
3. **静态分析**：动态语言项目必须配合静态分析器和类型检查器。

资料把模型不稳定地使用 `ripgrep` 搜索列为一个主要问题：模型有时没有搜到已有实现，就误判功能不存在并重复造轮子。因此，Prompt 会反复强调“不要假设没有实现，先搜索”。每次发现新的失败模式，就继续调整 Prompt；Addy 把这种持续校准称为 Tuning。

## 297 美元案例及其边界

资料引用的案例以 297 美元 API 成本完成了一个价值 5 万美元的合同，并使用 Ralph 构建了编程语言 CURSED 的编译器、LLVM 后端和标准库。CURSED 不在大模型训练资料中，这个案例依赖的是规格、反馈和持续迭代，而不是模型对该语言的既有记忆。

这一数字是个案，不代表 Ralph 项目的一般回报率。适用边界同样明确：Ralph 只用于从零启动的绿地项目，不用于已有代码库。

## 总结

本期内容可以归纳为五点：

1. 一个完整循环包含发现、交付、验证、持久化和调度五个动作。
2. Automations、Worktrees、Skills、Connectors、Sub-agents 和 Memory 六个组件共同支撑这五个动作。
3. 生成者不能给自己的结果打分；独立评判器应使用不同上下文，并通过测试或实际行为证据作出判断。
4. Ralph 用单任务循环、规格重载和三层 Backpressure 把循环推到极端。
5. 297 美元与 5 万美元是有明确绿地项目边界的个案，不能推广为所有循环的收益。
