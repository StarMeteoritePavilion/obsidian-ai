> 循环工程系列 第二期

上一期把循环定义为放大器：输入充分理解，它便放大理解；输入对理解工作的逃避，它也会放大这种逃避。

本期进一步拆解这一放大器。同一张循环蓝图可以对应三种完全不同的工程哲学。它们争论的并非某项技术能否工作，而是同一个问题：**人能从循环中退出多远？**

资料把三种观点归纳为结构化流派、极端流派和精准修正流派。人的介入越少，系统的自主程度越高，验证债、理解腐烂、认知投降和 Token 失控四笔代价也越容易累积。

## 三种流派的分歧

### 结构化流派：循环可以运行，但必须受到约束

结构化流派以 Addy Osmani 的观点为代表。它接受循环自动执行工作，但要求工程师继续掌握验证、隔离和最终决策。

这套方法设置三道约束：

1. **独立评判器**：执行任务的 Agent 不能同时给自己的结果打分。让写代码的 Agent 自己审查代码，只会得到它对自身结论的再次确认。Maker 和 Checker 必须分开。
2. **工作区隔离**：多个 Agent 并行工作时，使用 Git worktree 隔离文件。让两个 Agent 同时修改同一工作区，会产生与多人同时覆盖同一行代码相同的冲突。
3. **人工卡点**：能够可靠自动处理的任务继续执行，无法自动判断的内容进入待处理队列，等待人作出决定。人的作用不是拖慢系统，而是保留最终签字权。

结构化流派的核心是：搭建循环时，仍要继续承担工程责任，而不能只负责启动系统。

它在四笔代价上提供了较强防护，代价是速度更慢，人的审查负担也不会消失。

### 极端流派：相信更多循环能够修正问题

极端流派以 Geoffrey Huntley 的 Ralph Wiggum 技术为代表。Ralph 的纯粹形式是一行 Bash 循环：

```bash
while :; do cat PROMPT.md | claude-code ; done
```

它的设计极其简单：

- 每个循环只完成一件事。
- 主上下文负责调度，子 Agent 承担搜索、分析和实现等重任务。
- 每轮重新加载规格文件和 `fix_plan.md`，不依赖上一轮对话记忆。
- 通过编译、测试、类型检查等外部反馈拒绝无效结果。

Huntley 对 Ralph 的概括是：它在非确定性世界里“确定性地糟糕”。失败具有可观察的模式，就可以调整规格、提示序列和外部反馈，再运行下一轮。

资料引用了两个案例：

- 一位工程师用 297 美元的 API 成本完成了一个价值 5 万美元的合同。这个数字来自 Huntley 分享的案例，不代表所有 Ralph 项目都能获得相同回报。
- Ralph 用于构建新的编程语言 CURSED，包括编译器和标准库。该语言不在模型训练资料中，因此这个案例强调的是通过规格、外部状态和持续反馈处理陌生任务。

极端流派的边界也很明确：Ralph 适合从零启动的绿地项目，不适合直接用于已有代码库。它以更高的运行次数和更大的失败风险，换取更少的逐轮人工介入。

### 精准修正流派：先计算成本，再决定是否自动化

精准修正流派以 Fridayland 创建者 Rico Kahler 的观点为代表。它不是否定前两种做法，而是给循环工程加入经济学约束。

其核心修正是：不是 Prompt 已经失去价值，而是重复的 Agent 操控工作应该被自动化。循环也不一定是一段持续运行的代码，以下内容都可以承载循环能力：

- `AGENTS.md` 中可复用的项目规则。
- CI 检查。
- PR 模板。
- 可重复调用的 Skill。
- 带明确停止条件的自动化任务。

判断关键不在于形式是否类似循环，而在于人是否重复执行同一种引导工作。

## 执行视界：瓶颈从操作转移到判断

Rico Kahler 把一个关键转折称为执行视界：系统支持的执行速度，超过人产生、排序和审查好想法的速度。

越过这条线之前，瓶颈是执行。人知道应该做什么，但没有足够时间完成。越过这条线之后，循环完成任务的速度太快，瓶颈变成判断哪些任务值得做。

因此，循环工程不会消除人的工作，而是把人的稀缺资源从操作转移到判断、品位、优先级和审查。

## 盈亏平衡：循环必须偿还建设成本

精准修正流派用盈亏平衡公式判断一项工作是否值得自动化：

`P × N × (S + R) > F`

其中：

- `F` 是搭建循环或基础设施的成本。
- `N` 是未来能够复用它的任务数量。
- `S` 是每次任务节省的注意力或时间。
- `R` 是每次任务避免的风险或返工成本。
- `P` 是循环持续有效并真正被使用的概率。

例如，编写一个发布 Skill 需要 90 分钟，每个 PR 节省 10 分钟操作并避免 5 分钟返工，成功率按 80% 计算。代入公式后，需要超过 7.5 个 PR 才能收回建设成本，因此从第 8 个 PR 开始达到盈亏平衡。

循环还会衰减。工具、仓库、模型和人的要求都会变化，当前有效的循环可能在下个月失效。长期计算必须把维护成本和有效概率随时间下降纳入判断。并非所有工作都应自动化，合理做法是先计算复用次数、节省、风险和维护成本。

## 四笔代价

### 第一笔：验证债

循环可以在无人值守时持续生成 PR，但人的审查速度没有同步增加。结果积累得越快，验证债越重。

根因通常是评判器太弱，或者 Maker 和 Checker 实际上是同一个模型、同一套上下文甚至同一个人。结构化流派设置独立评判器，正是为了限制这笔债。

### 第二笔：理解腐烂

循环运行几天后，代码可能仍然正确，但人已经无法解释它为什么正确。代码持续增长，工程师脑中的系统地图却停留在循环启动之前。

当执行速度越过执行视界时，理解腐烂就是警报：系统产出的变化已经超过人能够吸收和审查的速度。

### 第三笔：认知投降

循环运行得越顺，人越容易停止形成自己的判断，对系统给出的结果照单全收。

执行可以外包，决定做什么、为什么做以及结果是否可接受不能外包。认知投降最危险的地方，是它通常被便利和舒适感包裹，不会像明显错误那样立即暴露。

### 第四笔：Token 失控

循环缺少预算和重试边界时，可能在无人值守期间持续消耗 API 费用，却没有产生相应进展。

高用量不等于进步。上线前必须限制预算上限、最大轮次和重试次数，而不是等到账单出现后再判断循环是否失控。

## 四笔代价形成因果链

四笔代价不是互相独立：

1. 评判器过弱产生验证债。
2. 未完成验证的变化持续累积，导致理解腐烂。
3. 人逐渐放弃理解和审查，进一步滑向认知投降。
4. 循环继续加速运行，又可能同时耗尽 Token 预算。

循环能力越强，这条链传播得越快。设计循环时，必须同时约束验证能力、人的理解速度、决策责任和计算成本。

## 总结

本期内容可以归纳为三点：

1. 结构化流派设置评判器、隔离和人工卡点，极端流派相信更多循环能够修正问题，精准修正流派先用经济公式判断是否值得自动化。
2. 三种流派的根本分歧，是人能够从循环中退出多远；自主程度越高，验证、理解、判断和 Token 成本越需要外部约束。
3. 验证债、理解腐烂、认知投降和 Token 失控会形成因果链，循环越强，这条链累积得越快。
