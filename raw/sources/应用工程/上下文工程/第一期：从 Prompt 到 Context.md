> 上下文工程系列 第一期

## 开篇：为什么 Prompt 写得再好，模型还是会翻车？

这是上下文工程系列的第一期。

Prompt 写得精确到标点，为什么模型还是会翻车？20 轮对话后，它忘了最开始的要求；检索出来的知识跟 prompt 冲突；用户发的链接模型压根访问不了——这些问题，不是 prompt 写得不够好。

而是 prompt 本身只解决了"怎么跟模型说话"，没解决"模型看到的世界长什么样"。这就是上下文工程要补的那一块。

## 一句话说清楚这四个词

- **Prompt Engineering（提示工程）**：跟模型说什么。
- **Context Engineering（上下文工程）**：让模型看到什么。
- **Harness Engineering（框架工程）**：让模型安全执行。
- **Memory Engineering（记忆工程）**：让模型跨会话记住什么。

今天聚焦最核心的那一跳：从 Prompt 到 Context。

## 提示工程 vs 上下文工程

提示工程看的是一段 prompt：写好、发出去、怎么调，全凭经验。

上下文工程管的是六种东西：

1. **系统指令**：模型的角色和底线。
2. **对话历史**：20 轮前的要求不能忘。
3. **外部知识**：RAG 搜来的最新文档。
4. **工具定义**：让模型知道自己能调什么。
5. **用户输入**：当前任务。
6. **示例样本**：范本。

这六样东西各自动态变化、互相影响。一句话概括：**在正确的时间，把正确的信息，以正确的格式，给模型。**

## 提示工程的四道硬伤

1. **静态性**：prompt 写死了，但用户需求是活的。
2. **孤立性**：只盯单轮交互，不管对话历史。20 轮之后，约束全忘了。
3. **扩展性差**：三个模块还行，30 个模块塞进一段 prompt，自己都读不懂。
4. **缺乏工程化**："感觉还行"是唯一标准，没法测试、没法交接。

连 Anthropic 自己在 2025 年 9 月都改口了：把上下文工程定义为"策划与维护最优 token 集合的一整套策略"，明确提示工程只是它的子集。不是替代，是包含。

## 上下文工程管的六张拼图，缺一张就翻车

- **系统指令是常量层**：不随对话变。
- **对话历史是累积层**：20 轮前的要求得记住。
- **外部知识是实时层**：得靠 RAG 搜，而不是靠训练数据里过期的信息。
- **工具定义是能力层**：模型得知道自己能调什么。
- **用户输入和示例样本是信号层**：这是关键认知。

关键在于：这六维不是静态的拼图。每跑一轮就产生新信息——工具输出、中间结果、错误——要不要塞回上下文？怎么塞？

这就是上下文工程的核心：**从不断演化的信息里，策展出一个有限的窗口。**

## 为什么它决定产品能不能上线

上下文工程不是"效果好一点"，它决定产品能不能上线。

- **质量上**：高质量上下文大幅减少幻觉。
- **成本上**：精准检索 + 压缩 + 缓存 + 分层，组合下来 token 消耗能省四倍。
- **可靠性上**：故障隔离和降级策略，是生产系统不崩的地基。
- **复杂场景**：多轮对话、多智能体、多模态，都得靠它撑住。

更长期的是两点：

- **迭代效率**：检索器、压缩器、记忆管理器各自独立，可测试、可交接。
- **护城河**：AI 能力都在商品化，GPT 能做，Claude 也能做。真正的区别在于——谁积累的上下文策略和经验库更深。

## 四句话收尾

1. 上下文工程不是取代提示工程，是包含它——从"怎么说"升级到"看什么"。
2. 六维信息环境，每一样都动态变化。
3. 核心动作是策展：从无限信息里选出有限的最优 token 集。
4. 价值不只是效果好，是更省、更稳、壁垒更强。
