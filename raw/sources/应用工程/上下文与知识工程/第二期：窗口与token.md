> 上下文工程系列 第二期

本期从底层机制出发，介绍信息容器的物理规律。

上下文窗口并非容量无限的容器，它既有硬性上限，也存在“中间信息容易被忽略”的问题。Token 也不简单对应单个字或词，而是直接影响成本与延迟。扩大窗口并不意味着模型能力随之提高，很多情况下反而会降低有效表现。

本期涉及三个核心概念：

- **上下文窗口**：模型一次能够接收的最大 Token 数。容量固定，超出部分会被丢弃。
- **Token**：处理文本的最小单位，不是字，也不是词，是切出来的片段。
- **有效 vs 声称**：说明书写 128K，实际能稳定用的可能只有 64K。窗口越大，管理越重要。

## 上下文窗口

上下文窗口包含模型一次推理能够接收的全部信息：指令、对话历史、检索文档、工具定义，加上模型自己生成的输出。输入、输出共用一个容量池。

可以把上下文窗口类比为工作记忆：容量受到限制，超过有效范围后可能丢失信息，位于中间位置的内容也更容易被忽略。

公式很简单：

> 输入 + 输出 = 总窗口

实际使用仍受容量约束。8K 窗口加入 6K 输入后，输出空间只剩 2K；即使总窗口足以容纳文档，输入占用过多也会压缩输出空间并影响生成质量。

## 窗口不能无限大的三层约束

### 第一层：位置编码

早期方案采用绝对位置编码，训练时只处理过 2K 长度，推理扩展到 4K 时便难以正常工作。

当前主流方案采用 RoPE，通过旋转矩阵编码相对位置，使训练长度为 8K 的模型能够推理到 128K 甚至更高。ELLIE 更进一步，直接根据距离对注意力分数施加惩罚，天然支持任意长度。

### 第二层：KV 缓存

每生成一个新词，都要跟前面所有词的 Key、Value 做点击。缓存下来能省重算，但缓存大小跟上下文长度成正比。

B 模型启用 128K 上下文时，KV 缓存可能占用数十 GB 显存。这会直接影响部署可行性。

### 第三层：注意力计算

每个 Token 要看所有 Token，复杂度是 O(n²)。1K Token 是 100 万次交互，100K 就是 100 亿次。

Flash Attention 等优化可以缓解这一问题，但无法改变其物理规律：长上下文天然需要更高成本。

## Lost in the Middle

长上下文的主要问题是中间信息容易被忽略。这个现象称为 Lost in the Middle，学术上对应 U 型注意力分布。

把整篇论文放入上下文并询问中间段落的数据时，模型可能更多引用开头和结尾，而忽略中间内容。这反映的是注意力分配问题。

经典测试称为 Needle in a Haystack：把一句关键信息置于长文档的不同位置，检查模型能否找到。

测试结论是，多数声称支持 128K 窗口的模型在超过 64K 后，检索准确率便开始显著下降。声称支持的容量不等于有效容量，关键信息的位置比信息总量更重要。

## Token 是什么

Token 是模型处理信息的基本单位。它既不是单个字，也不是完整词，而是分词算法切分出的片段。“上下文工程”五个字可能对应 3～8 个 Token，具体数量取决于所用分词器。

三种主流算法：

- **BPEGPT 系列**：基于频率合并，高频词保持完整。
- **Word Piece BT 系列**：合并标准是自然增益，用标记表示非词首片段。
- **Sentence Piece**：L L M A A、Mistro 这些开源模型的首选，直接在字符级别操作，中文、日文天然友好。

Token 直接影响三项因素：

- **容量**：计数错误会导致内容超出窗口并被截断。
- **成本**：输出 Token 通常比输入贵 2～4 倍。
- **延迟**：推理速度跟 Token 数正相关。

建议使用官方分词器精确计数，不依赖“一个字约等于两个 Token”等经验估算法，以免产生较大误差。

## Token 预算管理

Token 预算管理要求为有限窗口中的每类信息分配预算，并持续记录实际消耗。

典型分配：

- **系统提示词：5%～15%**。尽量精简，冻结不变。
- **检索知识：30%～50%**。这是核心信息区。
- **对话历史：20%～30%**。简单任务少留，多轮复杂任务多留。
- **输出预留：15%～25%**。避免输入占满窗口而挤压生成空间。

不同任务需要采用不同权重：知识密集型任务增加检索预算，多轮对话增加历史预算，长文本生成增加输出预留。

最关键的是使用官方 API 的 Token Counting 获取精确值，不应直接用字符数除以四进行估算。代码、JSON、中文和多模态内容会产生明显误差，不同 Tokenizer 之间的差异也很大。

## 总结

本期内容可以归纳为六点：

1. 上下文窗口是模型的工作记忆，容量固定，输入、输出共享。
2. 底层存在三层约束：位置编码决定可扩展长度，KV 缓存决定显存是否足够，注意力计算决定处理速度。
3. 长上下文的主要问题是 Lost in the Middle，中间信息天然处于劣势，关键内容应置于开头或结尾。
4. 窗口大小与有效使用范围并不相同，多数模型超过 64K 后检索表现便会明显下降。
5. Token 不只是计数单位，还直接影响成本、容量和延迟。
6. Token 预算管理需要划分窗口容量、记录消耗，并根据任务动态调整。

本期介绍了上下文窗口的物理规律。下一期将讨论信息选择与组织方法，包括七项设计原则、四大策略框架和三层质量评估。
