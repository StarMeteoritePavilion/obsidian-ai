# 第二期：窗口与token

上下文窗口并非容量无限的容器。Token 也不是简单对应单个字或词，而是切分出的片段，直接影响成本与延迟。本期从物理机制出发，将信息容器拆解为窗口容量、有效上下文、KV 缓存、注意力计算和 Token 预算五个互不混淆的层次。

## 窗口容量：输入与输出共享

上下文窗口包含模型一次推理能够接收的全部信息：指令、对话历史、检索文档、工具定义，以及模型自己生成的输出。最核心的规则是**输入与输出共用同一个容量池**。

> 输入（预填充） + 输出（解码） = 声明的总窗口

由于总容量固定，实际使用极易受到约束。例如，如果向一个 8K 窗口的模型填入 6K 的输入，留给输出的生成空间仅剩 2K。即使总窗口足以容纳长篇文档，输入如果占用过多，不仅压缩了输出空间可能导致截断，也可能使系统指令被淹没。

## 有效上下文：声明窗口 vs 任务有效窗口

模型声明的窗口（如 128K）主要基于位置编码的理论支持。早期的绝对位置编码难以扩展长度，当前主流多采用 RoPE 旋转位置编码通过插值支持更长序列，或采用 ALiBi 机制（直接根据距离对注意力分数施加线性惩罚）来天然支持任意长度的外推。但这只解决了理论上的扩展，不等于“有效窗口”[3]。

长上下文面临的主要挑战是中间信息容易被忽略，这种 U 型注意力分布现象被称为 Lost in the Middle（对应的经典测试是 Needle in a Haystack，即海底捞针）。

根据 Chroma 发布的上下文退化（Context Rot）研究（针对 18 个模型在受控语义检索等任务上的测试），模型的性能会随着输入长度的增加而变化[2]。部分声称支持 128K 的模型在输入超过特定阈值（如 64K）后，检索准确率便开始下降。但这种退化随具体模型架构和任务类型而异，并不能简单概括为所有模型和任务都会在 64K 显著下降。在实际业务中，关键信息的绝对位置往往比标称的总容量数字更能决定最终效果。

## KV 缓存：预填充与解码成本

每生成一个新词，模型需要与前面所有 Token 的 Key 和 Value 做点积（Dot Product）。为了避免重复计算，推理框架会缓存这些张量（即 KV 缓存）。

在这个过程中，不同阶段的成本存在显著差异：
- **预填充阶段（Prefill）**：并行计算所有输入 Token 的 KV，计算高度密集。
- **逐 Token 解码阶段（Decode）**：每生成一个 Token，都需要从显存读取整个历史 KV 缓存，因此成为受限于显存读取带宽的瓶颈阶段。

KV 缓存大小与上下文长度成正比，受到模型规模、精度、层数和 Batch Size 的严格约束。原视频中提到“模型启用 128K 上下文时，KV 缓存数十 GB”，但未给出具体条件。举例来说，对于一个未采用 GQA（分组查询注意力）的百亿参数量级模型，在 FP16 精度、Batch Size=1 的条件下，128K 窗口的 KV 缓存确实会占用高达数十 GB 显存。这种物理瓶颈直接影响大窗口在生产环境的部署可行性。

## 注意力计算：计算复杂度的物理限制

在标准注意力机制中，每个 Token 都需要与序列中的所有其他 Token 进行交互。
- 在**标准全注意力训练或预填充阶段**，这一操作的时间复杂度为 $O(n^2)$。1K Token 需要 100 万次交互，100K 则需要 100 亿次。
- 尽管在推理时可以通过缓存解码（KV 缓存）缓解，在底层架构上也可以通过稀疏注意力机制等技术优化局部计算成本，但长上下文的计算底座天然需要消耗更多算力资源，这也是长输入处理延迟更高的根本原因。

## Token 及其预算管理

Token 是模型处理信息的基本单位。它既不是单个中文字，也不是完整的英文单词，而是分词算法（Tokenizer）切分出的片段。不同的分词器切分的结果不同，通常五个中文字符可能对应 3～8 个 Token。

业界主要有三种分词算法：
1. **BPE（Byte-Pair Encoding）**：基于频率合并，高频词保持完整（如 GPT 系列）。
2. **WordPiece**：基于自然增益合并，使用特殊标记表示非词首片段（如 BERT 模型）。
3. **SentencePiece**：直接在字符或字节级别操作，对中文等多语言天然友好（如 LLaMA、Mistral 等开源模型）。

Token 数量直接影响：
- **容量**：估算不准会导致实际输入超出窗口而被截断。
- **延迟**：推理速度与生成的 Token 数直接相关。
- **成本**：在主流大模型 API 的计费中，受限于前述的逐 Token 解码代价，输出 Token 的价格通常是输入 Token 的 2～4 倍。因此，压缩冗余输出直接关乎业务利润率。

### Token 预算示例（非固定规范）

上下文工程要求为不同来源的信息分配预算，并持续记录实际消耗。以下仅为一个典型业务场景下的**示例比例**：
- **系统提示词（5%～15%）**：尽量精简、冻结。
- **检索知识（30%～50%）**：核心信息区。
- **对话历史（20%～30%）**：多轮任务多留，单轮任务精简。
- **输出预留（15%～25%）**：防止被输入占满导致截断。

比例不是绝对的固定规范，必须根据任务类型动态调整，且务必使用模型官方的分词器 API 进行精确计数，不依赖“一个字约等于两个 Token”的粗略估算。
