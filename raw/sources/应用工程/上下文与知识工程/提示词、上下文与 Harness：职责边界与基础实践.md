# 提示词、上下文与 Harness：职责边界与基础实践

在构建 AI Agent 和复杂应用时，仅仅优化发送给模型的提示词往往是不够的。模型不仅需要准确理解用户的意图，还需要在长程任务中获得正确的上下文，并受到合理的系统约束。

本文将提示工程（Prompt Engineering）、上下文工程（Context Engineering）、框架工程（Harness Engineering）和记忆工程（Memory Engineering）作为一组概念划分框架，重点探讨前三者的职责边界与基础实践。

## 职责对照：Prompt、Context 与 Harness

为了使模型更好地完成任务，我们需要在不同层面上进行治理。这三类工程分别处理不同的核心问题：

- **提示词工程（Prompt Engineering）——“怎么问”**：关注如何向模型表达要求。它通过设计系统指令和用户输入，引导模型给出更稳定、符合预期的回复。
- **上下文工程（Context Engineering）——“怎么记”**：关注如何管理模型在当前请求中能够看到的全部信息。在多轮调用和工具执行中，通过程序化规则持续维护和策展（Curate）传入模型的信息集合。
- **框架工程（Harness Engineering）——“怎么管”**：关注如何用模型外的规则和系统约束模型完成工作，包括预设工作流、权限控制和质量检查。

这三者的职责并非完全分离。例如，预制的工作流提示词既是提示词工程的产物，也会进入上下文中，同时其目的是为了在 Harness 层面对模型行为进行约束。区分它们的关键在于其主要目的：是在表达任务、组织当前信息，还是约束完整的执行过程。

## 无状态请求与历史回传

现代模型接口在基础调用层面大多是无持久状态的独立请求[^1]。这意味着每次模型调用时，必须将当前输入与此前积累的历史信息拼接起来，一并发送给模型。

在提示词工程中，开发者通常关注设定角色和任务。例如，主流模型接口将提示信息区分为不同的角色：
- **System Prompt**：承载背景、系统规则等全局设定。
- **User Prompt**：用户的具体输入和要求。
- **Assistant / Tool Response**：模型此前的回复或外部工具的返回结果。

在简单的对话中，只需通过追加 `User Prompt` 就能纠正模型方向。但当引入 AI Agent 和工具后，Agent 执行工具（Tool Call）并将工具的返回结果（Tool Response）放入上下文中，连续几十次调用会使上下文迅速膨胀。当这些历史记录和工具返回不断积累时，初始的用户要求很容易被淹没，这就是为什么在提示工程之外还需要上下文工程。

## 上下文六类信息

在上下文工程的视角下，一次请求中的上下文可以被拆分为动态变化、互相影响的六类信息：

1. **系统指令（常量层）**：设定模型的角色与底线，通常不随对话变化。
2. **对话历史（累积层）**：保留之前轮次中的对话脉络和任务要求。
3. **外部知识（实时层）**：通过检索增强生成（RAG）等方式获取的文档。
4. **工具定义（能力层）**：提供给模型的工具及其参数描述。
5. **用户输入（信号层）**：当前轮次用户的核心任务。
6. **示例样本（信号层）**：为模型提供预期输出格式或行为的范本（Few-shot）。

正如 Anthropic 在 2025 年 9 月提出的定义，上下文工程是“策划与维护最优 Token 集合的一整套策略”[^2]。提示工程专注于编写有效的提示，而上下文工程则是提示工程的自然演进，它将提示词也作为上下文管理的一部分，核心动作是从不断演化的信息中为有限窗口“策展”（Curate）。

## 长程任务的四项硬伤

如果不进行主动的上下文管理，仅仅依赖静态的提示词工程，Agent 在执行长程任务时会面临四项硬伤：

1. **静态性**：固定写好的 Prompt 无法适应用户在任务中途产生的动态需求变化。
2. **孤立性**：单轮 Prompt 不管理历史。多轮长程交互后，由于“上下文退化”现象（Context Rot）或注意力分散，模型极易遗忘原有的约束条件。
3. **扩展性差**：当业务逻辑变复杂，将几十条规则强行集中在一段长 Prompt 中会显著增加维护难度，且模型的指令遵循能力会下降。
4. **缺乏工程化**：只依赖主观测试调整 Prompt 难以形成可复用的工程组件，系统很难被稳定测试和交接。

## 笔记、修剪、摘要与检索外移

为了应对长程任务中上下文的迅速膨胀，常用的上下文工程实践包括：

1. **用笔记维持任务状态**：在系统提示中规定模型必须使用“记笔记”工具。模型在行动前分解清单，行动后更新状态，Agent 将这份笔记持续插在上下文的显眼位置，以确保核心目标可见。
2. **修剪旧消息**：最直接的方法是删除过旧的对话或冗余的工具返回记录，仅保留近期的交互（但必须保留初始的系统指令和核心任务要求）。
3. **摘要旧历史**：定期让模型总结较早的上下文，用精炼的摘要替换掉原始的长对话历史，从而在缩短长度的同时尽可能保留关键信息。
4. **长返回外移（动态检索）**：如果工具返回了上万字的完整文章或日志，直接塞入上下文会造成严重污染。此时可以由 Agent 内部消化，例如将其存入临时向量数据库或文件系统，仅向模型返回“已存入知识库，请使用查询工具”的简要结果，让模型按需局部检索（RAG）[^3]。
5. **源头精简工具返回**：在信息进入上下文之前，工具本身应剔除无关内容（例如网页浏览工具先移除多余的 HTML 标签，仅返回正文文本）。

这些操作的共同目标是：在人类无法实时干预 Agent 时，让模型始终记得最初任务，并剔除无关噪声。

## 工作流、权限与质量检查

除了管理上下文，要让 Agent 真正落地，还需要 Harness 工程在模型外部提供约束保障：

- **工作流预制**：对于诸如“写一个游戏”的复杂请求，不能指望模型凭借一句提示词一次性规划并完成。通常需要开发人员在系统外部预先编写好流程（例如提问澄清 -> 写设计文档 -> 代码实现 -> 运行测试），引导模型分步执行。
- **权限隔离**：出于系统安全性考虑，不能给予模型无限的系统访问权。例如，可以设定系统在文件级别只允许 AI 读写指定的项目文件夹，拒绝任何越界访问。
- **质量监控与检查**：为了保证生成质量，可以在 Harness 层引入外部监控。例如，在代码生成场景中，如果监测到新增代码的测试覆盖率不足，Harness 引擎会自动拦截并强制要求模型补充单元测试，然后再进入下一步。

通过提示词解决意图表达，通过上下文工程维持核心状态，再通过 Harness 工程提供边界约束，这是构建可靠长程 Agent 的基础工程范式。
