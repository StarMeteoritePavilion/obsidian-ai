# 第六期：结构化与隔离

当大量资料进入上下文时，模型可能把资料中的内容误认为命令；两个任务共享上下文时，任务 A 的规则也可能影响任务 B 的输出。问题不在于模型能力，而在于不同类型的信息缺少结构与隔离。

本期将上下文的组织分为上下两半：
- **结构化**：在单一上下文内部，用标签说明每块信息的用途，让模型区分指令、文档、示例和输入。
- **隔离**：在不同任务之间划定边界，防止约束、状态和结果互相污染。

## 上半部分：上下文的结构化

结构化负责整理上下文内部信息，使单个上下文内部井然有序，其遵循四项原则：

1. **分类清晰**：指令和文档不能混合，否则模型可能把文档中的文字当作命令执行。每类内容都需要具有明确身份。
2. **层次分明**：结合长上下文中的注意力分布规律，重要内容放在首尾，细节放在中间。层次不仅是排版，也是注意力调度。
3. **边界明确**：不同信息块必须具有清晰边界。边界模糊时，任务和规则容易跨区相互干扰。
4. **关系显式**：文档之间的从属、引用和上下位关系需要直接标注，避免让模型自行猜测。

### 结构化工具的选型

结构化上下文有三种常用工具，选型依据是上下文所含内容类型：

- **分隔符**：最简单、最省 Token，适合内容类型少（如仅有指令和文档两类）的场景。
- **XML**：适合包含指令、文档、示例、约束和格式等多类内容的复杂上下文。
- **JSON**：适合需要程序化拼装、传递和自动测试的场景。

### 本文建议的 XML 结构与三律

针对复杂上下文，本文建议使用以下六类 XML 标签来覆盖大部分内容：
- `<instructions>`：任务指令。
- `<context>`：知识。
- `<examples>`：示例。
- `<constraints>`：约束。
- `<format>`：输出格式。
- `<user_input>`：用户输入。

嵌套用于表达层级。例如，用 `<documents>` 包住文档集合，每篇文档使用 `<document index="1">`，内部再用 `<source>` 标记来源、用 `<content>` 包裹正文。

使用 XML 时，建议遵守以下三律：
1. **命名统一**：全团队采用同一种命名风格，不混用蛇形命名和驼峰命名。
2. **嵌套不超过三层**：层级过深会增加解析难度，应尽量采用扁平结构（注：此为实践建议，非官方强制标准）。
3. **用户输入动态转义**：用 `html.escape()` 处理用户输入，避免输入中的标签被当作真实结构。例如，如果用户输入中包含 `</instructions>`，未经转义就可能提前闭合指令区，形成标签注入。

**深化安全边界**：需要注意的是，不可信用户内容的转义（如 `html.escape()`）只能防止 XML 结构被破坏，**不能单独解决提示注入（Prompt Injection）**。要实现完整的安全防护，还需要补充数据身份标记、严格的权限边界、最小化共享机制以及对模型输出的独立验证。

### 实践总结：四层 Prompt 结构

在工程实践中，Prompt 通常不是一整段话，本文建议将其按稳定性划分为四层结构：
- **L1 核心身份**：定义模型身份，版本级稳定，可以缓存。
- **L2 任务框架**：划定行为边界，为任务画出行为圈。
- **L3 具体指令**：描述当前任务，每轮都可能变化。
- **L4 格式约束**：规定输出形式，比 L3 更稳定。

通过将稳定层（L1、L2）预定义并缓存，动态层（L3、L4）每轮组装，并分别用 XML 标签包裹，既能复用稳定前缀，也能让模型看清各层优先级，避免格式约束覆盖身份定义。

## 下半部分：多任务的隔离

把不同任务混在一起，会产生三类污染：
1. **任务混淆**：A 的约束被套到 B 的任务上。
2. **优先级冲突**：两个任务的指令彼此矛盾。
3. **状态混乱**：各任务的进度和中间状态混合在一起。

为防止不同上下文相互干扰，隔离遵循一条总原则：**默认隔离，确认需要再放开**。

### 隔离的三道防线

根据安全与灵活性的不同需求，隔离机制可以分为以下三层：

1. **“物理”隔离**：指不同任务使用独立 API 调用和独立上下文，边界最强，成本也最高。支付、权限等出错后果严重的高风险任务，应采用此级别的强隔离，确保任务状态绝不相交。
2. **逻辑隔离**：在同一窗口中使用命名空间（`namespace`）分区，适合内部流水线。它更加灵活，但不同分区仍共享一个上下文，因此存在相互干扰的风险。
3. **代码沙箱**：让 LLM 编写代码（如 Python）并在沙箱中执行。沙箱的作用在于建立隔离边界，大对象（如图片、音频等）留在执行环境，只把返回值交回主上下文，既保障了安全，也减少了大对象占用的 Token。

### 子智能体：隔离的生产级落地

在多智能体架构中，主智能体负责协调，子智能体使用独立上下文完成探索，结束后只交付蒸馏摘要。根据 Anthropic 在 2025 年 6 月发布的文章，在内部研究评估中，以 Claude Opus 4 为主智能体、Claude Sonnet 4 为子智能体的多智能体系统，比单智能体 Claude Opus 4 提升了 90.2%。

这套模式在落地时有两项明确的工程规则：
1. **最小信息原则**：子智能体可以完成几万 Token 的探索，但只向主智能体提交精简的蒸馏摘要，不传原始日志和完整对话历史。
2. **显式接口（本文建议格式）**：使用 JSON 标准化传递结果，推荐固定为 `conclusion`、`key_facts`、`next_hints` 三个字段。显式接口让交付可追踪、可调试、可自动测试。

## 总结：五项工程实践

综合结构化与隔离，本期提出以下五项工程实践：
1. **默认隔离**：初始状态不共享，确认需要后再开放。
2. **清晰边界**：明确每个单元的输入和输出。
3. **最小共享**：逐项评估共享信息是否必要。
4. **显式传递**：通过明确接口交付，不依赖隐式继承。
5. **独立测试**：使用 mock 数据单独验证每个单元。

通过结构化与隔离，可以有效防止上下文相互污染。下一期将从建设转向修复，讨论毒化、分心、混淆和冲突四类失效方式及其对应方案。
