> 应用工程／上下文工程独立专题

聊天工具可以产生高质量判断，却很少把这些判断沉淀为可持续维护的知识资产。Karpathy 在 2026 年 4 月提出的 LLM Wiki，试图把大语言模型从每次重新回答问题的工具，变成能够持续编译、链接和治理知识的系统。

LLM Wiki 不是新的 RAG 变种。RAG 在收到查询后检索原始资料、拼接片段并现场综合，回答结束后通常不会保存本次综合结果；LLM Wiki 则把综合从查询阶段前移到摄取阶段。新资料进入时，模型就把它编译为结构化、可导航、可阅读的知识页面，后续查询直接使用已经交叉引用和反复维护的知识资产。

更准确地说，LLM Wiki 是一种以开放文件为载体、以 Schema 为约束、以增量编译为机制的知识工程系统。它不替代 RAG，而是补充 RAG 不擅长的长期沉淀；RAG 可以退到大规模召回层，也可以在 Ingest 前帮助 Wiki 找到需要读取的原始材料。

## 从查询时合成到摄取时编译

资料用一条时间线概括知识系统的演进：2020 年的 RAG 解决外部知识怎样接入生成模型；2024 年的 GraphRAG 提取语料中的全局主题、社区和关系；2026 年 4 月的 LLM Wiki 则把重点从“查询时怎样找到答案”推进到“摄取时怎样把知识编译成长期资产”。这是一种来源中的技术脉络概括，不表示三个系统互相替代。

LLM Wiki 主要回应三个现实问题。

第一，聊天很强，但默认不留下资产。一次对话中形成的技术判断通常被留在会话流里，后续对话无法稳定复用。LLM Wiki 把“高价值答案必须回写”从偶然动作变成制度。

第二，传统笔记系统的主要成本不是写下内容，而是维护链接、分类、去重、冲突和对比。LLM 可以承担大量知识整理工作，但必须接受明确的结构和来源约束。

第三，RAG 会在每次查询时重新发现和综合。同一主题的跨文档判断如果每天重新生成，成本会持续累积。LLM Wiki 把这部分工作改为一次编译、反复使用。

## Raw、Wiki 与 Schema 三层架构

知识系统被分为三层，各层职责不能混合。

### Raw sources：不可变的原始材料

PDF、会议录音、网页和代码目录进入 Raw 层后，不允许 LLM 回头修改。原始材料必须保持可追溯、可审计，成为派生结论的事实依据。

### Wiki：可持续更新的派生知识

Wiki 层保存 LLM 消化后产生的概念页、实体页、对比页、综合页和冲突页。这些页面可以被更新、链接和查询，但每项事实性结论都应能回溯到 Raw 层。

### Schema：行为约束

Schema 决定页面怎样命名、何时新建、怎样引用来源以及怎样处理冲突。没有 Schema，LLM 只是写作者；有了 Schema，它才可能承担知识库维护者的角色。许多知识系统失败，并不是模型能力不足，而是把原始材料、派生内容和操作规则混在了一起。

## 运行控制面

Raw、Wiki 与 Schema 之外，成熟实现还会形成一组运行控制文件。

- `index.md` 是内容目录，列出页面、分类和摘要，也是模型进入知识库时的第一个导航点。
- `log.md` 是时间记录，保存 Ingest、Lint 和 Query 等操作。
- `overview.md` 保存当前认知快照。
- `hot.md` 充当近期上下文缓存。
- `purpose.md` 约束知识库存在的目的。
- `state/` 保存增量缓存或 SHA-256 检查点。
- `review/queue` 提供冲突、新实体和不确定结论的人工判断入口。
- `graph.json` 支持实体、概念、来源和页面之间的图层导航。

成熟的 LLM Wiki 不只是拥有许多页面，还要拥有可以观察、检查和恢复的运行面板。资料转述 Karpathy 的判断：在约 100 个来源、数百个页面的规模下，`index.md` 作为内容目录仍然非常有效。系统不必从一开始就引入向量数据库和知识图谱。

## 知识页面与 Frontmatter

LLM Wiki 不能只有摘要页。资料结合公开实现归纳了八至九类常见页面：Source、Entity、Concept、Comparison、Question、Synthesis、Decision、Gap 和 Meta。它们分别承载来源摘要、实体、概念、横向对比、高价值问答、跨来源结论、决策经验、开放问题以及导航和控制信息。

分类本身不是重点，关键是每页都具有 Frontmatter。类型、标题、摘要、来源、标签、状态、置信度和更新时间不是装饰，而是类型过滤、陈旧检测、图谱导出和结构化查询的基础。

`llm-wiki-compiler` 展示了更细的段落级治理字段：

- `confidence`：页面或结论的置信度。
- `provenanceState`：来源覆盖状态，例如完整、部分或无来源。
- `contradictedBy`：哪些资料反驳了当前页面。
- `inferredParagraphs`：哪些段落属于 LLM 推断，而不是原文直接陈述。

这些字段让直接抽取、模型推断和争议内容保持不同身份，避免派生知识在多轮维护后失去来源边界。

## Ingest 是增量编译

一次 Ingest 不只是为一篇文章生成一页摘要。在部分实现中，一个来源会触达 8～15 个页面：更新相关概念页、新建实体页、记录冲突，并刷新 `index.md`、`overview.md` 和 `log.md`。

成熟的 Ingest 管线可以分为八步：接收原始材料、规范化、读取 Schema、分析页面、生成页面、交叉引用页面、更新控制面、进入 Review Queue。

资料介绍了两个工程实例。`llm_wiki` 桌面实现把 Ingest 拆成两次 LLM 调用：先做结构化分析，再生成页面和 Review 项目。`atomicmemory` 将编译拆为概念抽取和页面生成，并通过 SHA-256 Hash 识别变化，只重新编译已经改变的部分。共同目标是把内容生成转化为可增量、可缓存、可审计的流水线。

## 让 Wiki 持续运行的四项动作

Ingest 只是入口，Query、Save、Lint 和 Research 才让 Wiki 成为持续运行的知识系统。

### Query：查询编译结果

查询不再直接面对原始文档堆。典型流程是先读取 `hot.md` 确定当前方向，再通过 `index.md` 缩小页面集合，执行混合检索，只读取必要页面，最后输出带来源的回答。

### Save：把高价值判断结晶化

Save 也称 Crystallization。对话中形成的长期有效判断应回写为 Synthesis、Comparison 或 Question 页面，而不是只停留在聊天记录中。缺少这一步，LLM Wiki 会退化为带日志的聊天系统。

### Lint：分层治理

Lint 分为结构检查和语义检查。结构层查死链、孤儿页、空 Frontmatter 和重复命名；语义层查陈旧声明、冲突结论和可疑推断。`llm-wiki-agent` 将两层分别放入 `health.py` 和 `lint.py`：前者不调用 LLM，后者才调用 LLM。确定性问题无需消耗模型调用。

### Research：主动补充知识缺口

部分实现从 Graph Insights 或 Review Item 自动生成研究主题，发起搜索，再把结果写回 Wiki。知识库由此不仅消化已有资料，也能发现自己缺少什么。外部研究会扩大来源、隐私和审核范围，不能在没有规则时自动升级为可信事实。

## 对抗性 Ingest

串行单视角 Ingest 容易产生确认偏差：一个模型读取一篇资料并直接写入结论，可疑声明可能被当作事实，后续页面继续沿用错误。

`nvk/llm-wiki` 的 Thesis Mode 为争议命题派出 5～10 个立场分化的 Agent 并行取证，包括支持方、反对方、机制视角、元检视视角和相关领域视角。最终输出明确 Verdict：`supported`、`partially supported`、`contradicted`、`insufficient evidence` 或混合证据，而不是只生成一段看似全面的总结。

另一种方式是多角度并行采集，同一主题分别从学术、技术、应用、新闻和反主流视角进入，再由 Lint 处理冲突。这些方法会让 Token 与延迟增加数倍，因此更适合高风险结论或需要主动打破共识偏差的领域，不应成为所有资料的默认流程。

## RAG、GraphRAG 与 LLM Wiki 的叠加关系

Wiki 扩大后仍需要正式检索层。资料给出的组合是三路信号融合：BM25 负责词法匹配，Vector 负责语义匹配，Graph 负责关系遍历，再用 Reciprocal Rank Fusion（RRF）合并排名。

GraphRAG 不会因为语料规模变大就自动成为最佳选择。资料引用 GraphRAG-Bench 的结论：GraphRAG 在多跳推理、跨实体关联和全局 Sense-making 上具有优势；对 Single-hop 事实检索，Vanilla RAG 更简洁高效。正确路线是按查询类型路由，而不是按语料体量升级。

Adaptive RAG 先由 Query Classifier 判断问题属于 Single-hop、Multi-hop 还是主题综述，再路由到对应检索管线。RAG、GraphRAG 与 LLM Wiki 因而不是互斥方案，而是可以叠加的不同层：RAG 做局部召回，GraphRAG 做关系与全局结构，LLM Wiki 负责长期知识资产。

## 与 Agent Memory、知识图谱和笔记工具的边界

Agent Memory 更关注会话、任务过程和执行轨迹，例如 Agent 做过什么、遇到什么问题以及下次怎样继续；LLM Wiki 面向可外部阅读、可长期维护的结论。前者记录过程，后者沉淀知识。

Obsidian、Notion 等个人知识管理工具更接近前端容器。Obsidian 提供本地 Markdown、Wikilink 和关系图谱，LLM Wiki 的关键则是 Schema、Ingest、Lint、Review 与 Save-back 工作流。

知识图谱和页面也不互相替代。Graph 适合导航、聚类、桥接发现和影响分析；Page 适合解释、叙事、引用和人工审校。成熟系统让 Graph 与 Page 共存。

## 导出、隐私与生命周期

导出层可以把 Wiki 继续提供给其他 Agent。`llms.txt`、JSON-LD、GraphML 和 MCP Resources 分别提供自然语言说明、结构化语义、知识图谱交换和 Agent 资源接口。

一旦启用外部 Research、Web Search 或云模型，内部知识就可能离开本地边界。本地优先、访问控制、审计日志和数据驻留策略因此属于架构选择，而不是上线后的附加功能。

旧知识不一定需要删除，但需要 Retention 与 Forgetting 机制。长期未验证、很少访问或被新证据削弱的内容，应在检索排序和上下文注入中逐步降权。

知识资产健康度可以通过五类指标观察：Source Coverage、Index Freshness、Citation Coverage、Review Backlog 和 Query Save Rate。它们分别检查来源是否被覆盖、索引是否及时更新、关键结论是否有证据、待审问题是否持续积压，以及高价值问答是否真正回写。

## 治理决定系统能否长期存活

两个机制决定 LLM Wiki 能否长期运行。

第一是 Confidence。新近、多来源支持且没有被反驳的内容应获得更高权重；长期未验证的内容应自动降权。

第二是 Supersession。系统不能只记录“这里存在矛盾”，还要明确当前采用哪项结论，并保留旧版本的来源、时间和适用范围。知识库最危险的状态不是缺少信息，而是旧信息仍以当前事实的身份出现。

## 幻觉回写与维护成本

LLM Wiki 最严重的风险是幻觉回写形成闭环。模型在 Ingest 时会把自己以前生成的 Wiki 页面作为背景；一次幻觉被保存后，可能在后续 Ingest 中被当作事实继续扩展、交叉引用和写入新页面。这是一条自我强化的错误传播链，比一次性回答中的幻觉更危险。

风险还包括三种衍生形式：

1. **部分上下文更新**：一次 Ingest 通常只读取 `index.md` 和少量相关页，可能形成局部一致、全局矛盾的修改。
2. **不可逆信息损失**：摘要可能丢掉细粒度条件、例外和限定语。
3. **去 Provenance 化**：派生页面如果不保留原句和来源，出现争议后就无法回溯。

Confidence、段落级 Provenance 和定期 Lint 只能缓解这些风险，不能根治。高风险声明需要主动进入 Review Queue，由人作出判断。LLM Wiki 也没有让维护成本消失，只是把成本从手工写笔记和整理链接，转移到维护 Schema、审核 Review 与处理 Lint 报告。

## 适用与不适用场景

LLM Wiki 适合资料持续进入、结论需要长期沉淀和反复复用的任务，包括长期主题研究、论文精读、代码库理解、竞品情报、个人第二大脑和多 Agent 共享上下文。

它不适合四类任务：一次性问答没有必要建立完整治理层；极大规模低价值语料的粗召回应优先使用 RAG；实时监控告警需要观测系统；严格合规的企业级知识平台还需要更多权限、安全、审计和数据治理基础设施。

## 总结

LLM Wiki 的价值不在某一次回答听起来多聪明，而在于让每一次 Ingest、Query 和 Research 都成为对同一份知识资产的增量投资。可以把这套系统理解为：LLM 是编译器，Chat 是入口，Wiki 是产品，Graph 是导航层，Schema 是操作系统，Review 是刹车，Log 是审计轨迹。

这套方法尝试把 LLM 从每次重新开始的回答器，转变为持续积累、可追溯并可由人审阅的知识运行时。它能否真正“越用越值钱”，取决于来源不可变、增量编译、冲突处理、人工审核和生命周期治理是否同时成立。
