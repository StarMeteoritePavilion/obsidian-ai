> 上下文工程系列 第一期

## 开篇：为什么完善的 Prompt 仍可能失效

这是上下文工程系列的第一期。

即使 Prompt 精确到标点，模型仍可能失效：经过 20 轮对话后遗忘最初要求，检索知识与 Prompt 冲突，或无法访问用户提供的链接。这些问题并非都源于 Prompt 质量。

Prompt 主要解决如何向模型表达任务，却没有完整处理模型能够接收哪些信息。上下文工程用于补足这一层。

## 四个核心概念

- **Prompt Engineering（提示工程）**：向模型表达什么。
- **Context Engineering（上下文工程）**：让模型看到什么。
- **Harness Engineering（框架工程）**：让模型安全执行。
- **Memory Engineering（记忆工程）**：让模型跨会话记住什么。

本期聚焦其中最核心的转变：从 Prompt 到 Context。

## 提示工程 vs 上下文工程

提示工程关注一段 Prompt 的编写、发送和调整，通常依赖经验完成。

上下文工程管理六类信息：

1. **系统指令**：模型的角色和底线。
2. **对话历史**：保留 20 轮前提出的要求。
3. **外部知识**：通过 RAG 检索得到的最新文档。
4. **工具定义**：让模型了解可以调用哪些工具。
5. **用户输入**：当前任务。
6. **示例样本**：范本。

这六类信息各自动态变化、互相影响。可以概括为：**在正确的时间，以正确的格式向模型提供正确的信息。**

## 提示工程的四道硬伤

1. **静态性**：Prompt 内容固定，但用户需求会动态变化。
2. **孤立性**：只关注单轮交互，不管理对话历史。经过 20 轮后，模型可能遗忘原有约束。
3. **扩展性差**：少量模块尚可维护，大量模块集中在一段 Prompt 中会显著增加理解和维护成本。
4. **缺乏工程化**：仅依赖主观感受判断效果，难以测试和交接。

Anthropic 在 2025 年 9 月把上下文工程定义为“策划与维护最优 Token 集合的一整套策略”，并明确提示工程只是其子集。两者不是替代关系，而是包含关系。

## 上下文工程管理的六类信息

- **系统指令是常量层**：不随对话变化。
- **对话历史是累积层**：需要保留 20 轮前提出的要求。
- **外部知识是实时层**：依靠 RAG 检索，而非模型训练数据中的过期信息。
- **工具定义是能力层**：模型需要了解可以调用哪些工具。
- **用户输入和示例样本是信号层**：这是关键认知。

关键在于，这六类信息并非静态拼图。每轮执行都会产生工具输出、中间结果和错误等新信息，系统需要决定是否以及如何把它们重新纳入上下文。

这就是上下文工程的核心：**从不断演化的信息中，为有限窗口策展。**

## 它为何决定产品能否上线

上下文工程不仅影响效果，还决定产品能否上线。

- **质量上**：高质量上下文大幅减少幻觉。
- **成本上**：精准检索、压缩、缓存和分层组合使用，可以使 Token 消耗降低四倍。
- **可靠性上**：故障隔离和降级策略，是维持生产系统稳定运行的基础。
- **复杂场景**：多轮对话、多智能体和多模态都依赖上下文工程支撑。

更长期的是两点：

- **迭代效率**：检索器、压缩器、记忆管理器各自独立，可测试、可交接。
- **护城河**：AI 能力逐渐商品化，GPT 与 Claude 都能完成相似任务。真正的差异在于上下文策略和经验库的积累深度。

## 四项要点

1. 上下文工程不是取代提示工程，而是包含提示工程，实现从“如何表达”到“让模型看到什么”的扩展。
2. 六类信息都会动态变化。
3. 核心动作是策展：从无限信息里选出有限的最优 token 集。
4. 其价值不仅体现在效果，还包括降低成本、提高稳定性和形成更强壁垒。
