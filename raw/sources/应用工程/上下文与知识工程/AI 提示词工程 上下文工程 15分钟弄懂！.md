> 提示词工程到上下文工程的独立导论

提示词工程与上下文工程经常被包装成彼此竞争的新概念，但二者管理的对象不同。提示词工程设计用户怎样向模型表达要求；上下文工程管理模型在当前请求中能够看到的全部信息。简单的一问一答主要依赖提示词，Agent 在多轮工具调用中自主行动时，则需要通过程序化规则持续维护上下文。

## Prompt：用户发送给模型的话

Prompt 的基础含义是用户发给 AI 的话，也就是提示词。普通聊天中，“你好”这类输入可能得到通用、稳妥但缺少特色的回复。用户可以在提示中加入角色设定，引导模型采用特定语气和表达方式。资料以 SillyTavern 作为把角色设定用到极致的例子，但没有展开其具体内容。

角色设定并不是对话内容本身。把设定和用户真正想说的话混在一起，会使输入逻辑变得混乱。为此，模型接口把提示信息区分为不同角色：

- **System Prompt**：承载角色、背景、语气和系统规则等设定。
- **User Prompt**：承载用户直接输入的对话内容或任务要求。

用户通常在聊天框中输入 User Prompt，System Prompt 则由聊天产品预设。资料以 ChatGPT 的 Customize ChatGPT 为例，说明用户偏好也可以间接影响系统提示。

## Prompt Engineering：约束模型行为

提示词工程通过设计 System Prompt 与 User Prompt，引导模型给出更稳定、更符合预期的回复，并减少错误和意外。资料列举了三类常见方法。

### Zero-shot：只给要求

Zero-shot 只描述任务要求，不提供具体示例。要求模型在回答前检查数学题，或在提示中说明任务的重要性、希望获得更完整的回复，都属于资料所说的行为约束。

### Few-shot：提供示范

Few-shot 先给出若干输入与输出示例，再提出真正任务。模型可以根据示例学习目标风格或格式。它尤其适合需要固定输出结构的 AI 应用与 Agent，因为示例能够展示模型应该返回怎样的字符串。

### Chain of Thought：分解问题

Chain of Thought（CoT，思维链）通过提示让模型先拆解问题并给出中间步骤，再生成最终答案。资料以 `1 + 2 × 3` 为例：先按运算优先级计算 `2 × 3 = 6`，再计算 `1 + 6 = 7`。模型本身没有改变，但分步生成提高了得到正确结果的可能性。

资料同时指出，这个算术例子过于简单，当前网页聊天产品通常已经内置更强的推理流程，简单场景不必由用户手工追加同类提示。

提示词工程的核心，是通过精心设计提问与约束方式，使模型输出更精确、更接近预期。

## Context：一次请求中的完整信息

资料采用无持久状态的请求模型解释上下文：每次模型调用本身都是独立请求，连续对话的历史由 Agent 或聊天服务器保存。收到新消息后，服务器把它追加到历史记录，再将包含过往消息的完整记录交给模型。模型因而能够依据此前对话继续回复，看起来像拥有记忆。

这份在当前调用中一次性交给模型的信息集合，就是 Context，即上下文。Context Engineering 则通过程序化规则管理和修改这份信息。

简单问答中，用户可以在每一轮通过新 Prompt 纠正方向。Agent 引入工具后，情况会迅速复杂起来：系统要把原有上下文和工具说明交给模型；模型返回 Tool Call；Agent 执行工具，再把 Tool Response 与调用记录放回上下文。复杂任务可能重复几十甚至上百轮，使上下文不断增长。

工具返回可能包含很长的网页或文档，而用户能够直接施加的任务要求往往位于最初几条消息中。当中间调用和返回持续累积时，模型容易偏离原始目标。上下文工程要解决的核心问题，就是在人类无法逐步干预 Agent 时，自动管理上下文，使模型在长程行动中仍然遵守最初要求。

## 方法一：用笔记维持任务状态

Agent 可以为模型提供记笔记工具，并在 System Prompt 中规定使用策略：

1. 行动前先分解任务。
2. 在笔记中写下任务清单。
3. 严格按照清单执行。
4. 每完成一项就更新状态。

面对“猫娘的口头禅是什么”这类需要多次检索的问题，模型可以先生成任务清单：用 Google 搜索、用萌娘百科搜索，再综合两次结果。模型随后通过 Tool Call 让 Agent 保存清单。Agent 把笔记重新插入上下文的开头或结尾，使核心目标和任务状态保持在显眼位置。每完成一步，模型再更新笔记并进入下一项。

笔记还可以保存检索得到的关键信息，供后续总结使用。其本质是：用户通过初始提示规定笔记策略，Agent 再把持续更新的状态放回上下文，以间接约束模型的后续行动。

## 方法二：控制上下文长度

### 修剪旧消息

最直接的方式是删除过旧消息，只保留近期内容。最初的 System Prompt 和 User Prompt 必须保留，否则模型会失去任务目标。修剪简单直接，但可能丢失仍有价值的信息。

### 摘要旧历史

Agent 可以提取较老的消息，让模型总结关键信息，再用精炼摘要替换原始历史。这样既缩短上下文，也比直接删除保留更多内容，但摘要仍可能遗漏重要细节。

### 把长 Tool Response 外移

如果 Tool Response 包含上万字文章，Agent 可以先将内容处理后存入临时向量数据库，再用一条短消息替换原文，例如说明“文章已存入知识库，并提供 `query document` 工具查询片段”。模型随后只检索当前需要的部分。

这种方法把几万字工具返回压缩成简短说明和少量主动查询片段，实质上是在 Agent 内部应用 RAG，将完整材料移出当前上下文。

### 从源头精简工具返回

工具本身也可以减少冗余。例如，网页浏览工具先删除不必要的 HTML 标签，只把核心内容返回模型。与事后修剪相比，这种方式在信息进入上下文前就降低了长度。

## Prompt 与 Context 的职责边界

Prompt Engineering 关注如何表达当前要求；Context Engineering 关注当前调用中应该保留、插入、压缩、外移或删除哪些信息。提示词是上下文的一部分，也是指导上下文管理策略的入口，但无法单独承担长程 Agent 的全部信息治理。

笔记、修剪、摘要、RAG 外移和工具输出精简没有改变同一个目标：当用户无法实时干预时，让模型始终记得最初任务，并保留完成任务真正需要的信息。资料没有把这些方法描述为公认的完美方案，而是视为当时较常见、较有效的实践；上下文管理仍在持续演进。

## 让长期目标保持可见

作者以童年时写下“长大后当老师”的愿望收束全文。多年后依然记得这项目标，说明真正重要的信息需要以合适的方式长期保持可见。对于 Agent 而言，上下文工程承担的也是类似职责：在大量中间信息中维持目标、状态和关键事实，不让行动过程淹没最初意图。
