> 提示工程系列 第五期

## 开篇：推理仍受知识与工具限制

这是提示工程系列的第五期。上一期介绍了自我一致性和链式提示，用于提高 AI 推理的稳定性并拆分大型任务。但稳定推理仍然受到知识不足、计算不准和信息过期的限制。

当被问及“高尔夫得分越高越好吗”，模型可能错误回答“是”，而高尔夫实际以杆数较少为优。模型并不具备全部知识，计算也可能不准确，训练知识还存在截止日期。

本期介绍三种解决方法：

- **生成知识提示**：让模型在回答前先自行生成相关知识。
- **编程语言推理**：让代码接管计算。
- **工具调用**：直接接入搜索引擎和外部 API。

## 核心结论

三种方法共同解决大模型自身能力存在不足的问题：

- **生成知识提示**：模型回答前先自行生成相关知识，把隐性知识转化为明确依据，在缺少把握时先补充知识再作答。
- **编程语言推理**：模型负责确定计算方法，Python 解释器负责执行计算，两者分工完成任务。
- **工具调用**：模型判断自身能力不足时，调用搜索引擎、计算器或翻译 API 等外部工具。

## 三种方法的关系：从轻到重

三种方法可以按工程复杂度从轻到重排列：

- **生成知识提示**属于纯 Prompt 工程，不依赖外部工具，通过两步 Prompt 即可完成，实施门槛最低。
- **编程语言推理**要接一个 Python 解释器，但接的是执行器，不是知识源。
- **工具调用**最重，需要接入搜索引擎、计算器和翻译 API，工程代价最高，但覆盖能力也最完整，由模型自行判断何时使用哪种工具。

这三条路径从轻量 Prompt 技巧延伸到完整工具架构，分别处理知识不足、计算不准确和信息过期等问题。

## 第一种方法：生成知识提示

### 为什么会错

模型在常识题上出错，并非一定缺少相关知识，也可能是错误调用或偏离了隐性知识。解决方法是先让模型写出相关知识，再基于这些知识作答。

### 具体两步

1. **第一步**：使用 few-shot 演示驱动模型生成知识。提供若干“输入 → 知识”范例，引导模型为新问题生成知识条目。
2. **第二步**：把生成的知识与原问题一同加入 Prompt，引导模型基于这些知识作答。

仍以“高尔夫得分越高越好吗”为例。先生成“目标是以最少杆数打完”这一知识，再回答问题，答案便会从“是”转为“否”。

### 内部检索

这种方法也称为**内部检索**：外部检索查询维基百科等外部来源，内部检索则调用模型自身的参数化知识，从而省去向量数据库的工程复杂度。

但生成的知识本身也可能错误。模型可能先生成错误知识，再基于该知识作答，使错误进一步累积。因此，生产环境不能直接使用单条生成结果，而需要多次采样和质量筛选。

## 第二种方法：编程语言推理

### 为什么算不准

大模型在算术任务中容易出错，涉及小数、除法和多步混合运算时，错误率会进一步上升。原因在于它并非计算器，每个数字都按 Token 逐步生成，而非逐位计算。

### 让代码接管计算

两个团队在 2022 年分别提出方向相同的解决方案：由模型生成代码，再交给 Python 解释器完成计算，即 PAL 和 PoT。具体做法是把 CoT 的自然语言推理链替换为 Python 代码。

模型不再写 `4 × 30 = 120`，而是写 `time = 30 * 4` 这样的代码交由解释器执行后可以得到确定的计算结果，而不是概率性的文本输出。

### 关键洞察：解耦计算与推理

这里的关键洞察是解耦计算与推理：

- **LLM 擅长语义理解**，负责把"四倍时间"对应成 `* 4`。
- **解释器擅长精确计算**，负责除法，结果永远精确。

该方法需要安全的代码沙箱，模型也必须具备基本代码能力，但可以使数学题计算基本不出错。

## 第三种方法：工具调用

### 前两招的局限

工具调用的覆盖范围最广。前两种方法各有局限：生成知识提示无法补充最新新闻，编程语言推理也无法承担翻译、搜索和日历查询。

工具调用的核心思想是承认 LLM 能力有限，为其接入外部工具，并让模型自行判断何时调用外部能力。

### 两条代表路线

- **TALM**：让模型反复与工具 API 交互，把效果较好的结果用于扩充训练集，以较松散的方式模拟强化学习。
- **Toolformer**：采用纯自监督方法。先通过 few-shot 让模型在文本中标注潜在的 API 调用位置，再执行调用，并检查加入结果后模型预测后续内容的损失是否下降；若损失下降，便把该结果保留到增强数据中用于微调模型。

Toolformer 接入计算器、问答系统、搜索引擎、翻译系统和日历五类工具，分别弥补不同能力短板。

### 训练侧 vs 提示侧

需要明确的是，TALM 和 Toolformer 属于训练侧方法，工具调用会改变模型权重。当前工业界更主流的是提示工程侧方法，即保持模型不变，通过 Prompt 引导模型决定何时以及如何使用工具。

例如，Claude 使用 system prompt 中的 XML 标签控制何时主动行动、何时等待指令。这套逻辑的完整形态是采用“思考—行动—观察”循环的 ReAct。

## 选择方法：AI Agent 的核心骨架

AI Agent 核心结构可以按以下条件选择：

- **常识问题经常答错** → 使用生成知识提示，成本最低。
- **算术问题经常算错** → 使用编程语言推理，接入 Python 解释器。
- **缺少最新信息** → 使用工具调用，接入搜索引擎。
- **同时存在多项能力短板** → 使用工具调用，并配置多个 API。
- **多类短板同时存在且需要自主决策** → 使用完整的 Agent 架构：ReAct + 工具链 + 记忆系统。

这几种方法还可以组合使用：

- **CoT** 负责推理，**链式提示**拆解任务，**自我一致性**在关键步骤投票纠错。
- **生成知识提示**补偿知识，**编程语言推理**接管计算，**工具调用**负责所有外部能力。

从第三期“让 AI 会想”，到本期“让 AI 能查、能算、能动手”，下一期将把这些方法应用到生产环境。

## 总结

| 方法 | 核心 | 适用场景 | 代价 |
| --- | --- | --- | --- |
| 生成知识提示 | 缺少把握时先补充知识，不依赖外部工具 | 常识、隐性知识类题目 | 最轻量，但可能有幻觉，需要筛选 |
| 编程语言推理 | LLM 确定公式，Python 执行计算，提高精度 | 算术、多步混合运算 | 需要安全的代码沙箱 |
| 工具调用 | 接入外部能力，由模型判断何时使用 | 从搜索引擎到日历 API 的各类实时能力 | 工程代价最高 |

这三条路线共同标志着一个转向：提示工程不再只关注“如何向模型表达任务”，而是扩展到“如何为模型配置协作能力”。
