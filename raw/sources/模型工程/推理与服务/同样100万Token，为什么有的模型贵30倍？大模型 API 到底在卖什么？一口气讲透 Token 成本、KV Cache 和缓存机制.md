# 模型 API 的成本结构：输入、输出、缓存与批处理

API 价格表使用相同的“每百万 Token”单位，不同模型、输入输出方向和调度方式却可能采用不同单价。判断成本时需要固定平台、模型、日期和调用条件，再比较完成同一任务的总支出；“旗舰模型一定更可靠”或“便宜模型一定需要更多重试”都不能只由单价推出。

要理解这种差异，必须将 Token 从单纯的分词单位，还原为由模型能力、算力消耗、显存占用、调度机制与缓存共同决定的商业计量单位。本文将按计费项目和成功任务成本展开，剖析大模型 API 的成本结构。

## 核心计费项目解析

API 价格表通常按不同的使用场景和消耗环节拆分计费。主流的计费项目主要包括输入、输出、缓存和批处理。

### 输入 (Prefill) 与输出 (Decode)
大模型推理分为两个阶段，这决定了它们不同的成本：
- **输入阶段 (Prefill)**：负责“读题”。完整输入已就绪，GPU 可大规模并行处理上下文，计算效率高，算力成本易摊薄。
- **输出阶段 (Decode)**：负责“答题”。采用自回归方式，每个新 Token 必须依赖前面的所有内容，无法一次性并行生成。每次计算都受限于显存带宽与调度效率。

Decode 的逐 Token 依赖会影响服务调度，但不能仅由硬件机理推出所有平台的定价比例。以 2026 年 9 月 7 日 Claude 官方 API 价格页为例，Fable 5.1 的标准输入和输出分别为每百万 Token 10 美元和 50 美元；同页 Opus 5、Sonnet 5、Haiku 4.5 也都显示输出价是输入价的5倍。这个5倍只描述该页面当日列出的四个模型，不是行业常数。[^价格]

### KV Cache 与长上下文
模型在生成新 Token 时，不会从头重算全部历史，而是复用注意力机制已计算的 Key 和 Value，这就是 KV Cache。它不是数据库，而是推理阶段的高速“草稿纸”。
上下文越长，单次请求占用的显存（KV Cache）就越大，同一张 GPU 能并发处理的请求数就越少，导致**吞吐下降**和**延迟上升**。因此，极长上下文（如 128K、100 万 Token）本质上消耗了更多的高速显存资源。部分平台会对长上下文单独设置阶梯定价。

### Prompt Caching (提示词缓存)
许多应用请求包含大量重复的 System Prompt、工具定义和知识库背景。如果将这些稳定的内容置于请求前部形成“稳定前缀”，平台可以将其 KV Cache 状态缓存下来。
命中缓存的输入 Token 可以采用单独的读取价格。上述官方价格页在5分钟 TTL 条件下为 Fable 5.1 列出每百万 Token 12.50美元的缓存写入价和0.25美元的缓存读取价；写入比标准输入更贵，后续命中读取更便宜。是否节省取决于前缀能否复用、有效期内命中次数及写入成本，不能只引用一个“最多节省”比例。[^价格]

### 批处理 (Batch API)
如果任务不需要实时响应（例如离线数据清洗、批量翻译、自动评测），可以检查平台是否提供异步批处理。Claude 官方价格页在2026年9月7日明确写“使用批处理节省50%”；该折扣只用于该平台页面指向的 Batch processing 条件，不能外推为其他平台的统一政策。[^价格]

## 成本算例：吞吐、延迟与单次费用的权衡

下面按2026年9月7日官方页面列出的 Fable 5.1 标准输入、输出、5分钟缓存写入和读取单价计算。这个例子只说明账单结构，不预测未来价格或任务质量。[^价格]

**场景设定**：
- 系统规则与背景知识（稳定前缀）：30,000 Token
- 用户查询（动态输入）：500 Token
- 模型输出：1,000 Token
- 假设：稳定前缀已经写入且仍在5分钟 TTL 内；本次请求100%命中该前缀

**未命中缓存的单次费用**：
- 输入成本：30,500 × (10 / 1,000,000) = 0.305 美元
- 输出成本：1,000 × (50 / 1,000,000) = 0.05 美元
- **总费用**：0.355 美元/次

**命中缓存的单次费用**：
- 缓存读取成本：30,000 × (0.25 / 1,000,000) = 0.0075 美元
- 新增输入成本：500 × (10 / 1,000,000) = 0.005 美元
- 输出成本：1,000 × (50 / 1,000,000) = 0.05 美元
- **总费用**：0.0625 美元/次

首次建立缓存还要支付：30,000 × (12.50 / 1,000,000) = 0.375美元；加上本例动态输入与输出，当次合计0.43美元，反而高于不缓存的0.355美元。要至少命中一次后再看累计账单，缓存才可能抵消首写溢价。这里没有计入TTL延长、批处理或其他服务层费用。

通过对比可见，单次费用不仅取决于基础单价，更受缓存策略影响。此外，成本还需区分以下维度：
- **单次费用**：单次 API 调用的直接账单支出。
- **成功任务费用**：将失败重试与人工干预纳入考量后的整体费用。
- **延迟成本**：实时交互场景下，未命中缓存或长上下文会导致首字延迟（TTFT）极高，损害用户体验。
- **吞吐成本**：在资源固定的私有部署或限流的 API 中，单次请求占用显存过大，会挤占系统整体吞吐量（TPS），间接推高并发服务的平均成本。

## 关注成功任务的总成本

比较 API 价格时，“每百万 Token 多少钱”只是表象。便宜的模型若能力不足导致反复重试、产生幻觉，后续的人工介入成本将远超节省的 API 费用。而旗舰模型虽然单价昂贵，如果能一次性达成目标，反而更经济。

我们可以用以下决策框架（注意：这是工程决策辅助，而非严格的会计公式）来衡量真实成本：

> **成功任务真实成本** = ( 单次 Token 费用 × 平均尝试次数 + 延迟带来的业务损失 + 人工稽核与修正成本 + 系统运维与路由调度成本 ) ÷ 任务最终成功率

## 开发者的 Token FinOps 实践

面向未来，Token 的计费将越来越精细化，开发者需要建立类似云账单管理的 Token FinOps 机制：

1. **核算总成本**：不再仅盯 API 账单，而是按上述决策框架评估“每次成功业务动作”的全局开销。
2. **实行模型路由**：将高价、强推理的模型留给复杂决策和高容错风险环节；将廉价模型用于客服闲聊、文本分类等高频标准化任务。
3. **结构化上下文**：不要将长上下文当成免费数据库。提取稳定前缀，把 System Prompt、Schema 和稳定背景知识前置，最大化缓存命中率；动态的片段放后。
4. **离线任务降级**：所有不追求实时响应的任务（如批量审核、数据打标），优先使用低优先级的 Batch 批处理来换取成本空间。

大模型 API 的账单同时受输入、输出、缓存写入与读取、批处理和任务重试影响。先固定价格版本，再按真实 Token 数和成功率计算，才能比较方案。
