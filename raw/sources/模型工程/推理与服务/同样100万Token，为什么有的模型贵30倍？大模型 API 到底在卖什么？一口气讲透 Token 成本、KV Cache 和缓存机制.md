> 大模型 API 成本与推理服务独立专题

同样是 100 万 Token，不同模型的价格可以相差 30 多倍。价格表虽然使用相同的计量单位，背后却不一定是同一种商品。本文的核心判断是：高价模型主要出售复杂任务中的确定性，低价模型主要出售规模化的性价比。理解这一区别，需要把 Token 从分词单位还原为模型能力、推理算力、显存、缓存、延迟、调度和服务保障共同形成的商业计量单位。

## Token 从技术单位变成商业单位

这里的 Token 与区块链代币或 Web3 资产凭证无关，而是大模型处理信息的基本单位。文本先被切分为 Token，再进入模型完成计算、理解和生成。

Token 原本只是技术文档和 API 参数中的工程概念，如今已经成为 AI 行业的商业单位。主流 API 价格表会区分输入 Token、输出 Token、缓存命中的输入 Token、批处理 Token、优先级请求、多模态输入和 Reasoning Token。它们把不同形态、不同环节的智能消耗折算成可报价、预算、优化和采购的单位。

相同数量的 Token 并不代表相同价值。低价模型通常服务高频、标准化、低风险、对错误容忍度较高的任务，出售的是吞吐、规模和足够好的能力；旗舰模型面向复杂、高风险、高价值任务，出售的是更高的成功率、稳定性、工具生态、安全边界和风险降低。两者处于同一计量单位之下彼此叠加的不同市场。

## Prefill 与 Decode 为什么价格不同

大模型推理大致可以分为两个阶段：Prefill 负责读题，Decode 负责答题。

在 Prefill 阶段，完整输入已经给定，模型可以较为并行地处理上下文，并计算生成阶段需要的中间状态。GPU 擅长这类大规模并行计算，输入 Token 的成本更容易摊薄。

Decode 阶段则按自回归方式工作。第二个输出 Token 依赖输入和第一个 Token，第三个又依赖此前全部内容，无法一次并行生成整段答案。每个新 Token 都需要新的计算和调度，还受到显存带宽与调度效率限制，因此输出 Token 通常比输入 Token 更贵。

资料称，主流旗舰模型的输出价普遍是输入价的五到六倍，并举出输入约 5 美元／百万 Token、输出 20 多美元／百万 Token 的定价结构。这些数字反映视频发布时的价格观察，具体采购仍需核对对应模型和平台的当前价格页。

Reasoning Token 进一步改变了账单。部分模型会在返回最终答案前生成用户不可见的内部思考 Token；在资料描述的计费结构中，这些 Token 仍按输出计费。最终回答可能只有几百字，中间却消耗数千乃至上万个 Reasoning Token，是否开启深度思考可能让同一任务的账单相差数倍。

图片和音频也会按平台规则换算为相应 Token。图像 Token、音频 Token 与 Reasoning Token 的共同逻辑，是把不同形态的模型计算折算为可计量的消耗。

## KV Cache：长上下文占用的高速工作区

模型生成新 Token 时，不会从头重算全部历史，而是复用注意力机制中已经计算出的 Key 和 Value。KV Cache 是推理阶段保存这些上下文中间状态的高速工作区，不是人类意义上的记忆，也不是数据库，更像模型工作时铺开的草稿纸。

复用能够减少重复计算，草稿纸本身却要占用显存。上下文越长，单个请求的 KV Cache 越大；并发请求越多，总占用也越大。结果是同一张 GPU 能同时服务的请求减少，吞吐下降、延迟上升，单位 Token 成本随之增加。

因此，支持 128K、200K 乃至 100 万上下文不只是“多读一些文字”。部分模型会对长上下文单独定价，输入超过特定长度后，输入和输出一起进入更高价档。具体长度门槛和倍率属于各平台的版本化规则，长上下文本身并不是免费的能力。

## Prompt Caching：把稳定前缀变成低成本输入

AI 应用的请求经常包含大量重复内容，例如 System Prompt、角色设定、工具定义、JSON Schema、企业规则、代码库背景和知识库说明，真正变化的可能只有用户问题与临时参数。如果这些内容构成可复用的稳定前缀，Prompt Caching 可以复用此前已经计算的状态，避免每次从头处理。

缓存命中的输入 Token 通常更便宜，响应也可能更快。资料称，命中部分的价格往往约为原价的十分之一；按部分平台的官方说法，Prompt Caching 最多可节省 90% 的输入成本，并把延迟最多降低 80%。这些是平台宣称的上限，不是所有请求的固定收益。

不同平台还可能要求前缀达到最小长度、受缓存有效期约束、显式设置缓存断点，或由平台自动判断命中。相同文字不必然命中缓存。更准确地说，Prompt Caching 是把可识别的重复上下文转化为低成本输入的机制。

Prompt 结构会直接影响命中率。稳定的 System Prompt、工具定义和长期规则应放在前部，用户问题、临时参数和动态内容放在后部，使前缀尽量保持不变。缓存 Token 并非完全没有成本，但通常明显低于重新计算。

## RAG 应用中的成本结构变化

一个企业知识库问答请求可以包含 3,000 个 Token 的系统规则与工具定义、30,000 个 Token 的企业文档片段、约 200 个 Token 的用户问题，以及 1,000 个 Token 的模型输出。若全部视为新输入，每次都要承担 33,000 多个输入 Token 的成本。

如果系统规则、工具定义和部分稳定背景材料能够缓存，后续请求的成本结构会发生变化。优化重点不再只是缩短回答，而是让稳定上下文尽可能复用，让动态检索内容更精准，并控制输出长度。Token 成本管理由此成为产品架构问题，而不只是文字长度问题。

## Batch：用等待时间换取更高 GPU 利用率

实时请求要求平台预留高优先级算力、减少排队并保证延迟；批处理允许平台合并和调度大量请求，提高 GPU 利用率，因此价格通常更低。资料把实时请求比作专车，把 Batch 比作拼车，并称批处理价格通常约为标准价的一半。

离线摘要、批量标注、数据清洗、自动评测、内容审核和代码迁移等不要求即时响应的任务，更适合使用 Batch。Token 的价格因此不只取决于模型，还取决于请求需要多快、使用什么优先级、能否缓存、运行在哪个资源池，以及采用标准请求、批处理、企业合约还是自托管。

## 真正应比较的是成功任务的总成本

低价 Token 适合客服、文本分类、信息抽取、摘要、翻译、简单代码解释和批量内容处理等标准化任务。高价 Token 面向大型代码库重构、复杂数据分析、法律文书审查、金融建模、科研辅助和企业级 Agent 工作流等高价值任务。

用户最终购买的不是 Token，而是任务完成。便宜模型单次调用成本低，如果失败率高、需要反复重试、人工审核和返工，总成本可能更高；贵模型单次费用高，如果一次成功并减少人工干预，反而可能更便宜。

资料给出一个判断框架：

> 真实成本 =〔Token 单价 × Token 用量 + 延迟成本 + 错误成本 + 人工稽核成本 + 运维成本〕÷ 任务成功率

这不是会计公式，而是提醒采购者把单价、用量和任务外成本放在一起比较。每百万 Token 的价格不能单独回答模型是否昂贵，关键是模型能否稳定完成具体任务、减少重试并降低错误风险。

## API 费用最终落在三件事上

表面按 Token 收费的 API，费用最终落在三个层面：

1. **能力本身**：模型能力、上下文长度、复杂任务处理能力，以及减少人工与返工的可能性。
2. **交付方式**：实时或等待、普通或优先队列、缓存命中、Batch 调度，以及这些选择背后的算力利用率。
3. **风险与保障**：API 稳定性、工具生态、权限、日志、监控、合规、安全和企业支持。

Token 因此只是智能基础设施的计量单位。越关键的任务，用户越可能为可交付性和风险降低付费。

## 开发者的六项成本实践

1. **核算任务总成本**：同时记录 Token 费用、延迟、错误、人工修正、运维和返工，不以单价替代总账。
2. **区分任务类型**：长输入短输出重点优化上下文与缓存；长输出重点控制生成长度和结构；实时任务关注延迟，离线任务优先评估 Batch。
3. **实行模型路由**：简单任务使用低价模型，复杂任务使用强模型，失败后再升级，而不是所有任务都固定使用最强或最便宜的模型。
4. **管理上下文**：不把长上下文当数据库；能检索、摘要或压缩的信息，不应把全部历史和文档直接塞入 Prompt。
5. **提高缓存命中率**：把 System Prompt、工具定义、Schema 和稳定背景材料放在前部，减少稳定前缀中的无意义变化。
6. **建立 Token FinOps**：像管理云账单一样，追踪高消耗用户、过长输出、浪费性的 Prompt、高重试任务、缓存命中率和每个成功任务的平均成本。

## 结论

未来 Token 定价不会变得更简单。输入、输出、缓存、长上下文、思考、批处理、优先级、多模态、工具调用和自托管 Token，会继续对应不同的成本结构与商业模式。

高价端竞争的是更稳定、更高质量地生产复杂任务所需的智能，低价端竞争的是以更低成本规模化生产足够好的智能。应用层则需要把昂贵能力留给最难的任务，把低价能力交给可规模化任务。讨论大模型价格时，真正有意义的问题不是每百万 Token 多少钱，而是每完成一个有价值的任务究竟花了多少钱。
