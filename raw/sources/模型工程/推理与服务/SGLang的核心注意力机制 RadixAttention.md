# SGLang的核心注意力机制 RadixAttention

SGLang 使用 Radix Tree 组织不同请求的公共前缀，并复用已经计算好的 KV Cache，减少重复 Prefill。一条边可以保存一整段连续 Token，出现分叉时再拆分；节点记录这些 Token 的 KV 位于哪些 GPU 物理槽位。

## 公共前缀怎样组成一棵树

以“为什么我的代码会报错”“为什么显存老是不够用”和“为什么我的代码这么慢”为例，三条提示词都共享“为什么”，其中两条进一步共享“我的代码”。Radix Tree 从根节点出发，将相同前缀合并，在不同部分分叉。沿根到对应叶子的路径，把各条边上的 Token 连起来，就还原了示例中的完整提示词。

节点保存五类信息：子节点映射、父节点引用、边上的 Token 列表 `key`、物理槽位下标张量 `value`，以及最近访问时间 `last_access_time`。`key` 表示父节点到当前节点这条边上的 Token；`value` 表示这些 Token 的 KV 存放在哪里。两者长度相同、逐项对应，节点不直接保存 KV 数据。

子节点映射以分支的第一个 Token ID 为整数键，以子节点为值。不同分支已经在公共前缀之后分叉，其第一个 Token 不同，因此只用第一个 Token 就能区分分支，无需把整段 Token 都作为映射键。

例如，“我的代码”对应节点的 Token 列表包含“我的”和“代码”，槽位下标为 2、3；父节点对应“为什么”，槽位为 1。它有两个子分支：以“会”开头的“会报错”对应槽位 4、5，以“这么”开头的“这么慢”对应槽位 10、11。

## 物理槽位与空闲池

在作者描述的缓存布局中，K、V 缓存在启动时预先分配，按 Transformer 的 L 层 Decoder 组织。每层再划分为多个物理槽位，每个槽位保存一个 Token 在该层的 K、V 张量。相同槽位编号贯穿全部层，可以理解为一根柱子：例如槽位 4 在每层都对应同一位置的切片。

按这一教学布局，单层中一个 Token 的 K 或 V 张量形状是“注意力头数 × 每个头的维数”；把各层合起来，K、V 缓存各自可表示为“层数 × 槽位总数 × 注意力头数 × 每个头的维数”。

空闲槽位下标保存在 GPU 上的 `free_pages` 张量列表中，示例初始下标从 1 到槽位总数。分配 N 个槽位时，从列表前端取出 N 个下标；释放时，则把指定的槽位下标交回空闲池。例如分配两个槽位，初始会取出 1、2。下标本身位于 GPU 上，取出后可以直接用于索引对应的 K、V 缓存。

## 前缀匹配与节点分割

新提示词从根节点开始逐边匹配。整条边都匹配时继续向下；如果只匹配边的前半段，就在最长公共前缀结束的位置分割节点，将公共部分提取为父节点，把原有剩余部分接到它下面，再为新提示词的未匹配部分建立分支。

例如树中已有“为什么我的代码会报错”，新请求是“为什么显存老是不够用”。只有“为什么”匹配，于是将它单独提取成公共前缀节点，原来的“我的代码会报错”成为一个子分支，新增的“显存老是不够用”成为另一个子分支。

分割时改变的是 Token 段和槽位下标的组织方式，已有 KV 在 GPU 中保持原位。请求复用命中前缀的槽位，只为未命中后缀分配空间并计算 K、V，随后把后缀及其槽位信息插入树中。

作者将这种方式与此前介绍的 PagedAttention 前缀匹配作对照：后者按 Block 计算哈希并查表，RadixAttention 则遍历树寻找最长公共前缀。作者认为两种思路的复杂度相同；这里保留这一比较判断，不把它扩展为端到端性能相同的结论。

## 从叶子开始回收槽位

物理槽位不足时，作者介绍的淘汰流程把叶子节点按 `last_access_time` 组织成最小堆，取出最久未访问的叶子，删除节点并归还其槽位。叶子删除后，父节点可能成为新的叶子，需要继续维护叶子集合与堆，重复处理直到释放足够空间。

这一过程保留公共前缀，并先从末端分支回收缓存。究竟哪个分支先被淘汰，取决于示例中记录的访问时间。

## 四个时刻中的匹配、分割与淘汰

以下 Token 切分和槽位编号均沿用作者的教学示例。

### 时刻 0：第一条请求全部计算

“为什么我的代码会报错”进入空树，没有任何前缀命中。五个 Token 全部计算，依次使用槽位 1–5。计算完成后，整段提示词作为一条边插入树中，节点的槽位列表为 1、2、3、4、5，最近访问时间为时刻 0。

### 时刻 1：分出“为什么”

“为什么显存老是不够用”只匹配原边上的第一个 Token“为什么”。系统在此分割，公共前缀复用槽位 1；剩余四个 Token 分配槽位 6–9，计算后插入新分支。

此时有两个叶子：原提示词剩余的“我的代码会报错”，以及新提示词剩余的“显存老是不够用”。作者在示例中将两个叶子的最近访问时间都记为时刻 1，并把前者的时间变化归因于刚发生的节点分割。

### 时刻 2：进一步分出“我的代码”

“为什么我的代码这么慢”先完整匹配“为什么”，再按“我的”找到原分支；但该分支只有“我的代码”匹配，因此再次分割，将这两个 Token 提取为公共节点。

沿途收集到槽位 1 和 2、3，这三处 KV 无需重算。新增的“这么慢”占用槽位 10、11，计算后插入树中；此时空闲池耗尽。

按照作者的示例，“会报错”和“这么慢”两个叶子的最近访问时间都变为时刻 2，而“显存老是不够用”仍为时刻 1。这个时间差决定下一次淘汰顺序。

### 时刻 3：命中前缀后淘汰旧分支

“为什么我的代码不能编译”完整匹配“为什么”和“我的代码”，继续复用槽位 1、2、3。公共节点下没有以“不能”开头的分支，因此无需再次分割已有边，只需增加新分支。

新增的“不能”“编译”需要两个槽位，但空闲池已经耗尽。最小堆中，“显存老是不够用”对应叶子的最近访问时间最早，为时刻 1，因此该叶子被删除，槽位 6、7、8、9 归还空闲池。请求取出槽位 6、7，完成两个新 Token 的计算，再将其插入树中。

## 前缀命中节省了什么

Radix Tree 负责找到可复用的 Token 前缀，槽位下标把这些 Token 与已经计算好的 KV 连接起来。命中后可以跳过该段 Prefill；新后缀仍需计算。缓存保留的是 K、V 中间状态，后续请求在公共前缀的基础上继续处理，并非直接取回以前的回答。
