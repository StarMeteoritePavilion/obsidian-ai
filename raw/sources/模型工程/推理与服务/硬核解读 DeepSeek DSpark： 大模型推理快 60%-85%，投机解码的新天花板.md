# DSpark：半自回归草稿与置信度验证调度

DSpark 的论文标题是《DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation》。它针对投机解码中的草稿生成与验证调度进行联合优化。

本文原视频属性记录的发布日期为2026年6月30日；arXiv:2607.05147v1 的提交记录为2026年7月6日。现有材料没有解释这一先后差异，因此分别保留两个日期，不把视频日期写成论文公开日期。[^论文]

大语言模型逐 Token 自回归生成时，每产出一个 Token 都要重新执行一次网络前向。长回答需要连续完成数百轮计算，硬件利用率和用户等待时间因此受到限制。投机解码（Speculative Decoding）用一个更小、更快的草稿模型（Draft Model）先生成若干 Token，再由目标模型（Target Model）并行验证整段草稿：被接受的前缀保留，从第一个错误位置开始舍弃后续草稿。

这一过程可以在数学上保持与目标模型独立自回归生成相同的输出分布，因此属于无损加速。它的优化空间可以归纳为三个杠杆：更快地产生草稿、更准确地产生草稿，以及以更低成本完成验证。DSpark 同时处理了前两个阶段中的关键矛盾。

## 草稿生成的两种路线

自回归草稿会在预测下一位置时参考已经生成的草稿 Token，因此连贯性较好；代价是草稿每增加一个位置，都要多执行一次前向。为了控制延迟，这类草稿模型通常只能采用较浅的网络，并生成较短的草稿块。

并行草稿的代表方法 DFlash 只需一次前向，就能同时预测后续一整块 Token。草稿长度对这次前向的耗时影响很小，因此网络可以更深，草稿块也可以更长。但同一块内的各个位置同时预测，无法参考相邻位置已经选择了什么，容易把多个合理表达的片段错误拼接在一起。

例如，后文既可能是 `of course`，也可能是 `no problem`。如果两个位置分别偏向 `of` 和 `problem`，组合结果就会变成不连贯的 `of problem`。资料把这种现象称为多模态碰撞（Modal Collision）。随着草稿位置向后移动，不连贯问题不断积累，接受率快速下降，形成后缀衰减（Suffix Decay）。

## 反直觉结果：并行草稿的接受长度更长

从单个位置的预测质量看，自回归草稿更连贯；实验结果却显示，存在后缀衰减的并行草稿最终获得了更长的接受长度。原因不在草稿尾部，而在第一个 Token。

投机解码从前向后依次验证草稿。一旦第一个 Token 被拒绝，后面即使预测正确也会一起失效。第一个位置因而是整块草稿的关键门槛。预测第一个 Token 时，前面还没有已经确定的草稿 Token 可供参考，准确性主要取决于草稿模型理解原始上下文的能力，也就是模型容量。

自回归草稿为了避免每个位置都增加过多延迟，只能采用较浅的网络；并行草稿一次产生整块，可以使用更深的网络。更大的容量使并行草稿在第一个位置上更准确，这一优势通过前缀验证规则被放大。即使后续位置逐渐出现后缀衰减，总接受长度仍可能超过自回归草稿。

这项拆解把草稿生成问题分成了两部分：第一个 Token 主要需要容量，后续 Token 主要需要连贯性。DSpark 据此设计了半自回归生成。

## 半自回归：并行主体加轻量串行模块

半自回归（Semi-Autoregressive）把草稿生成拆成两个阶段。深层并行模型作为主体，一次前向生成整块草稿的底稿，保留容量与速度优势；随后连接一个极轻量的串行模块，让后续位置参考已经确定的前文，修正并行预测造成的不连贯。

在 `of course` 与 `no problem` 的例子中，如果第一个位置已经确定为 `of`，串行模块会提高 `course` 的分数并压低 `problem` 的分数。它不是用完整自回归过程重做草稿，而是在并行底稿上补充少量位置依赖。

论文第4.3.2节在批量大小128、上下文长度集合为512/1024/2048/4096的条件下测量整轮延迟：草稿长度从4增至16，相对DFlash增加0.2%～1.3%的延迟；在草稿长度15时，数学、代码、聊天的接受长度相对DFlash分别提高30%、26%、22%。这些数字不能脱离目标模型、批量、上下文和草稿长度理解。[^论文]

## 固定验证长度为什么浪费算力

草稿能够生成得更长以后，验证阶段会出现新的浪费。越靠后的 Token 越不确定，如果把整块草稿一律交给目标模型验证，高并发时就会让大量算力消耗在很可能被拒绝的尾部上。系统空闲时验证更多位置可以利用剩余算力，系统繁忙时则应优先保证吞吐。

任务类型还会显著改变草稿接受率。不同任务的输出约束和可接受续写空间不同，草稿通过目标模型验证的概率也会变化。对所有任务、所有负载采用同一个固定验证长度，因此只能得到次优结果。

## 置信度调度：按当前负载决定验证多长

DSpark 为草稿模型增加置信度头（Confidence Head），给每个位置输出一个置信度分数，用来估计该 Token 通过验证的概率。调度器不再使用固定草稿长度，而是以有效吞吐为目标：

> 有效吞吐 = 预计接受的草稿数 × 每秒轮数

增加验证位置可能提高每轮接受的 Token 数，但更大的批量也可能降低每秒能完成的轮数。调度器从最有把握的草稿开始，按通过概率逐个加入验证范围；当有效吞吐不再上升时停止。相同的计算会随负载得到不同停止点：系统空闲时多验证几个位置，系统繁忙时更早砍掉低置信度尾部。

置信度筛选提高的是送入目标模型验证的草稿质量，并改变实际验证长度；它不等于提高草稿模型对所有位置的原始预测准确率。具体收益必须与目标吞吐、负载和置信度阈值一起报告。[^论文]

## 校准与无损早停

置信度分数只会排序还不够。调度器需要用概率计算每轮预计接受多少 Token，因此需要准确的绝对概率，而不只是位置之间的高低顺序。神经网络输出通常过度自信，直接参与计算会使停止点偏离最优位置。DSpark 增加校准步骤，使预测分数与真实接受率对齐。

动态裁剪还必须保持投机解码的无损性质。决定是否裁剪以及裁剪到哪里时，不能参考尚未确定的草稿 Token，否则会引入偏差并改变输出分布。DSpark 的无损早停（Lossless Early Stop）只依据已经确定的部分作出停止决定；一旦继续验证不再划算，就立即结束当前验证范围，同时保留系统效率和数学约束。

## DeepSeek-V4 线上结果

论文报告 DSpark 已部署在 DeepSeek-V4 服务系统的真实用户流量中。此前线上对比基线为 MTP-1；静态增加验证长度会在高并发下浪费目标模型的批处理容量。[^论文]

在总吞吐对齐的前提下，论文摘要和第5节报告：V4-Flash单用户生成速度相对MTP-1提高60%～85%，V4-Pro提高57%～78%。论文还列出Flash 120 TPS、Pro 50 TPS等严格交互档位，说明收益同时受服务负载约束。[^论文]

这些结果属于 DeepSeek-V4 线上系统及资料所述负载条件，不能直接外推到其他模型、硬件或流量结构。实际收益依赖草稿模型容量、置信度校准、任务接受率、批量大小和实时系统负载。

## 结论

DSpark 分别处理了投机解码的两个矛盾：半自回归用深层并行模型保证第一个 Token 所需的容量，再用轻量串行模块恢复后续连贯性；置信度调度按负载计算验证长度，并通过校准与无损早停保证概率可用和输出分布不变。

更具普遍性的启示是，优化不能停留在“自回归更准确”或“并行一定更快”这类整体直觉上。把接受率按位置拆开后，第一个 Token 与后续 Token 的作用并不相同；把有效吞吐拆成接受草稿数和每秒轮数后，验证更多也不必然更快。先找到真正控制结果的杠杆，再把模型容量和系统算力投入到对应位置，才可能同时获得算法质量与工程收益。
