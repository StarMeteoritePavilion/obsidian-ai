> Agent 强化学习基础设施独立专题

Kimi K3 技术报告中有一个容易被模型跑分遮住的数字：训练和评估期间累计创建了 51,219,741 个沙箱，涉及 1,505,678 种镜像。它们不是用户、服务器或同时运行的虚拟机数量，而是在不同时间、不同任务中创建的隔离执行环境。

这项工作的核心是 Kimi 团队与合作伙伴共同开发的 AgentENV。它不是让模型保存内部思考，而是让训练系统能够暂停、复制和恢复 Agent 正在操作的外部世界，包括文件系统、进程、内存、软件依赖、数据库内容和其他操作系统状态。长时程任务由此不必在一次连续运行中完成，外部环境的生命周期也能进入强化学习调度。

## 长时程 Agent 需要保存三类状态

一次长时程 Agent 任务通常涉及三类彼此不同的状态。

第一类是模型状态。训练期间模型参数持续更新，系统需要知道一条轨迹由哪个版本的模型生成，这会影响该轨迹之后怎样参与策略优化。

第二类是推理与轨迹状态，包括消息历史、工具调用及返回结果，以及推理引擎保留的 KV Cache。这些信息记录 Agent 已经知道什么、执行到了哪一步。

第三类是外部环境状态，包括修改过的文件、运行中的进程、已经安装的依赖、数据库变化和操作系统状态。AgentENV 主要负责这一层。模型权重、请求状态和 KV Cache 由 Kimi K3 的其他基础设施管理，因此 AgentENV 既不保存模型内部推理，也不等同于完整的强化学习系统。

## Partial Rollout 如何缓解长尾延迟

同一批强化学习轨迹的完成时间可能相差很大：简单任务几十秒结束，复杂任务可能需要数百次工具调用并持续数小时。如果必须等整批轨迹全部完成后才能更新模型，少数超长任务会拖住训练迭代，已经完成的轨迹只能等待。

Kimi K3 使用 Partial Rollout 缓解这种长尾延迟。一批任务完成到设定比例后，系统先用已完成的轨迹进行策略优化；尚未完成的轨迹被暂停并进入队列，在下一轮训练迭代开始时优先恢复。

暂停一条轨迹不能只保存当前答案。Agent 可能已经修改大量文件、启动测试进程或安装复杂依赖；如果外部环境无法恢复，之前的执行就会失效。因此，Partial Rollout 决定何时暂停和恢复轨迹，AgentENV 则保存并恢复轨迹对应的外部环境。

跨训练迭代并不是唯一需要暂停的场景。Agent 完成一次工具调用后，需要等待模型根据返回结果生成下一步行动。在 Kimi K3 技术报告所述的部分工作负载中，等待模型推理的时间最高可占沙箱生命周期的 98%。AgentENV 可以在等待期间暂停沙箱，释放 CPU 和内存；模型返回后再恢复原来的文件系统、内存和进程状态。快照仍会占用存储空间，并非没有成本。

## 为什么传统容器不够

传统容器主要使用 Namespace 隔离进程可见的系统资源，使用 Cgroup 限制 CPU、内存等资源配额。它们成熟、高效，适合权限受控、行为明确的常规服务，但多个容器仍共享宿主机内核。

Agent 训练需要允许更开放的探索。任务可能挂载磁盘、运行容器，甚至在环境中启动虚拟机。Kimi 团队早期使用传统容器沙箱时，曾观察到意外 Agent 操作引发的 kernel panic 和 deadlock。共享宿主机内核时，这类故障可能波及同一机器上的其他任务；如果反过来把权限锁得过紧，环境又无法提供接近真实系统的操作空间。

AgentENV 因而以 Firecracker microVM 为基础。每个 microVM 保留独立的操作系统内核和运行任务所需的虚拟硬件，同时移除传统虚拟机中不必要的设备与启动环节。它比共享内核的容器提供更强隔离，又比传统虚拟机更适合高密度、短生命周期的沙箱工作负载。

## Pause and Resume、Fork 与 Snapshot

AgentENV 在 microVM 之上提供三类关键操作。

### Pause and Resume

Pause 把正在运行的沙箱暂停，并保存恢复所需的状态。暂停后的沙箱不再占用 CPU 和内存；Resume 恢复文件系统、内存和进程，使任务从暂停位置继续运行。它既服务于 Partial Rollout，也用于释放等待模型推理期间的空闲资源。

### Fork

Fork 从正在运行的沙箱精确状态创建独立副本，同时让原环境继续执行，两边互不干扰。奖励评判与结果验证可以在副本中运行测试或修改环境，而不污染原始轨迹。

### Snapshot

Snapshot 按固定间隔保存恢复点。任务发生故障时，系统可以回到最近状态继续执行，而不必从头重跑整条长轨迹。

## 让海量沙箱可承受的底层机制

三类操作能够在大规模训练中使用，依赖多项底层优化。

**增量检查点**只保存上一次检查点之后被修改的内存页，不必每次复制全部内存。技术报告给出的最低检查点延迟约为 133 毫秒，最低恢复延迟约为 49 毫秒；这是特定设置下的最低值，不代表每次操作都能稳定达到。

**Copy-on-Write** 让多个环境在创建时共享相同的内存页或数据块，只有真正发生写入时才复制对应部分。Fork 和大规模并行因此不必为每个沙箱立即复制完整状态，但复制本身仍有开销。

**OverlayBD** 用于沙箱镜像，配合定制的批量驱动、存储层共享和点对点传输，减少重复数据读取与复制。相同的底层镜像层可以复用，只有沙箱自身的差异层需要独立保存。

技术报告称，Copy-on-Write 内存和页面缓存优化使真实工作负载中的内存超配比例最高达到 6.5 倍。这里的“超配”表示分配给全部沙箱的账面内存总量可以高于实际物理内存，而不是物理内存本身增加。该数字来自 Kimi K3 的工作负载，不能直接外推为其他集群的可用比例。

## 跨模型版本轨迹带来的 Off-Policy 问题

频繁暂停和恢复也会引入训练代价。一条长轨迹可能跨越多个训练迭代：前半段由旧版本模型生成，后半段由更新后的模型继续。采集数据的策略与执行更新时的策略不再一致，轨迹会产生 Off-Policy 数据陈旧问题。

Kimi K3 使用逐 Token 正则化限制策略更新的局部变化，使训练能够容忍跨版本长轨迹并维持稳定。这个机制处理的是模型侧的数据陈旧；它与 AgentENV 保存外部环境属于不同职责，不能用环境快照替代。

## AgentENV 的边界与意义

Kimi K3 的后训练与评估并非只使用 AgentENV。技术报告还列出传统容器运行时和 GPU 沙箱运行时；AgentENV 是其中面向 Agent 工作负载、以 microVM 实现高保真隔离和灵活生命周期的一类环境。

AgentENV 的价值也不只是创建轻量虚拟机，而是以较低的状态切换成本管理数量庞大、镜像各异、生命周期不同的执行环境。它为 Agent 强化学习提供了高保真、强隔离且可持久化的交互空间，并把文件系统、进程、内存和快照纳入训练系统的调度范围。

“让 AI 学会存档”保存的不是思考文字，而是 Agent 正在操作的世界。随着软件开发、网页操作和信息检索任务持续时间增长，这类基础设施会直接影响长轨迹数据的生产效率、训练成本和可靠性。
