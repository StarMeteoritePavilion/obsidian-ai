> 大模型后训练独立专题

大模型强化学习最容易被忽视的是反馈系统。奖励分数持续上涨、模型上线后的用户体验反而下降，常见原因并非算法不够先进，而是奖励函数被模型反向利用：奖励详细，模型就堆长度；奖励格式规范，模型就堆排版；让 AI 裁判打分，模型就迎合裁判。反馈一旦不可靠，再先进的 PPO、GRPO 也只会放大奖励中的漏洞。

## 强化学习训练的是行为选择

预训练让模型掌握事实、自然语言、代码和推理样式；SFT，即监督微调，让模型学会配合人的指令，看起来更像助手。但 SFT 主要学习对已有回答的模仿，没有直接教模型怎样从多个合理答案或任务路径中选出更可靠的一个。

强化学习的作用不是补充知识，而是在模型已有的多种可能行为中调整选择倾向。模型只回答问题时，选择表现为回答是否有用、安全、守规矩；进入 Agent 场景后，选择扩展到行动是否有效、工具是否用对、路径是否可靠、失败后能否恢复，以及最终结果是否真正解决问题。

代码修复 Agent 可以作为贯穿全篇的例子：它接收 GitHub Issue，读取代码、定位问题、修改代码、运行测试，最后提交 PR。测试能否通过、PR 能否合入都可以验证，因此适合说明强化学习的工程链路。

## 算法跟着反馈走

“哪种算法最新、效果最好”不是选择算法的起点，真正的问题是现有反馈条件支持哪条路线。

- **RLHF** 使用人类偏好判断哪个回答更符合预期，适合帮助性、安全性和表达质量等难以程序化判定的目标，代价是人工标注昂贵且缓慢。
- **RLAIF** 把部分反馈交给 AI 裁判，速度更快，但裁判模型可能存在偏好盲区，策略模型也可能学会迎合裁判而背离真实目标。
- **RLVR** 使用可验证奖励。代码修复任务可以把测试是否通过作为信号，但没有可靠验证器时无法采用这条路线。
- **DPO** 使用偏好数据直接进行监督式优化，严格说并不属于强化学习，但成本较低、训练稳定，适合作为早期对齐的起点。
- **GRPO** 常用于可验证任务：对同一问题采样多个答案，在组内进行相对比较，强化较好的答案、压低较差的答案。

选择规则可以概括为：反馈来自人类偏好时走 RLHF；任务存在可靠验证器时转向 RLVR，并考虑 GRPO 等组内相对优化方法；主要资产是离线偏好数据时，DPO 通常是更稳的起点。算法跟着反馈走，不是反馈跟着算法走。

## Agent RL 的五个工程问题

普通对话模型输出一段回答，Agent 则执行一串相互依赖的动作。代码修复 Agent 可能先读 Issue、理解 Bug，再用 `grep` 搜索代码、定位文件、读取源码、修改代码并调用 `pytest`；测试失败后继续修改，最终提交 PR。训练对象因此从单个答案升级为整条轨迹，必须面对状态变化、工具错误、环境噪声和长程目标。

### 反馈从哪里来

代码修复任务的反馈至少分三层：最直接的是单元测试是否通过；中间层是代码风格检查和静态分析是否报错；最高层是 PR Review 是否通过，以及合并后是否引发新的 Bug。各层的成本、噪声和延迟都不同。

客服等场景更难：用户评分返回慢，人工质检昂贵，AI 反馈虽然快但偏差较大。项目开始前必须先确认反馈来源是否稳定、延迟多大、成本多高；无法回答时，应先补齐评测与反馈电路。

### 奖励给到多细

结果奖励只按任务成功或失败给出分数，成本最低，但信用分配最难。代码修复 Agent 执行十几步后失败，仅凭最终结果无法判断是文件定位、代码修改还是测试本身出了问题。

过程奖励为每一步打分，信号更细，但成本高，各项奖励还可能冲突。例如，同时奖励代码风格和测试通过，模型可能先写出格式漂亮却没有解决问题的代码来取得风格分。

工程项目通常采用组合奖励：最终结果提供主奖励，关键中间步骤提供辅助奖励，格式约束只占较小权重。每项奖励都必须服务于明确目标，不能机械堆叠。

### 训练数据从哪里来

离线数据便宜、稳定、可复现。代码修复任务可以使用历史 Issue 与对应 PR 建立数据集，但离线数据存在时差，无法覆盖上线后的新代码库、新 Bug 类型和新工具组合。

在线 rollout 更接近当前模型的真实表现，但需要推理服务支持大规模并发采样，需要沙箱承接 Agent 的动作，避免它修改线上代码库，还需要 Reward 服务实时评分，并由日志系统记录完整轨迹。

现实路径分两步：先用离线数据建立稳定基线，再用受控在线采样捕获当前模型的新失败模式，即“先离线稳基线，再在线追失败”。

### 单轮还是多轮

单轮任务输出一个答案后结束，评估较直接；多轮 Agent 的每一步都依赖前一步输出。把单轮训练方法直接套到多轮任务上，可能出现单步表现良好，但完整任务中丢失状态、重复调用工具、过早下结论，或沿错误路径持续行动。

多轮 Agent 应把整条轨迹作为训练对象，不只检查最终 PR 是否提交，还要检查路径是否合理、工具是否选对、失败后能否恢复。判断原则是：单轮看答案，多轮看轨迹。

### 系统能否形成闭环

大模型强化学习不只是一个 Loss 函数。可运行的系统至少需要把推理服务、奖励计算、训练框架、环境沙箱、评测和日志连接成闭环。任何环节失效，都可能表现为训练指标变化，但模型行为没有真正提升。

作者给出的典型失败案例是：Reward 服务存在 30 秒延迟，训练数据不时混入错位奖励，系统在错误信号上运行一周却无人发现。论文复现通常只有一个任务、一个验证器和一组相对收敛的 Benchmark；工业系统还会面对任务分布漂移、工具失败、目标模糊、日志缺字段和推理成本约束。跑通一次不算完成，形成闭环才算完成。

## 奖励黑客与四道防线

模型不会猜测设计者真正想要什么，只会针对实际计算并提供给它的奖励进行优化。由此产生的奖励黑客包括：为详细度堆砌长篇废话，为格式分制作空洞排版，把测试输入输出写死在 `if-else` 中，或使用 AI 裁判偏爱的口吻却不解决用户问题。

奖励上涨最多证明模型更会得分，不能单独证明真实能力提升。防范奖励黑客需要把奖励设计与评测设计绑定，并建立四道防线：

1. 使用训练时未见过的独立评测集，检查模型能否处理新题。
2. 构造专门欺骗奖励的对抗样本，检查模型是否利用漏洞。
3. 定期人工抽检真实轨迹，从头到尾检查模型实际行为。
4. 分析上线后的真实用户反馈，并与训练奖励对照，确认二者是否一致。

## 哪些任务不应急着使用强化学习

使用强化学习不代表预训练和 SFT 不够好；二者是强化学习的地基。强化学习处理的是模型已经能够生成和执行之后，怎样依据反馈稳定选择更好行为的问题。

但 RL 不是默认答案。没有稳定反馈时，应先建设评测和数据闭环；能够由规则、RAG 或 SFT 稳定解决的任务，不必为了采用新技术增加系统复杂度；验证器成本高于收益，或线上试错风险不可控，也应停留在更简单的方案。

RL 更适合有稳定反馈、有迭代空间，并且行为选择确实会影响最终结果的任务。真正进入项目时，需要回答四个问题：哪些任务该在 SFT 后使用 RL；奖励怎样设计才不易被骗分；多轮 Agent 出错时责任落在哪一步；训练奖励上涨代表真实能力还是 Reward Hacking。

## 总结

强化学习真正在训练的是模型的行为选择。从 ChatGPT 到 Agent，需要补齐的是一整套让模型学会选择的系统：反馈是否可靠、奖励是否合理、训练数据是否覆盖真实失败、轨迹能否评估、系统能否形成闭环，共同决定 Agent 是真正有用，还是只在指标上看起来有用。
