> 提示工程系列 第五期

## 开篇：想得再稳，脑子里没货也白搭

这是提示工程系列的第五期。上一期讲了自我一致性和链式提示，让 AI 想得更稳，把大任务拆开。但想得再稳，脑子里没货还是白搭。

问大模型：高尔夫得分越高越好吗？它张嘴就说"是"，完全反了——高尔夫是杆数越少越好。模型不是万事通，有些知识它压根没有，数学也算不准，知识还有截止日期。

这一期给出三个解法：

- **生成知识提示**：让模型答题前先自己补知识。
- **编程语言推理**：让代码接管计算。
- **工具调用**：直接接上搜索引擎和外部 API。

## 先说结论

一句话说清楚这三招要解决的问题：大模型自身能力有短板，怎么补？

- **生成知识提示**：模型答题前先自己生成相关知识，把隐性知识变成明确依据。没把握就先补一课再答。
- **编程语言推理**：模型负责想怎么算，Python 解释器负责算出来，各干各的。
- **工具调用**：模型自己判断"这题我不会"，直接叫外援——搜索引擎、计算器、翻译 API。

## 三招的关系：从轻到重

先把三招的关系捋清楚，从轻到重排开。

- **生成知识提示**是纯 prompt 工程，零外部依赖，两步 prompt 就搞定，门槛最低。
- **编程语言推理**要接一个 Python 解释器，但接的是执行器，不是知识源。
- **工具调用**最重，接搜索引擎、计算器、翻译 API，工程代价最高，但也补得最全，模型自己判断什么时候用哪种工具。

这三条路，从轻量级的 prompt 技巧到重装上阵的架构，应对不同层级的短板。一句口诀记住：知识不够自己补，计算不准代码算，知识过期、啥都不会就叫外援。

## 第一招：生成知识提示

### 为什么会错

模型在常识题上犯错，不是因为它笨，是因为隐性知识调错了、调偏了。解法很巧妙：与其指望模型自动调对，不如让它先把知识写出来，再看着知识作答。

### 具体两步

1. **第一步**：用 few-shot 演示驱动模型生成知识。给几个"输入 → 知识"的范例，引导它对新问题产出知识条目。
2. **第二步**：把这条知识和原问题一起塞进 prompt，让模型基于知识作答。

还是那道题：高尔夫得分越高越好吗？先生成知识"目标是以最少杆数打完"，再回答，答案就直接从"是"翻转成"否"。

### 内部检索

有人把这一招叫作**内部检索**：外部检索是查维基百科，内部检索就是让模型查自己的知识库，省掉了向量数据库的工程复杂度。

但要注意，生成的知识可能本身就是错的。模型可能生成错误知识，再基于错误知识作答，错上加错。生产环境不能生成一条就用，需要多条采样、质量筛选。

## 第二招：编程语言推理

### 为什么算不准

大模型算术常出错，一旦涉及小数、除法、多步混合运算，翻车率就蹭蹭涨。因为它不是计算器，每个数字都是逐 token 生成的，不是逐位计算的。

### 让代码接管计算

两个团队在 2022 年同时想到同一个解法：别让模型自己算，让它写代码，交给 Python 解释器算。这就是 PAL 和 PoT，做法很直接——把 CoT 的自然语言推理链换成 Python 代码。

模型不再写 `4 × 30 = 120`，而是写 `time = 30 * 4` 这样的代码，扔进解释器跑，结果精确，不是"大概率对"。

### 关键洞察：解耦计算与推理

这里的关键洞察是解耦计算与推理：

- **LLM 擅长语义理解**，负责把"四倍时间"对应成 `* 4`。
- **解释器擅长精确计算**，负责除法，结果永远精确。

代价是需要安全的代码沙箱，模型也得有基本的代码能力，但换来的是数学题基本零出错。

## 第三招：工具调用

### 前两招的局限

工具调用是最重磅的一招。前两招各有局限：生成知识提示补不了最新新闻，编程语言推理补不了翻译、搜索、查日历。

工具调用的核心思想是承认 LLM 不是万能的，给它接上外部工具，让它自己判断什么时候叫外援。

### 两条代表路线

- **TALM**：让模型反复跟工具 API 互动，做得好就记住、扩充训练集，松散地模拟强化学习。
- **Toolformer**：更优雅，纯自监督。先用 few-shot 让模型在文本里标注潜在的 API 调用位置，再执行调用，看加了结果后模型预测后续内容的损失有没有下降；下降了就保留进增强数据里微调模型。

Toolformer 接入了计算器、问答系统、搜索引擎、翻译系统、日历五类工具，各补一个短板。

### 训练侧 vs 提示侧

但要讲清楚一件事：TALM 和 Toolformer 是训练侧的工具，调用改的是模型权重。现在工业界更主流的是提示工程侧，不改模型，靠 prompt 引导模型决定何时、如何使用工具。

比如 Claude 用 system prompt 里的 XML 标签控制什么时候该主动行动、什么时候该先等指令。这套逻辑的终极形态，就是"思考—行动—观察"思考循环的 ReAct。

## 怎么选：AI Agent 的核心骨架

现在来看 AI agent 的核心骨架怎么选：

- **常识老答错** → 用生成知识提示，成本最低。
- **算术老算错** → 用编程语言推理，接 Python 解释器。
- **不知道最新信息** → 用工具调用，接搜索引擎。
- **短板不止一个、同时存在** → 直接上工具调用，配多个 API。
- **要是全都有，还需要自主决策** → 那就是完整的 agent 架构：ReAct + 工具链 + 记忆系统。

而且这几招不止能一起用，天然就该一起用：

- **CoT** 负责推理，**链式提示**拆解任务，**自我一致性**在关键步骤投票纠错。
- **生成知识提示**补偿知识，**编程语言推理**接管计算，**工具调用**负责所有外部能力。

从第三期"让 AI 会想"，到这一期"让 AI 能查、能算、能动手"，下一期我们把这一切搬上生产线。

## 总结

| 方法 | 核心 | 适用场景 | 代价 |
| --- | --- | --- | --- |
| 生成知识提示 | 没把握先补一课，不依赖外部工具 | 常识、隐性知识类题目 | 最轻量，但可能有幻觉，需要筛选 |
| 编程语言推理 | LLM 想公式，Python 出结果，精度拉满 | 算术、多步混合运算 | 需要安全的代码沙箱 |
| 工具调用 | 自己搞不定就叫外援，模型自己判断何时用 | 从搜索引擎到日历 API 的各类实时能力 | 工程代价最高 |

这三条路线共同标志着一个转向：提示工程不再只是"怎么跟模型说话"，而是"怎么给模型搭团队"。
