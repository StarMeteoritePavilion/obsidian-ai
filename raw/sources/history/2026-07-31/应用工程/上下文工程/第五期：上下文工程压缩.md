> 上下文工程系列 第五期

对话滚了几十轮，检索出来的文档堆成山，有限的上下文窗口装不下了怎么办？答案是压缩。

压缩不是粗暴截断，而是提取精华：把 20 轮对话浓缩成 500 字摘要，把 50 页文档里真正有用的三段留下来。

一句话概括：**压缩的本质是提高信息密度，用更少的 Token 传达同样甚至更多的有效信息。**

## 压缩的全栈框架

上下文压缩是一套从软件到硬件的全栈策略：

- **底层权衡**：信息密度、保真度和压缩比。
- **技术路线**：抽取式、生成式、结构化和层次化四类压缩。
- **工程实践**：对话历史管理、锚点保护与长任务紧凑化。
- **生产能力**：Claude 的服务端压缩 API、上下文编辑与提示缓存的协同。
- **硬件侧路线**：MLA、GQA 压缩 KV 缓存，Radix Attention 在系统级复用缓存。

## 压缩的三条铁律

### 信息保真

压缩是提炼精华，不是截断。冗余词可以删，用户明确说过的约束却不能丢。例如“只用中文”这类锚点信息，必须特殊保护。

### 任务导向

没有普遍适用的最优压缩方案。写代码时要保留函数签名和技术决策；闲聊则可能只需记住用户偏好。

### 可理解性

压缩后的内容必须让模型读懂。过度精简会让语义破碎，反而比不压缩更糟。

实际选择中要持续权衡三组关系：

- **压缩率与信息完整性**：压得太重会丢掉关键信息，压得太轻则节省有限。
- **通用压缩与针对性压缩**：前者一次处理、多次使用，后者额外花费成本，但更精准。
- **成本与效果**：简单截断几乎没有处理成本，但可能切掉关键句；LLM 摘要质量高，但需要额外调用模型。

压缩还有去噪效应：在中等压缩率区间，删掉冗余和噪声后，任务质量反而可能上升。一旦越过临界点，关键信息开始丢失，质量就会急剧下降。拐点必须由评估结果决定。

## 四类压缩技术

### 抽取式压缩

抽取式压缩直接从原文挑选关键句。TextRank 借鉴 PageRank，按句子之间的相似度迭代排序，保留高分句子；嵌入方法则计算每个句子与全文的语义余弦距离，选出最接近的几句。

它的优点是保持原文、可回溯，缺点是可能漏掉分散在多处的隐含信息。

### 生成式压缩

生成式压缩让 LLM 重写一份精炼版。超长文档可以先分段摘要，合并后再摘要，绕开单个窗口的容量限制；也可以生成标题、简述和详情三种粒度。

这类方法效果好，但每次模型调用都有成本。

### 结构化压缩

结构化压缩不保留自然语言形式，而是转换成实体关系、三元组或表格。对话历史可以整理为用户目标、已确定偏好、待解决问题和当前状态。

这种格式紧凑、易解析，代价是丢失叙述连贯性。

### 层次化压缩

层次化压缩构建一座粒度金字塔：窗口空间充裕时给全文，紧张时给段落摘要，极限时只给一句结论。

它把“要么全给，要么全删”变成了按可用空间自适应提供信息。

## 对话历史管理

对话历史是压缩的主战场。多轮对话累积到几十甚至上百轮后，需要组合使用四种管理策略：

1. **滑动窗口**：只保留最近 N 轮完整原文，零处理成本、无额外延迟，但旧轮次中的关键约束也可能被删除。
2. **选择性保留**：按重要性打分，筛选需要保留的轮次。
3. **对话压缩**：用摘要替代旧轮次，不是丢弃，而是浓缩。
4. **分层管理**：热数据放在上下文，温数据放在摘要，冷数据放在外部存储，并按访问频率动态迁移。

### 锚点信息必须独立保护

用户明确说过的约束、偏好和限制，在任何压缩操作中都必须原样保留。否定约束尤其脆弱，“不要推荐海鲜”中的“不要”一旦在摘要里丢失，含义就会完全反转。

工程上应将锚点信息作为独立的上下文组件，始终放在系统提示词之后，不受其他压缩策略影响。

### 压缩后的五段式组装

压缩后的上下文按从稳定到动态的顺序排列：

1. 基本不变的系统提示词。
2. 跨会话保持的用户画像。
3. 独立保护的锚点约束。
4. 早期对话的摘要。
5. 最近几轮原文，然后紧跟当前问题。

这一顺序利用了 U 型注意力分布和长内容置顶原则。

## 长任务紧凑化

代码生成、研究分析和多轮客服等长任务需要做紧凑化：把消息历史交给 LLM，生成一份高保真摘要，保留架构决策、未解决问题和关键实现细节，丢弃冗余工具输出和过时消息，再用摘要替代旧历史继续工作。

这比普通压缩更激进，相当于对整个上下文窗口重新初始化。

### MemoryFlush：先存后压

紧凑化之前需要先做 MemoryFlush。在 LLM 生成摘要之前，先把必须长期保留的信息写入外部文件，包括关键决策、用户偏好、待办事项和当前进度。

压缩是有损的，不能保证摘要百分之百覆盖所有关键细节，因此要先存后压。

### Claude 的 compact

Anthropic 把紧凑化做成了 API 原生能力。Claude 的 compact 用一行配置由服务端自动检测 Token 用量，触发压缩、生成摘要、替换旧内容并继续响应。它支持自定义摘要指令、在压缩后暂停以注入额外内容，以及提示缓存断点。

压缩需要额外的模型采样步骤，会计入速率限制和计费用量。统计时要汇总 `usage.iterations` 数组，而不是只看顶层的 `input tokens`/`Output tokens`。

并非所有长任务都应使用 Compaction。有明确里程碑的迭代开发更适合 StructuredNoteTaking，每到一个里程碑就写结构化笔记；需要并行探索的复杂研究更适合 SubAgentArchitecture，让子智能体使用独立上下文，只返回结论摘要。

选对策略，比选对参数更重要。

## KV 缓存压缩与复用

KV 缓存大小随上下文长度线性增长，128K 上下文可以占用数十 GB 显存。压缩不只发生在软件层，硬件侧同样需要处理。

- **MLA**：MLA，DeepSeek 的方案，把 Key 和 Value 映射到低维隐向量，只在需要时扩展到多个查询头，压缩比约七倍，精度影响极小。
- **GQA**：GQA，LLaMA 3 和 Mistral 都在用，让多个查询头共享一组 KV 头。典型配置为 8:1，压缩比约八倍。
- **MQA**：GQA 的极端版，让所有查询头共享一个 KV 头。压缩最大，但精度可能下降。
- **Radix Attention**：SGLang 的 Radix Attention 从复用角度解决问题。系统维护一个全局基数树，让所有请求共享缓存节点。系统提示词或 RAG 文档相同的请求可以直接命中缓存。

再配合亲和路由，把相同前缀的请求调度到同一个 GPU 节点，可以继续提高缓存命中率。KV 缓存命中率是生产阶段最重要的单一工程指标，命中和未命中的成本可以相差十倍。

## 上下文编辑

上下文编辑，和 Compaction 的“摘要替代”不同，它使用清除策略精细删除不再需要的内容。

两类清除策略分别是：

- **工具结果清除**：清除对话深处那些调用后已经无用的工具返回结果，用占位符替换原内容。
- **思考块清除——扩展思考产生的 thinking 块**：清除后保留缓存可以延续的内容，同时释放大量 Token。

最佳实践是把清除策略与记忆工具配合：Claude 在内容被清除前，先自动把关键信息写入记忆文件。再配合提示缓存，用 `clear_at_least` 参数控制每次清除的 Token 量，确保缓存重建的收益大于成本。

Claude 的 compact 把这一切做到 API 原生，上下文编辑提供更精细的清除控制。

## 总结

七句话说完：

1. 压缩的本质是最大化信息密度，用更少的 Token 传达同样的有效信息。
2. 三条铁律分别是信息保真、任务导向和可理解性，压缩比、信息完整性、成本和效果必须按评估结果权衡。
3. 四类技术从挑选原文关键句，到 LLM 重写、结构化转换和分级保留，各有适用场景。
4. 对话历史是压缩的主战场，滑动窗口、选择性保留、对话压缩和分层管理需要组合使用，但锚点信息绝对不能丢。
5. 长任务紧凑化先用 MemoryFlush 刷写关键记忆，再用 Compaction 生成高保真摘要并重建窗口。
6. Claude 的 compact 把紧凑化做到 API 原生，上下文编辑则提供更精细的清除控制。
7. MLA、GQA 和 Radix Attention 在硬件与系统层继续压低 Token 成本。

这期讲完了怎么往窗口里挤进更多信息。下期讲怎么让信息不互相污染：结构化组织、XML 标签、深度物理隔离和逻辑隔离，以及多智能体编排中的上下文管理。
