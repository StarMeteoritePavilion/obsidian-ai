> 上下文工程系列 第四期

这一期进入上下文工程最核心的一条腿：RAG 检索增强生成。

大模型的知识截止于训练数据。你问它公司上周发布了什么，它没见过，答不出来，甚至可能硬编一套。RAG 的思路很朴素：模型记不住最新信息，那就在回答之前先去查，把相关文档塞进上下文窗口，再让模型基于这些文档生成答案。

不重新训练，不微调，只要更换外部知识源，就能让模型知道最新的事。

## RAG 的核心思想

一句话概括：**把模型的参数化记忆和非参数化记忆结合起来。**

- **参数化记忆**：训练时学到、固化在模型权重里的知识。
- **非参数化记忆**：外部知识库和向量索引中的知识。

检索器从外部知识库找到相关文档，生成器基于这些文档生成答案，两者端到端联合训练。这个想法源自 Patrick Lewis 等人在 2020 年提出的原始 RAG 论文。

当时，626M 参数的 RAG 模型在开放域问答上超越了 11B 参数的 T5 纯参数化模型。这个结果验证了一条路线：外部记忆可以比单纯堆参数更高效。

## 端到端的五步流程

RAG 的端到端流程分五步：

1. **查询处理**：把用户问题转换成可检索的形式。
2. **信息检索**：从向量数据库中找到最相关的片段。
3. **上下文构建**：把检索结果、指令和对话历史拼成完整 Prompt。
4. **模型生成**：基于增强后的上下文生成答案。
5. **输出响应**：返回带来源引用的答案。

这五步经历了三个阶段：

- **朴素 RAG**：只做简单向量检索和固定分块。
- **高级 RAG**：标配混合检索、重排序和查询增强。
- **模块化 RAG**：让检索策略自适应，并与智能体系统深度集成。

## 原始 RAG 框架

Lewis 等人在 2020 年提出的原始 RAG 框架，是一个有严格概率基础的统一模型，不是工程拼凑。

RAG 把检索文档 $z$ 当作潜在变量，边际化后产生最终输出分布。检索器使用 DPR 双编码器，分别把查询和文档编码成稠密向量，再用 FAISS 做最大内积搜索，从 2100 万个 Wikipedia 片段中找到 Top-K 文档。生成器使用 BART-large，基于输入和检索文档自回归生成答案。整个系统共有 626M 个可训练参数。

原始框架有两种配方：

- **RAG-Sequence**：整个生成序列共享同一篇文档。解码较慢，但在开放域问答上略优；检索文档越多，性能越稳定。
- **RAG-Token**：每个 Token 可以使用不同文档，在 Jeopardy 这类需要结合多篇文档信息的生成任务上更优。

几个发现到今天依然成立：

- 不需要标注应该检索哪篇文档，模型可以通过端到端训练自己学会怎么找。
- 稠密检索 DPR 在多数任务上优于关键词检索 BM25，但 BM25 在实体密集型任务上仍有优势，这成为后来混合检索的动机。
- 626M 参数的 RAG 超越了 11B 参数的纯参数化模型，展示出显著的参数效率。
- 非参数化记忆可以热替换。换掉 Wikipedia 索引就能更新世界知识，不用重新训练。

## 分块：RAG 管道的第一公里

原始文档必须切成小块才能进入向量库，分块质量直接决定检索精度。常见方法从简到繁有五种：

1. **固定大小分块**：按字符数一刀切，成本低，但经常把一句话切成两半。
2. **基于分隔符分块**：按段落、标题切分，适合结构清晰的文档。
3. **递归分块**：先用大分隔符切，块仍然太大就逐级换成更小的分隔符，直到不超过上限。它是大多数场景的推荐起点。
4. **语义分块**：用嵌入模型计算句子间相似度，在相似度低谷处断开，效果好但成本高。
5. **LLM 驱动分块**：让模型判断应该在哪里切分，能力最强，成本也最高。

分块有三条铁律：

- **块大小按任务选择**：精确问答使用 200～500 Token，综合理解使用 500～1000 Token。
- **设置重叠**：重叠范围为块大小的 10%～20%，防止关键信息正好被边界切开。
- **保留元数据**：来源、位置、标题层级和时间戳都要保留，否则检索出片段后无法知道它来自哪里。

## 混合检索、RRF 与重排序

语义检索懂意思，但可能漏掉精确术语；关键词检索匹配精确，却不理解同义改写。把两者融合的混合检索，是当前生产环境的标准配置，并在高级 RAG 中配合重排序进一步筛选结果。

常用的融合算法是 **RRF（Reciprocal Rank Fusion，倒数排名融合）**。不同检索器的原始分数刻度不同，直接加权并不可靠。RRF 不比较原始分数，只看一条结果分别排在语义检索和关键词检索的第几名，因此天然不受分数分布差异影响，也不需要调权重。

## 查询增强的三板斧

在检索之前改造查询，可以进一步提高精度。

### 查询扩展

把“空调不制冷”扩展成一组相关词，横向扩大检索覆盖范围。

### 查询分解

遇到“A 公司和 B 公司谁的收入更高”这类对比问题，拆成两个子查询，分别检索后再融合。

### HyDE

HyDE 不直接使用查询向量检索，而是先让 LLM 根据查询生成一个假设答案，再用假设答案的向量去检索。假设答案的文本结构更接近真实文档，能够跨过查询和文档用词不同造成的语义鸿沟。

## 多跳检索与自适应检索

有些问题一次检索不够。例如，要查询某位图灵奖得主的老师是谁，就要先检索出这位获奖者的导师，再用导师的名字检索其背景。

这就是**多跳检索**：每一跳的结果为下一跳提供方向，让推理和检索交替推进。

**自适应检索**更进一步。不是所有问题都需要检索，也不是所有问题都应该用同一种检索方式。路由机制按照查询类型分发：

- 事实查询走关键词精确匹配。
- 概念查询走语义检索。
- 对比查询走多路并行，再融合结果。

最容易被忽视的优化是识别免检索请求。常识和创意任务不需要外部事实，就不要为它们增加延迟和 Token 成本。这正呼应了上一期的注意力预算原则：每个塞进窗口的 Token 都要值得花。

## MemoryCube：让检索发生在提问之前

传统 RAG 是被动、阻断式的：用户提问之后，系统才开始检索、拼接和推理，每一步串行执行，都在拉长用户感知延迟。用户打字、阅读、思考的碎片时间里，系统却处于闲置状态。

MemoryCube 的思路，是把这批闲置时间利用起来。用户还没有发出查询时，系统就根据上下文预测意图，异步预加载可能的检索结果，并提前组装上下文。等用户真正提问，只差模型推理这一步。

这让 RAG 从“请求到了才检索”转向全时持续调度。问题不再只是“怎么检索”，还包括“什么时候检索”。它也是上一期四大策略在时间维度上的深化。

## 总结

七句话说完：

1. RAG 的本质，是把参数化记忆和非参数化记忆统一在同一个概率框架里。
2. Lewis 等人在 2020 年提出的 RAG-Sequence 和 RAG-Token，至今仍是理论基础；RAG 从朴素阶段发展到高级和模块化阶段，混合检索与重排序已经成为标配。
3. 分块是第一公里，递归分块是大多数场景的推荐起点，元数据决定检索后上下文是否可追溯。
4. 混合检索使用 RRF 融合排名，避开不同检索器的分数分布差异。
5. 查询增强通过扩展、分解和 HyDE 提高召回效果。
6. 多跳检索与自适应检索用于复杂场景的路由分发，按需检索，不浪费 Token。
7. MemoryCube 在时间维度上打开一条新路，让检索发生在用户提问之前。
