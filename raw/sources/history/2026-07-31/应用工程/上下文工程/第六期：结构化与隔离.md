> 上下文工程系列 第六期

给 AI 塞进一堆资料，它却把资料中的一句话当成命令；两个任务放在一起，A 的规则混进了 B 的输出。这不是模型笨，而是上下文成了大杂烩。

本期讲两道防线：

- **结构化**：用标签说明每块信息的用途，让模型分清指令、文档、示例和输入。
- **隔离**：给不同任务划定边界，防止约束、状态和结果互相污染。

结构化是内务整理，隔离是任务之间的边界管理。前者让一个上下文内部井然有序，后者让不同上下文互不串台。

## 结构化的四项原则

### 分类清晰

指令和文档不能混装，否则模型可能把文档中的文字当成命令执行。每类内容都要有明确身份。

### 层次分明

结合长上下文中的 U 型注意力分布，重要内容放在首尾，细节放在中间。层次不仅是排版，也是注意力调度。

### 边界明确

不同信息块必须有清晰边界。边界模糊，任务和规则就容易跨区串台。

### 关系显式

文档之间的从属、引用和上下位关系要直接标注，不让模型猜测。

## 三种结构化工具

结构化上下文有三种常用工具：

- **分隔符**：最简单、最省 Token，适合内容类型少的场景。
- **XML**：适合复杂上下文，模型对标签和嵌套结构的解析更准确。
- **JSON**：适合程序化拼装、传递和自动测试。

选型判据只有一条：**上下文里有几类内容，就选哪类武器。** 只有指令和文档两类内容时，分隔符足够；同时包含指令、文档、示例、约束和格式等多类内容时，使用 XML；需要程序化处理时，使用 JSON。

## XML 的六类标签

六类标签可以覆盖大部分上下文内容：

- `<instructions>`：任务指令。
- `<context>`：知识。
- `<examples>`：示例。
- `<constraints>`：约束。
- `<format>`：输出格式。
- `<user_input>`：用户输入。

嵌套用于表达层级。例如，用 `<documents>` 包住文档集合，每篇文档使用 `<document index="1">`，内部再用 `<source>` 标记来源、用 `<content>` 包裹正文。

### XML 结构化三律

1. **命名统一**：全团队采用同一种命名风格，不混用蛇形命名和驼峰命名。
2. **嵌套不超过三层**：层级过深会增加解析难度，能扁平化就扁平化。
3. **用户输入动态转义**：用 `html.escape()` 处理用户输入，避免输入中的标签被当作真实结构。

如果用户输入中包含 `</instructions>`，未经转义就可能提前闭合指令区，形成标签注入。转义后，它只是一段普通文本，不再改变上下文结构。

## 按稳定性划分四层 Prompt

Prompt 不是一整段话，而是按稳定性划分的四层结构：

- **L1 核心身份**：定义模型身份，版本级稳定，可以缓存。
- **L2 任务框架**：划定行为边界，为任务画出行为圈。
- **L3 具体指令**：描述当前任务，每轮都可能变化。
- **L4 格式约束**：规定输出形式，比 L3 更稳定。

工程上预定义并缓存 L1、L2，每轮动态组装 L3、L4，并分别用 XML 标签包裹。这样既能复用稳定前缀，也能让模型看清各层优先级，避免格式约束覆盖身份定义。

## 三类上下文污染

把不同任务混在一起，会产生三类污染：

1. **任务混淆**：A 的约束被套到 B 的任务上。
2. **优先级冲突**：两个任务的指令彼此矛盾。
3. **状态混乱**：各任务的进度和中间状态搅在一起。

## 隔离的三道防线

### 物理隔离

不同任务使用独立 API 调用和独立上下文，边界最强，成本也最高。支付、权限等出错后果严重的高风险任务，应采用物理隔离。

### 逻辑隔离

逻辑隔离在同一窗口中使用 `namespace` 分区，适合内部流水线。它更灵活，但不同分区仍共享一个上下文，因此存在串台风险。

### 代码沙箱

让 LLM 编写 Python 并在沙箱中执行。图片、音频等大对象留在执行环境，只把返回值交回主上下文。执行环境本身就是隔离边界，还能减少大对象占用的 Token。

隔离遵循一条总原则：**默认隔离，确认需要再放开。**

## 子智能体：隔离的生产级方案

多智能体架构中，主智能体负责协调，子智能体使用独立上下文完成探索，结束后只交付蒸馏摘要。视频引用 Anthropic 的测试结果称，多智能体系统比单智能体提升 90%。

这套模式有两条硬规矩：

1. **最小信息原则**：子智能体可以完成几万 Token 的探索，但只向主智能体提交约 1000 字的蒸馏摘要，不传原始日志和完整对话历史。
2. **显式接口**：使用 JSON 标准化传递结果，固定为三个字段：`conclusion`、`key_facts`、`next_hints`。显式接口让交付可追踪、可调试、可自动测试。

## 五项工程实践

1. **默认隔离**：初始状态不共享，确认需要后再开放。
2. **清晰边界**：明确每个单元的输入和输出。
3. **最小共享**：逐项评估共享信息是否必要。
4. **显式传递**：通过明确接口交付，不依赖隐式继承。
5. **独立测试**：使用 mock 数据单独验证每个单元。

## 总结

六句话说完：

1. 结构化遵循分类清晰、层次分明、边界明确、关系显式四项原则。
2. 分隔符、XML 和 JSON 分别适合简单分区、复杂结构和程序化场景；内容类型决定工具选择。
3. XML 使用六类标签，并遵守命名统一、嵌套不超过三层、用户输入动态转义三律。
4. Prompt 按稳定性拆成 L1 核心身份、L2 任务框架、L3 具体指令、L4 格式约束，稳定层缓存，动态层每轮组装。
5. 物理隔离、逻辑隔离和代码沙箱从不同层面阻断污染，默认先隔离，确认需要再放开。
6. 子智能体用独立上下文探索，只通过显式 JSON 接口提交蒸馏摘要，是隔离在生产系统中的落地方式。
