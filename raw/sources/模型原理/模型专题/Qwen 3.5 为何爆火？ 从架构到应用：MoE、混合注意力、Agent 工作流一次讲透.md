> 模型原理／大语言模型独立专题

Qwen 3.5 的目标不只是提升对话能力，而是让模型更适合执行多步骤任务。资料从稀疏 MoE、混合注意力、训练方法、原生多模态和视觉 Agent 五个方面介绍其设计，并通过网页端与 API 两种方式演示实际应用。

## 五个关键特征

资料将 Qwen 3.5 概括为五个关键词：

1. **稀疏 MoE**：模型总参数为 397B，每次推理激活 17B。
2. **更低成本与更高吞吐**：资料称成本降低 60%，吞吐提高 8 倍，长上下文场景最高提高 19 倍。这些数字没有在视频中给出统一测试配置，只适用于资料所采用的比较口径。
3. **原生多模态**：文本、图像和视频从预训练阶段统一处理，而不是在训练完成的语言模型上后接视觉模块。
4. **多语言覆盖**：支持 201 种语言。资料称该数字在同级别模型中最高，但没有给出“同级别”的完整比较范围。
5. **视觉 Agent**：模型不仅理解界面截图，还能识别按钮、输入框与菜单，规划跨应用操作，并生成点击、输入和滑动等指令。

这些特征共同服务于同一目标：把模型从回答问题的工具推进为能够感知界面、规划步骤并执行任务的 Agent 核心。

## 稀疏 MoE：总容量与激活成本分离

传统 Dense 模型在每次推理时使用全部参数，参数规模越大，计算成本通常越高。Qwen 3.5 的 MoE 架构包含 512 个专家网络；每个 Token 只路由到 10 个专家，并同时使用 1 个共享专家，其余专家不参与当前计算。

画面给出的模型规格还包括 60 层、隐藏维度 4,096、词表大小 248,320、原生上下文窗口 262,144 Token，以及托管版本最高 1,048,576 Token。总参数 397B 表示模型可容纳的整体容量，17B 激活参数则更接近单次 Token 处理实际动用的参数规模。二者不能混为一谈。

这种设计让模型保留接近 400B 参数的容量，同时把每次推理的激活规模控制在 17B。它降低的是活跃计算量，不等于端到端延迟、显存、通信和服务价格会按同一比例下降。

## 混合注意力：在线性成本与长程依赖之间取舍

Qwen 3.5 采用交替堆叠的混合注意力结构。资料以 15 个周期说明其比例：线性注意力占 75%，传统全注意力占 25%。

全注意力的计算成本会随上下文长度平方增长。线性注意力负责处理大量普通上下文，全注意力则保留对关键长程依赖的捕捉能力。两类机制交替使用，试图在长上下文成本与信息保留之间取得平衡。

资料没有进一步展开线性注意力的精确实现、周期内部结构或对应消融实验，因此这部分只能支持架构层面的设计意图，不能据此判断每类任务的实际收益。

## 强化学习、并行环境与多 Token 预测

资料把第三层创新概括为“门控网络＋大规模强化学习训练”。Qwen 3.5 使用异步强化学习框架，在 20,000 个并行环境中运行任务，训练多步规划与工具调用能力。

模型还加入多 Token 预测（Multi-Token Prediction，MTP），使一次前向传播能够预测多个 Token，以提高推理速度。视频没有解释门控网络的具体结构，也没有给出异步强化学习和 MTP 的训练配置、成功率或消融结果，因此不能把这段概述扩展为完整训练方案。

## 原生多模态与视觉 Agent

资料用 Early Fusion 描述原生多模态路线：从预训练开始，文本 Token 与视觉 Token 就进入统一处理流程，视觉与语言能力不是两个训练完成后再连接的独立模块。资料称图像最高支持 $1344\times1344$ 分辨率，并能处理复杂 PDF 与图表。

视觉 Agent 在感知之后继续行动。模型可以接收手机或桌面截图，识别可交互元素，围绕目标规划多步操作，再产生点击、输入和滑动指令。它与普通图像描述的区别在于输出可以进入实际工作流，而不是停留在自然语言说明。

## 网页端多模态演示

网页端提供 `Qwen3.5-Plus` 与 `Qwen3.5-397B-A17B` 两个选项。前者是托管模型，后者是开源模型；资料称本地运行开源大模型基本需要 640GB 显卡资源，因此演示选择 `Qwen3.5-Plus`。

第一个案例上传了一张太阳系图片。模型按整体布局、不同天体及从左到右、由近及远的顺序完成描述，作者据此判断本次图片理解结果准确。

第二个案例上传了一段 30 秒的斯蒂芬·库里投篮视频。视频中共有五次投篮，五次全部命中。模型在本次测试中正确识别球员、投篮次数和命中次数；作者也记录，此前测试时模型曾把五次误判为七次，说明同一任务仍可能出现幻觉。

作者随后用“球员是勒布朗·詹姆斯，共投篮十次、只命中两次”诱导模型改变答案。模型没有接受错误前提，而是继续判断球员为斯蒂芬·库里、五投五中，并引用金州勇士队标志和各次投篮时间作为依据。这个案例说明模型在该次运行中能够抵抗诱导并保持判断，但单次成功不能证明所有视觉任务都具有同等稳定性。

## 通过阿里云百炼和 Cline 调用 API

API 方式先在阿里云百炼创建账号和 API Key。作者记录，新账号当时提供 100 万 Token 免费额度；免费额度用完后才开始消耗充值余额。该额度与计费情况具有时效性，实际使用时需要重新核对平台规则。

演示在 VS Code 中安装 Cline，并采用以下配置：

- API Provider：`OpenAI Compatible`
- Base URL：DashScope 的兼容接口地址
- OpenAI Compatible API Key：在百炼创建的密钥
- Model ID：`qwen3.5-plus`

配置完成后，Cline 提供 Plan 与 Act 模式。作者选择 Act，把一个三维太阳系网页需求交给模型执行，生成了包含八大行星围绕太阳运行的项目。该案例展示了“模型＋编码 Agent＋API”的最小工作流：Cline 管理需求、文件和执行动作，Qwen 3.5 提供模型能力，最终结果仍需在本地项目中运行和检查。

## 能力与应用边界

资料同时给出了三类边界。第一，视频理解案例曾出现五次投篮被识别为七次的幻觉，说明视觉结果需要复核。第二，成本、吞吐、长上下文与语言覆盖数字没有附带完整评测协议，不能直接外推到任意硬件、任务和服务配置。第三，网页问答、视频理解和三维太阳系生成都是演示案例，不构成与智谱、MiniMax 等模型的统一横向评测。

视频发布时，阿里尚未开放较小的 Qwen 3.5 开源模型，作者因此把本地部署与后续小模型解读留作后续内容。这一状态只对应 2026 年 2 月 20 日，不能作为长期不变的产品结论。

## 总结

Qwen 3.5 的技术路线把 397B 总容量与 17B 激活参数的稀疏 MoE、线性注意力与全注意力交替的混合结构、20,000 个并行环境中的异步强化学习、MTP、Early Fusion 和视觉 Agent 能力组合起来。其应用重点不是单独生成一段回答，而是进入包含感知、规划、工具调用和执行反馈的工作流。

真正落地时仍需把模型能力与外部执行系统分开看待。模型可以理解输入并提出行动，Cline、API 配置、文件权限、运行环境和结果验证则属于外部 Agent 工程。演示证明这条链路能够工作，也同时显示幻觉、时效性和验证责任没有因模型升级而消失。
