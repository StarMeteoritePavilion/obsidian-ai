# Jev的原理是什么？

> 从逐字生成到一次返回多个受限判断

作者以“上个月突然刷屏”的 Jev 引出一种不同于日常聊天大模型的使用方式。据他转述，Jev 发布一周后，GitHub 上已有 2000 多个项目使用；官方宣称它比常用大模型快 200 多倍，每百万输入 Token 收费 4 美分，输出免费。

这些消息被反复传播，容易让人以为通用大模型的能力边界又被突破。理解 Jev 更合适的起点，是看它究竟解决什么任务，以及它省去了普通文字生成流程中的哪些工作。

## 用生成式大模型分类评论的三个问题

假设外卖平台每天需要阅读大量评价，例如“送得挺快，就是汤洒了一半”，并将其划分为好评、中评或差评。把评论放入提示词，再要求“告诉我这是好评、中评还是差评”，大多数常用模型都能完成。

### 逐 Token 生成怎样得到“中评”

模型先将文字切分为 Token。作者用“一个 Token 大约相当于一个字或一个词、词表包含十几万个 Token”作直观说明，表示模型可以处理大量文字与符号。

读完提示词后，模型为词表中的 Token 计算分数，再换算为概率。在本例采用的最高概率选择方式中，先选出“中”，把它接到已有文本后，再计算下一步并选出“评”，随后继续，直到选出表示结束的 Token。

这种逐步生成的方式用于评论分类时，会暴露三个问题。

### 速度随输出长度增加

按作者每字一个 Token 的示意，回答“中评”要生成两步；若改成“我认为是中评”，又多出四步。带思维链的模型还可能输出上百字，生成步骤随之增加。

分类本来只需要一个结果，却可能为组织文字和解释消耗更多计算。

### 输出格式不稳定

模型可能回复“中评。”、“我认为是中评”，也可能给出“中评偏差评”，都不一定符合系统要求的三个固定标签。

提示词可以要求“只回答差评、中评、好评三种结果”，但作者认为，仅靠提示约束仍难以保证每次遵守，往往还要加程序检查，不合格就重试。

### 单个标签不说明判断有多确定

只收到“中评”，无法区分模型是明显偏向中评，还是觉得中评与差评都说得通、最终选了其中一个。标签本身没有呈现不同选项之间的倾向。

## 只读取首个 Token 的概率，能解决多少问题？

既然生成前已经有各 Token 的概率，一个直接办法是停止生成文字，只取所需标签的概率。

对于同一条评论，只运行一次，读取“好”“中”“差”三个 Token。作者给出的例子是：好 9%、中 63%、差 18%，合计 90%；其余所有 Token 合计 10%。

将三个概率分别除以 90%，归一化后得到好 10%、中 70%、差 20%。作者把其中的 70% 解释为模型选择中评的把握。

在这个简化任务中，一次运行便得到结果，输出被限定在三个选项内，同时还有每项概率，看起来兼顾速度、格式与置信度。但这种首 Token 取概率的方法仍有两个漏洞。

### 选项共用开头时，首 Token 不足以区分

将问题改为“这条评价的问题出在哪”，选项为“餐品洒漏”“餐品变凉”“配送超时”“少送漏送”。前两个选项都以“餐”开头，只读第一个字就无法比较它们。

按本例的逐字方式，至少需要继续到第三个字，区分“餐品洒”与“餐品变”。这意味着重新引入多步生成，而且完整选项的最终概率怎样计算，也成为需要处理的问题。

### 多个问题仍需分别处理

一条评价可能同时涉及满意度、是否退款和生气程度。只检查某一次下一 Token 分布，这套方法只能针对当前问题读取选项概率；三个问题就需要分别运行三次。

## Jev 的接口：给定问题，直接返回结果与概率

作者介绍，Jev 不生成自由文本。调用者提供一段内容和一组问题，它直接返回这些问题的结果，支持三种形式：

1. **选择题**：例如好评、中评、差评。可以提供 200 多个选项，所述上限为 255 个，并返回每个选项的概率。
2. **是非题**：例如是否给用户退款，返回“是”的概率，可以理解为选择题的简化形式。
3. **打分题**：例如用户生气程度从 1 到 5，返回相应评分结果与概率信息。

同一次请求可以提出多个问题，结果一起返回。作者将这种方式概括为：只运行一次，便得到所有问题的答案；输出来自预先定义的范围，每个结果带有概率。

他也用“不需要像聊天模型一样生成文字”解释输出免费的原因。这里仍然有答案与概率返回，省去的是逐字生成自由回复的过程。

## 作者的实现推演：从文字接龙改为填空

作者明确说明，发布 Jev 的 TypeSafe 公司没有公开内部实现。以下是他提出的一种技术上可行的方案，不保证与 Jev 的实际实现相同。

### 两类训练任务的区别

文字接龙式训练可以用“我是老王”说明：输入“我”，训练输出“是”；输入“我是”，训练输出“老”；输入“我是老”，训练输出“王”。作者以 GPT、Claude、DeepSeek、千问等模型说明这条路线。

另一类任务是填空。Google 的 BERT 可以接收“我 [MASK] 老王”，恢复被遮盖的“是”；接收“我是 [MASK] 王”，恢复“老”。作者将这类结构用于概括输入内容的表示能力，与处理图像的 Vision Transformer 作类比。

这为一次处理多个答案位置提供了思路。

### 将多个问题与占位符放进同一输入

在作者的设想中，训练材料是人工标注的评论。对于“送得挺快，就是汤洒了一半”，示例标签为中评、退款概率 60%、生气程度 2 分。

输入先放评论，再依次放入“好评、中评还是差评？”及其答案占位符、“退款概率”及其占位符、“有多生气”及其占位符。训练目标分别对应“中评”“60%”和“2”。

使用时，把新评论与各个“问题＋占位符”放在一起。整段输入运行一次，各答案位置便同时形成结果。

不过，传统 BERT 的填空示例是在占位符处恢复一个词元，用户需要的却可能是完整标签、百分比或评分。作者因此进一步改变答案的表示方法。

## 用答案 Embedding 连接表示与选项

### 不恢复某个字，而是预测答案表示

作者用“文字的压缩”直观解释 Embedding：语义相近的文字，其表示也应接近。例如，“中评”与“一般”“中等评价”“马马虎虎”较近，与“差评”较远，与“我是老王”差别更大。

沿这一思路，不再要求占位符输出答案文字，而是预测与正确答案对应的 Embedding。每个占位符形成一个答案向量，再拿它与用户提供的选项向量比较。

真实 Embedding 往往包含上千个数，作者用三维向量简化演示：

- 好评：`[0.3, 0.1, 0.8]`。
- 中评：`[0.9, 0.1, 0.2]`。
- 差评：`[0.1, 0.9, 0.3]`。
- 模型在占位符处预测：`[0.9, 0.1, 0.1]`。

### 点积得到选项分数，再转成概率

本例将对应位置相乘后相加，得分越高，表示匹配程度越高。预测向量与中评的计算为：

$$
0.9\times0.9+0.1\times0.1+0.1\times0.2=0.84
$$

与好评的得分为 0.36，与差评的得分为 0.21。随后把分数换算成概率，中评最高，成为输出。作者将各选项概率称为置信度。

是非题和打分题也可以按这个思路处理。退款问题把“是”“否”作为选项，“是”的概率就是所需百分比；生气程度则比较输出向量与 1 到 5 各档答案的 Embedding。

### 训练目标随答案表示一起改变

答案改用向量表示，训练目标也不再是恢复某个字。按照作者的解释，预测 Embedding 越接近正确答案 Embedding，越应得到奖励；距离越远，越应受到惩罚。

作者进一步提出：训练题足够多、选项足够丰富时，模型学到的就不再只是某一道题的答案，而是“答案位置应靠近哪个选项”的规律；因此，即使新写一个选项，也能答对。这是他对这一训练方案泛化能力的判断。

至此，作者完成了一个类 Jev 方案的原理推演：将内容和多个问题共同编码，再在各个答案位置与限定选项比较，直接形成判断。

## 判断与解释，谁先发生？

Jev 引出另一个问题：大模型写下几千字思维链时，判断是否可能在第一个字生成之前就已经形成？无需长篇表达的判断，与看起来深思熟虑的解释之间，究竟是什么关系？

作者借认知科学家加扎尼加研究裂脑病人的案例作类比：据其转述，人常常先做出决定，再由负责说话的半边大脑给出解释。这是他提出问题的联想。

他又用一个下班后的个人场景收束：到了楼下，坐在车里迟迟不想上楼，闭眼沉默很久，才在心里解释“我只是累了，想一个人静静”。判断何时形成、语言又怎样解释它，仍是值得追问的问题。
